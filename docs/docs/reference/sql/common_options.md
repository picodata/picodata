# Общие опции SQL-запросов

В этом справочнике описаны опции SQL-запросов и особенности их применения.

## Обзор опций {: #overview }

В таблице ниже показаны возможные опции, их применимость, расположение и доступность:

| Опция | Запросы | Место в запросе | В подключении | В [ALTER SYSTEM] |
|---|---|---|---|---|
| [**FORWARD**](#forward) | [DQL] и [DML]: `INSERT`, `UPDATE`, `DELETE`, `CALL`; `DO`-блок; `EXPLAIN` | блок `OPTION(...)` | да | нет |
| [**SQL_VDBE_OPCODE_MAX**](#vdbe) | [DQL] и [DML]: `SELECT` (и `VALUES`), `INSERT`, `UPDATE`, `DELETE`, `CALL`; `DO`-блок; `EXPLAIN` | блок `OPTION(...)` | да | да (`sql_vdbe_opcode_max`) |
| [**SQL_MOTION_ROW_MAX**](#vdbe) | [DQL] и [DML]: `INSERT`, `UPDATE`, `DELETE`, `CALL`; `DO`-блок; `EXPLAIN` | блок `OPTION(...)` | да | да (`sql_motion_row_max`) |
| [**READ_PREFERENCE**](#read_preference) | [DQL] | блок `OPTION(...)` | да | да (`read_preference`) |
| [**TIMEOUT**](#timeout) | [DDL] (`CREATE`/`ALTER`/`DROP TABLE`, индексы и т.п.), [DCL] (`CREATE`/`ALTER`/`DROP USER` и тп), `BACKUP`, `ALTER SYSTEM`, команды плагинов | блок `OPTION (TIMEOUT = N)` в конце команды | нет | да (`sql_ddl_timeout`) |
| [**WAIT APPLIED**](#wait_applied) | [DDL], [DCL], `BACKUP`, `ALTER SYSTEM` | конструкция `WAIT APPLIED GLOBALLY \| LOCALLY` | нет | нет |
| [**ROLLBACK_TIMEOUT**](#rollback_timeout) | `ALTER PLUGIN ... MIGRATE TO` | блок `OPTION(...)` | нет | нет |

## Использование и ограничения {: #usage }

При указании опций разными способами следует помнить о приоритетах и
особенностях применения опций. Значение, которое будет использовано, выбирается
в соответствии с приоритетом:

**Приоритет 1: уровень SQL-запроса**<br>
Опции можно задавать явно в запросах (блок
OPTION) — допускается указание опций в любом порядке. Все опции можно
дублировать — приоритетным будет последнее указанное значение (однако, это не
относится к опции <a href=#timeout_note>TIMEOUT</a> и параметру <a
href=#wait_applied_note>WAIT APPLIED</a>).

Также, некоторые опции в SQL-запросе могут быть параметризованы, например:

```sql
SELECT 1 OPTION (sql_vdbe_opcode_max=$1);
```

где `$1` — значение, передающееся как параметр запроса через протокол PostgreSQL.

**Приоритет 2: уровень соединения**<br>
Некоторые опции (например, [FORWARD](#forward)) можно задавать на уровне соединения как параметр
подключения. В таком случае все запросы, выполняемые на этом соединении, будут
использовать указанные опции (если они не переопределены запросом).

Для использования опций при подключении к инстансу Picodata применяется следующий синтаксис:

```shell title="Пример для Psql"
psql postgres://postgres:T0psecret@127.0.0.1:4327?options=forward%3Doff
```

**Приоритет 3: конфигурация СУБД**<br>
Некоторые опции (например, [SQL_VDBE_OPCODE_MAX](#vdbe))
можно задавать на уровне конфигурации через [ALTER SYSTEM](alter_system.md).

## Описание опций {: #options_details }

### Ограничение сетевых пересылок {: #forward }

Для всех [DQL]- и [DML]-запросов поддерживается опция [FORWARD], которая
даёт возможность пользователям ограничивать количество пересылок по
сети. Так, если для исполнения запроса требуется больше пересылок, чем
разрешено, то пользователь получит ошибку на этапе исполнения запроса.
Подробнее с информацией об опции FORWARD можно ознакомиться в
[соответствующем разделе](forward_option.md).

### Исполнение плана запроса {: #vdbe }

Для всех [DQL]- и [DML]-запросов поддерживается явное указание ограничений на
инструкции исполнения плана и число строк в виртуальной таблице:

* **SQL_VDBE_OPCODE_MAX** — ограничение на максимальное количество
  [инструкций](https://www.sqlite.org/opcode.html) при исполнении
  локального плана ([VDBE](https://www.sqlite.org/vdbe.html)) на узле
  кластера.
* **SQL_MOTION_ROW_MAX** — ограничение на максимальное число строк в
  результирующей виртуальной таблице, собирающей результаты отдельных
  локальных запросов.

См. также:

- [Неблокирующие запросы](non_block.md)

### Чтение данных с реплики указанного типа {: #read_preference }

Для [DQL]-запросов [SELECT] поддерживается специальная опция
**READ_PREFERENCE** — предпочтительная стратегия чтения данных с
репликасета. Допустимые значения:

* `LEADER` (по умолчанию) — чтение производится только с
[лидеров](../../overview/glossary.md#leader)
[репликасетов](../../overview/glossary.md#replicaset). Это безопасная и
рекомендуемая стратегия, так как
[vshard](../../overview/glossary.md#vshard) контролирует перемещение
бакетов только на лидерах. В [неблокирующем SQL](non_block.md) чтение
всегда выполняется с лидеров, другие значения опции вернут ошибку.
* `ANY` — чтение производится с ближайшей доступной реплики, а при ее
отсутствии — с лидера. Если запрос может быть полностью выполнен через
локальный fast-path на экземпляре, куда он пришел (например, запрос
маршрутизируется в локальный репликасет или весь целевой tier локален),
то Picodata выполняет его на текущем экземпляре, включая лидера. Это
поведение уменьшает число сетевых пересылок для локальных запросов.
**Важно:** во время выполнения DQL-запросов не должно быть пишущей
нагрузки и изменений топологии кластера. Это помогает избежать
перемещения бакетов, которое может привести к неконсистентным
результатам. Использование этой стратегии помогает лучше утилизировать
ресурсы.
* `REPLICA` — чтение производится только с ближайшей доступной реплики,
а при ее отсутствии запрос возвращает ошибку. Если запрос может быть
полностью выполнен через локальный fast-path на экземпляре, куда он
пришел, то этот fast-path используется только на реплике. Если тот же
запрос приходит на лидер, Picodata отправляет его на доступную реплику
обычным маршрутом, а не исполняет локально. Требования к отсутствию
пишущей нагрузки и изменений топологии аналогичны `ANY`.

### Ожидание применения изменений в кластере {: #timeout_and_wait }

#### TIMEOUT {: #timeout }

Для всех [DCL]-запросов и большинства [DDL]-запросов поддерживается общая
опция **TIMEOUT**, которая нужна для синхронизации
изменений в кластере СУБД:

* **TIMEOUT** — интервал времени, за который Picodata пытается выполнить
  указанное действие/изменение объекта в кластере. Если времени не
  хватило и вернулась ошибка, то или действие не успело примениться
  (целевой объект ещё не изменён), или успело, но нам не хватило времени
  получить об этом подтверждение. Чтобы проверить статус выполнения
  команды, можно повторить её ещё раз. Если указанное действие/изменение
  объекта применилось успешно, то в результате вернется нуль строк. В
  противном случае вернётся одна строка. Если параметр не указан,
  используется значение системного параметра
  [`sql_ddl_timeout`](../db_config.md#sql_ddl_timeout) (по умолчанию
  86400 секунд, что эквивалентно 24 часам).

<a name="timeout_note"></a>
!!! note "Примечание"
    Опцию TIMEOUT можно указать в запросе только один
    раз. Повторное указание приведёт к ошибке разбора запроса.

#### WAIT APPLIED {: #wait_applied }

Дополнительно предусмотрен параметр WAIT APPLIED, который находится вне блока OPTION:

* **WAIT APPLIED** — при использовании этого параметра контроль пользователю
  будет возвращен только после того как данная операция будет применена либо во
  всем кластере (`GLOBALLY`), либо в рамках текущего инстанса (`LOCALLY`). По
  умолчанию используется поведение `GLOBALLY`.

<a name="wait_applied_note"></a>
!!! note "Примечание"
    Параметр WAIT APPLIED находися вне блока OPTIONS, и его можно указать в
    запросе только один раз. Повторное указание приведёт к ошибке разбора запроса.

### Ожидание отката миграции {: #rollback_timeout }

Специфическая опция для [ALTER_PLUGIN]:

* **ROLLBACK_TIMEOUT** — интервал времени, за который Picodata пытается
  выполнить откат миграции. Помимо недостаточного общего таймаута
  миграции, причиной отката может служить ошибка хотя бы одной команды
  из скрипта миграции. Откат запускается автоматически непосредственно
  после ошибки миграции. Если параметр не указан, используется значение
  системного параметра
  [`sql_ddl_timeout`](../db_config.md#sql_ddl_timeout) (по умолчанию
  86400 секунд).
