# Учётные данные

Страница описывает ключи доступа S3: что получает пользователь хранилища и как
администратор выдаёт, меняет и отзывает ключи. Первый раздел нужен
разработчику, который подключает клиент; остальные нужны администратору кластера
или [тенанта](../reference/glossary.md#tenant).

## Ключ доступа и пользователь Picodata {: #storage_credentials }

Клиент S3 подписывает запросы парой из
[идентификатора ключа доступа](../reference/glossary.md#access_key_id) и
[секретного ключа](../reference/glossary.md#secret_access_key). Пару выдаёт
администратор.

Ключ доступа S3 сопоставляется с пользователем Picodata, и права на операции S3
проверяются средствами СУБД. Отдельной системы управления доступом плагин не
вводит. Из этого следует:

- ключ действителен, пока существует пользователь, которому он выдан;
- срок действия для ключа доступа не задаётся;
- одному пользователю можно выдать несколько ключей;
- запрос, подписанный неизвестным ключом, отклоняется. Запрос без подписи
  выполняется, только если это разрешает
  [список управления доступом](access.md#acl) или
  [политика бакета](access.md#bucket_policy);
- ключ доступа S3 не даёт права входа в СУБД (см.
  [Пароль для входа по SQL](#sql_client_password)).

## Выдача ключей (для администратора) {: #credentials_issue }

Ключи доступа хранятся в глобальной таблице `s3r_credential`. В таблице указаны
тенант, которому принадлежит ключ, и пользователь Picodata. Ключи выдаются
тремя способами:

- через [API управления](../reference/management_api.md) или
  [консоль](../admin/console.md#console_users_and_keys): запрос
  `POST /v2/credentials` с телом `{"username": "alice"}` создаёт ключ и
  возвращает секретный ключ один раз, в ответе на этот запрос;
- для тенанта 0 параметром `s3r_api.credentials` (см.
  [Начальный список ключей](#credentials_seed));
- для тенантов, созданных после установки, только через [API управления](../reference/glossary.md#management_api)
  тенанта.

Действующие ключи показывает запрос:

```sql
SELECT access_key, tenant_id, pico_user, state FROM s3r_credential;
```

Роли создаются миграциями плагина; см. [Ролевая модель
тенантов](../concepts/tenants.md#tenants_role_model).

### Начальный список ключей {: #credentials_seed }

Параметр `s3r_api.credentials` служит начальным списком ключей тенанта 0.
Пользователь, указанный в `pico_user`, должен существовать заранее:

```sql
CREATE USER "alice" WITH PASSWORD '...' USING scram-sha256;

ALTER PLUGIN s3r 2.2.0 SET s3r_api.credentials =
  '[{"access_key":"AKIA...","secret_key":"...","pico_user":"alice"}]';
```

!!! warning "Параметр `pico_user` обязателен на практике"
    Если параметр `pico_user` не указан, пользователем считается сам ключ
    доступа. Пользователя с таким именем, как правило, нет, и подписанные
    запросы отклоняются с сообщением о неизвестном ключе доступа.

При каждом запуске сервиса `s3r_api` ключи из списка добавляются в таблицу
`s3r_credential`. Запуск сервиса этой записи не ждёт: пока строка ключа не
записана, подписанные им запросы отклоняются как запросы с неизвестным ключом
доступа. Когда записаны все ключи списка, в журнале [инстанса](../reference/glossary.md#instance) появляется строка
`seeded N credential(s) into s3r_credential`.

Список только добавляет ключи:

- ключи, созданные администратором, он не удаляет;
- ключ из списка, который уже есть в таблице, получает пользователя и секретный
  ключ из списка, а его состояние не меняется: отключённый ключ остаётся
  отключённым после перезапуска сервиса;
- ключ, который уже совпадает со списком, не записывается заново.

Пустой список не переводит эндпоинт в режим без аутентификации: ключи из
таблицы `s3r_credential` продолжают действовать, а неизвестные ключи
отклоняются. Запрос без подписи выполняется, только если это разрешает список
управления доступом или политика [бакета](../reference/glossary.md#bucket).

## Смена и отзыв ключей (для администратора) {: #storage_credentials_revoke }

!!! warning "Ключ из начального списка отзывается в двух местах"
    Удаление ключа из списка `s3r_api.credentials` ключ не отзывает: строка в
    таблице `s3r_credential` остаётся. И наоборот, ключ, отозванный через API
    управления, но оставшийся в списке, снова добавляется в таблицу при
    следующем запуске сервиса `s3r_api`. Отзывая ключ из начального списка,
    удалите его и из списка, и через API управления.

| Задача | Действие |
| --- | --- |
| Отозвать ключ | Запрос `DELETE /v2/credentials/{access_key}` или консоль. Для ключа не из тенанта по умолчанию добавьте параметр `tenant_id`: `curl -u ivanov -X DELETE 'https://console.example.net/s3gateway/api/v2/credentials/AKIAEXAMPLE000000001?tenant_id=1'` |
| Заменить секретный ключ | Запрос `PUT /v2/credentials/{access_key}` выдаёт ключу новый секретный ключ; прежний секретный ключ после этого не действует |
| Отозвать все ключи пользователя в тенанте | Запрос `DELETE /v2/users?tenant_id=<id>` удаляет ключи пользователя в тенанте и назначенные ему квоты |
| Временно отключить все ключи пользователя в тенанте | Запрос `PUT /v2/users?tenant_id=<id>` с полем `"state": false` отключает все его ключи в тенанте; значение `true` включает их снова |
| Отозвать ключи пользователя во всех тенантах | Удалите пользователя командой SQL `DROP USER`: ключ, выданный несуществующему пользователю, не действует |

Блокировка входа по SQL ключи не отзывает. Команда `ALTER USER ... WITH NOLOGIN` и смена пароля
запрещают пользователю подключаться к СУБД, но его ключи доступа S3 продолжают действовать, и он
остаётся владельцем своих бакетов.

Смена ключа без перерыва в обслуживании выполняется в три шага:

1. Выдайте пользователю второй ключ.
2. Переведите приложение на новый ключ.
3. Отзовите старый ключ.

Когда изменение начинает действовать, зависит от способа:

- Запрос API управления возвращает ответ после того, как изменение ключа начало
  действовать на инстансе, принявшем запрос.
- Изменение, записанное в таблицу `s3r_credential` или `_pico_user` средствами
  SQL, каждый инстанс применяет сразу после фиксации записи у себя, обычно за
  миллисекунды. Поэтому запрос S3, отправленный сразу после такой записи, ещё
  может получить прежний ответ.

## Пароль для входа по SQL (для администратора) {: #sql_client_password }

Пользователь, созданный через консоль или API управления, получает случайный
пароль, который никому не сообщается, потому что ключ доступа S3 не даёт права
входа в СУБД. Подключиться таким пользователем через `psql` можно только после
того, как пароль задан явно.

!!! warning "Пароль открывает все привилегии пользователя Picodata"
    Пароль открывает вход от имени пользователя Picodata со всеми его ролями и
    привилегиями SQL. При этом ключ доступа администратор тенанта может выдать
    пользователю с любым именем, в том числе уже существующему: ключ в тенанте
    не означает, что пользователь принадлежит этому тенанту. Поэтому задать
    пароль может только `s3r_superuser`; администратор тенанта получает
    ответ 403.

Пароль задаётся для отдельного пользователя кнопкой «SQL password» в списке
пользователей консоли или запросом к API управления:

```http
PUT /v2/users/password?tenant_id=0
{"username": "alice", "password": "..."}
```

Пароль сохраняется методом `scram-sha256`. Только этот метод принимают
одновременно `psql`, консоль и протокол iproto:

- метод `chap-sha1` принадлежит Tarantool, и протокол PostgreSQL его отклоняет,
  намеренно не уточняя причину, чтобы по ответу нельзя было подбирать имена
  пользователей;
- метод `md5` слабее.

Пароль задаётся только пользователю S3R, то есть пользователю, которому роль
`s3r_user` выдана напрямую, а не через другую роль. Эту роль S3R выдаёт каждому
пользователю, которого создаёт сам, а любому другому пользователю её выдаёт
администратор средствами SQL:

```sql
GRANT "s3r_user" TO "ivanov";
```

Ключ доступа роли не даёт: если ключ выдаётся уже существующему пользователю,
роль ему не выдаётся. Для пользователя без роли и для встроенных пользователей
Picodata `admin`, `guest` и `pico_service` запрос отклоняется ответом 403 с
кодом `UserNotS3r`. Пароль такого пользователя задаёт администратор средствами
SQL командой `ALTER USER ... WITH PASSWORD`. Отозвать роль, выданную `admin` или
`pico_service`, Picodata не позволяет.

Если запрос на создание пользователя завершился ошибкой, пользователь мог быть
создан без роли `s3r_user`. Повторный запрос `POST /v2/users` с тем же именем
отвечает кодом `NameInUse`, а выдача ключа такому пользователю роль ему не
выдаёт; роль выдаёт администратор средствами SQL.

!!! note "Внешний провайдер идентификации"
    Пароль задаётся только там, где пароли проверяет сам кластер
    (`auth_type: "picodata"`). Если настроен внешний [провайдер идентификации](../reference/glossary.md#identity_provider),
    пароли принадлежат ему: запрос отклоняется с кодом `ProviderOwnsPasswords`,
    а консоль не показывает кнопку.

Смена пароля записывается в журнал аудита Picodata событием `change_password`.
Инициатором в этом событии указан служебный пользователь плагина, поэтому для
полной картины событие сопоставляется с журналом обращений к API управления.

Пароль пользователя, созданного средствами SQL, меняется штатной командой
Picodata:

```sql
ALTER USER "alice" WITH PASSWORD '...';
```
