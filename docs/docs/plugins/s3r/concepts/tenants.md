# Тенанты

Страница объясняет, как один кластер S3R обслуживает несколько независимых
потребителей, [тенантов](../reference/glossary.md#tenant): как разделены их
данные, как запрос относится к тенанту и что настраивается для тенанта и его
[бакетов](../reference/glossary.md#bucket): [дедупликация](../reference/glossary.md#deduplication) и сжатие. Она нужна администратору, который заводит
тенантов и выдаёт им адреса и ключи доступа; сами действия описаны на странице
[Управление тенантами](../admin/tenants.md).

!!! abstract "Коротко"
    - Тенант представляет собой отдельное [пространство имён](../reference/glossary.md#namespace)
      со своими таблицами. Оборудование у тенантов общее.
    - Тенанта запроса определяют заголовок `Host` и ключ доступа. Если они указывают на разных тенантов, запрос отклоняется с ответом `403`.
    - Дедупликация и сжатие по умолчанию выключены и действуют только на
      записи, выполненные после включения.

## Как разделены данные тенантов {: #tenants_isolation }

Один кластер обслуживает несколько тенантов, и каждый тенант представляет
собой отдельное пространство имён.

| Что хранится | Где | Как отделено |
| --- | --- | --- |
| Объекты, директории, составные загрузки и служебные очереди тенанта | Собственные таблицы тенанта: `s3r_t<N>_object`, `s3r_t<N>_dir`, `s3r_t<N>_mpu` и другие, где `N` означает номер тенанта | Запрос не может обратиться к объектам другого тенанта, потому что не может назвать его таблицу |
| Бакеты | Глобальная таблица `s3r_bucket` | Идентификатор тенанта входит в ключ строки бакета |
| Ключи доступа | Глобальная таблица `s3r_credential` | Идентификатор тенанта указан в строке ключа доступа |

Тенант с номером 0 и именем `default` служит тенантом по умолчанию. Если в
кластере не создано других тенантов, кластер целиком принадлежит ему и всё
описанное в остальных разделах руководства относится к нему.

## Определение тенанта запроса {: #tenant_resolution }

Запрос может указывать тенанта двумя способами, и решение принимается по
обоим:

- заголовок `Host` с FQDN тенанта из `s3r_tenant.fqdn` указывает тенанта ещё до
  разбора запроса;
- ключ доступа указывает тенанта через столбец `s3r_credential.tenant_id`.

Если запрос указывает тенанта обоими способами, они должны совпадать:

- если тенанты совпадают, запрос относится к этому тенанту;
- если тенанты разные, запрос отклоняется с ответом `403`;
- запрос без обоих признаков относится к тенанту 0.

Ключ одного тенанта, пришедший на FQDN другого, отклоняется, а не разрешается
в пользу одного из них: молчаливый выбор открыл бы путь к чтению данных
другого тенанта.

## Адресация тенанта {: #tenant_addressing }

Тенант с заданным `domain` отвечает по своему FQDN в обеих формах адресации:

```text
Формат пути: FQDN тенанта, бакет и ключ указаны в пути
https://acme.s3.example.net/documents/report.pdf

Виртуально-хостовая адресация: бакет указан меткой перед FQDN тенанта
https://documents.acme.s3.example.net/report.pdf
```

Точкой входа по умолчанию служит обращение по IP-адресу или имени [узла](../reference/glossary.md#node) без FQDN
тенанта. Такой запрос обрабатывается как путь, а тенант определяется по ключу
доступа; по умолчанию это тенант 0.

Хост, похожий на схему адресов тенантов, но не принадлежащий ни одному из них,
отклоняется, а не обслуживается тенантом по умолчанию. Иначе запросы к
несуществующему тенанту попадали бы к данным тенанта по умолчанию.

Смежные темы:

- собственный сертификат тенанта и обязательный клиентский сертификат описаны в
  разделе [Сертификат тенанта и выбор по SNI](../admin/tls.md#tenant_cert_and_sni);
- роли `s3r_superuser` и `s3r_tenant_admin_<id>` описаны в разделе
  [Ролевая модель тенантов](#tenants_role_model).

## Дедупликация {: #deduplication }

При дедупликации объекты с одинаковым содержимым хранят одну общую копию.
Совпадения находит индекс дедупликации по сумме SHA-256 содержимого.

По умолчанию дедупликация выключена. Её включают для тенанта или для бакета:

- SQL-запросом:

    ```sql
    UPDATE s3r_bucket SET dedup = true WHERE tenant_id = 0 AND name = 'archive';
    UPDATE s3r_tenant SET dedup = true WHERE tenant_id = 0;
    ```

- для бакета в консоли, переключателем рядом с переключателем сжатия;
- для бакета в [API управления](../reference/glossary.md#management_api): `PUT /v2/buckets/{bucket}/deduplication` с
  телом `{"dedup": true}`.

Пока дедупликация выключена, запись не оставляет никаких следов: ни записи в
очереди, ни отпечатка содержимого в индексе дедупликации.

!!! warning "Включение действует только на новые записи"
    Дедуплицируются записи, начатые после включения. Ранее записанные объекты
    в индекс не попадают.

Причина в сумме SHA-256: при выключенной дедупликации запись вычисляет её,
только если клиент её запросил (см.
[Контрольные суммы S3](../usage/objects.md#s3_checksums)). Отсюда следует:

- запись, которая началась до включения и не запрашивала SHA-256, не
  дедуплицируется, даже если завершилась после него;
- то же относится к частям
  [составной загрузки](../reference/glossary.md#multipart_upload), переданным
  до включения;
- копирование объекта в тот же ключ, например для замены метаданных, не
  переписывает содержимое и не добавляет объект в индекс.

Выключение не разделяет уже объединённое содержимое: записанное при включённом
переключателе остаётся общим, но новые объекты к нему не добавляются.

## Сжатие {: #compression }

По умолчанию сжатие выключено. Объект сжимается, если включён хотя бы один из
трёх переключателей:

| Переключатель | Как задаётся |
| --- | --- |
| Бакета | в консоли на странице настроек бакета; запросом API управления `PUT /v2/buckets/{bucket}/compression` с телом `{"compress": true}`; средствами SQL |
| Тенанта | только средствами SQL |
| [Яруса](../reference/glossary.md#storage_tier) | полем `compress: true` в записи яруса параметра `s3r_storage.tiers` (см. [Классы хранения S3 и ярусы](storage_classes.md#storage_classes_and_tiers)) |

Переключатель яруса учитывается только при записи объекта операцией
`PutObject`: части составной загрузки и копии объектов он не сжимает.

```sql
UPDATE s3r_bucket SET compress = true WHERE tenant_id = 0 AND name = 'archive';
UPDATE s3r_tenant SET compress = true, compress_level = 6 WHERE tenant_id = 0;
```

!!! warning "Включение действует только на новые записи"
    Переключатели действуют на записи, выполненные после их включения. Уже
    записанные объекты не перезаписываются.

### Алгоритм и уровень {: #compression_level }

Применяется алгоритм zstd. Уровень сжатия задаётся для тенанта столбцом
`s3r_tenant.compress_level` и действует для любого задействованного
переключателя. Значение `NULL` означает уровень 3. Значение вне допустимого
для zstd диапазона заменяется ближайшей границей диапазона.

### Что и как сжимается {: #compression_scope }

- Содержимое объекта сжимается участками по 1 МиБ до разбиения на
  [полосы](../reference/glossary.md#stripe). Поэтому сжимаются объекты как с
  [избыточным кодированием](../reference/glossary.md#erasure_coding), так и с репликацией.
- Участок, который после сжатия занимает больше 0,9 исходного размера,
  хранится без сжатия.
- Чтение диапазона распаковывает только затронутые участки, но каждый из них
  целиком: запрос даже одного байта распаковывает до 1 МиБ.
- Объекты со [способом хранения](../reference/glossary.md#encoding) `inline`
  не сжимаются.

### Перенос между ярусами и дедупликация {: #compression_transition }

Перенос объекта в другой ярус правилом жизненного цикла сохраняет его форму:
несжатый объект не сжимается и в ярусе с включённым сжатием. Если перенос
выполняется на том же [инстансе](../reference/glossary.md#instance), сжатый объект сжимается заново с уровнем 3, а
не с уровнем тенанта.

Общее содержимое при дедупликации хранится в той форме, в которой была
записана его первая копия.

### Нагрузка и наблюдение {: #compression_monitoring }

Сжатие и распаковку выполняют рабочие потоки плагина
([среды выполнения Tokio](../reference/glossary.md#tokio)), которые
обслуживают запрос (см.
[Процессорные ядра](../install/requirements.md#cpu_cores)).

- Степень сжатия показывает метрика `s3r_compression_bytes_total` как
  отношение значения с меткой `direction="stored"` к значению с меткой
  `direction="logical"`.
- Ответ `HeadObject` на запрос всего объекта содержит заголовки `x-s3r-codec`
  с алгоритмом и `x-s3r-stored-bytes` с хранимым объёмом.
- Квоты учитывают объём объекта до сжатия.

## Ролевая модель тенантов {: #tenants_role_model }

Миграции создают четыре роли. [Субъект доступа](../reference/glossary.md#principal) S3 соответствует пользователю
SQL Picodata, поэтому ролевая модель использует роли Picodata, а не отдельную таблицу плагина.

| Роль | Что даёт |
| --- | --- |
| [`s3r_superuser`](#s3r_superuser) | полные полномочия над плагином в кластере и доступ SQL ко всем таблицам плагина |
| [`s3r_observer`](#s3r_observer) | только чтение состояния кластера |
| [`s3r_tenant_admin_<идентификатор>`](#s3r_tenant_admin) | управление пользователями, ключами и бакетами одного тенанта |
| [`s3r_user`](#s3r_user) | полномочий не даёт; отмечает пользователя S3R, которому можно задать пароль для входа по SQL |

Роль выдаётся обычным оператором SQL. Оба имени берутся в кавычки, иначе они приводятся к нижнему
регистру:

```sql
GRANT "s3r_superuser" TO "ivanov";
```

Роли не наследуют друг друга: если пользователю нужны полномочия двух видов, ему выдают две роли.

### `s3r_superuser`  {: #s3r_superuser }

Полные полномочия над плагином в кластере:

- ярусы и уровни избыточности;
- режим обслуживания;
- тенанты и их сертификаты;
- доступ SQL ко всем таблицам плагина.

Это единственная роль с правом чтения `s3r_tenant`, поскольку она же записывает в таблицу
сертификаты. Её обладатель создаёт тенантов и их сертификаты, а также получает список тенантов и
сведения об их ёмкости с помощью SQL.

### `s3r_observer` {: #s3r_observer }

Только чтение: ёмкость, состояние кластера и дисков, [группы размещения](../reference/glossary.md#placement_group), восстановление, проверка
целостности. Роль предназначена тому, кто наблюдает за кластером и ничего в нём не меняет; без неё
такому человеку пришлось бы выдать полномочия администратора.

Секреты наблюдателю недоступны: `s3r_credential` хранит секретные ключи, `s3r_tenant` хранит
закрытые ключи TLS, и обе таблицы выданы только `s3r_superuser`.

### `s3r_user` {: #s3r_user }

Роль `s3r_user` полномочий не даёт. Она отмечает пользователя S3R: такому
пользователю `s3r_superuser` задаёт пароль для входа по SQL (см.
[Пароль для входа по SQL](../usage/credentials.md#sql_client_password)).

### `s3r_tenant_admin_<идентификатор>` {: #s3r_tenant_admin }

Управление пользователями, ключами и бакетами одного тенанта, идентификатор которого указан в
имени роли. Такая роль создаётся для каждого тенанта.

| Свойство | Объяснение |
| --- | --- |
| Отдельная роль на тенанта | полномочие нельзя выразить табличным разрешением: `s3r_credential` является глобальной таблицей, а разрешение SQL нельзя сузить до строк одного тенанта. Область действия задаёт выдача роли |
| В имени идентификатор, а не имя тенанта | идентификатор не переиспользуется после удаления тенанта, поэтому выданная роль никогда не станет означать другого тенанта, и переименование тенанта её не ломает |
| Чужой тенант отвечает «не найдено», а не «запрещено» | ответ «запрещено» подтвердил бы, что такой тенант существует |
| Пароль для входа по SQL | администратор тенанта его не задаёт: это может только `s3r_superuser`, см. [Пароль для входа по SQL](../usage/credentials.md#sql_client_password) |
| `CREATE USER` | полномочие уровня кластера, которое нельзя сузить до тенанта. Поэтому администратор тенанта не получает его напрямую: пользователя Picodata создаёт плагин |

Операции предоставляет API управления. Он принимает токен доступа OIDC и тенанта в самом запросе,
поэтому именно выданная роль определяет, к какому тенанту обращение допустимо.

#### Запросы администратора тенанта {: #tenant_admin_requests }

| Запрос | Действие |
| --- | --- |
| `GET /v2/users?tenant_id=<id>` | перечислить пользователей тенанта и их ключи (без секретов) |
| `POST /v2/users` | зарегистрировать пользователя |
| `PUT /v2/users?tenant_id=<id>` | заблокировать или разблокировать пользователей (`state`) |
| `DELETE /v2/users?tenant_id=<id>` | удалить ключи пользователей в тенанте и назначенные им квоты; пользователь Picodata остаётся |
| `POST /v2/credentials?tenant_id=<id>` | выдать ключ доступа |
| `PUT /v2/credentials/<ключ>?tenant_id=<id>` | заменить секрет, сохранив ключ |
| `DELETE /v2/credentials/<ключ>?tenant_id=<id>` | удалить ключ |
| `PUT /v2/buckets` с именем бакета и именем нового владельца | передать бакет другому владельцу; в консоли это действие «передать» |

Правила:

- **Секретный ключ.** Ответ на создание или замену ключа содержит
  [секретный ключ доступа](../reference/glossary.md#secret_access_key) только один раз. Больше его не
  возвращает ни один запрос.
- **Блокировка** действует на пользователя, а не на отдельный ключ: все ключи пользователя
  переходят в состояние «отключён» вместе. Операция обратима: ключи остаются, и разблокировка
  возвращает прежнее состояние.
- **Передача бакета.** Новый владелец должен быть субъектом доступа того же тенанта. Прежний
  владелец не сохраняет никаких прав на бакет. В ответе назван тот, кто потерял владение; больше
  нигде прежний владелец не записан.
