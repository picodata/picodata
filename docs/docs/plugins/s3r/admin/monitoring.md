# Наблюдение за кластером

Страница для инженера эксплуатации: что проверять в первую очередь, как отличить исправный
кластер от неисправного, где смотреть состояние дисков, групп размещения, свободного места и
репликации между площадками. В конце приведён справочник метрик и сообщений журнала.

Как устранять найденное, описано на страницах [Отказы и восстановление](failures.md),
[Действия с дисками](disks.md), [Контроль целостности](integrity.md) и
[Решение типовых проблем](troubleshooting.md).

## Что проверять в первую очередь {: #first_look }

У кластера четыре источника сведений о состоянии. Они отвечают на разные вопросы и доступны
по-разному.

| Источник | Что показывает | Где и кому доступен |
| --- | --- | --- |
| `GET /-/health` | [инстанс](../reference/glossary.md#instance) принимает соединения на порту S3. Диски, группы размещения и фоновые процессы не проверяются | порт эндпоинта S3, без подписи и без аутентификации |
| `GET /-/ready` | инстанс готов обслуживать запросы: кластер прошёл [начальное формирование](../reference/glossary.md#formation), инстанс загрузил свои [группы размещения](../reference/glossary.md#placement_group) | там же, без подписи и без аутентификации |
| `GET /v2/health`, `GET /v2/repair` | состояние всего кластера: сводка по подсистемам и четыре области контроля целостности (см. [«Состояние по областям»](integrity.md#repair_areas)) | [API управления](../reference/glossary.md#management_api) на HTTP-порту Picodata; требуется [аутентификация](../reference/management_api.md#api_auth) с ролью `s3r_superuser` или `s3r_observer` |
| `/metrics` | числовые ряды каждого инстанса (см. [«Метрики»](#metrics)) | HTTP-порт Picodata (`instance.http_listen`) |

Состояние отдельных таблиц читается запросами SQL (см. [«Состояние кластера»](#cluster_state)),
сообщения инстанса читаются в его журнале (см. [«Журнал»](#logging)).

!!! warning "«Процесс работает» не значит «инстанс готов»"
    Ответ `/-/health` подтверждает только работу [слушателя](../reference/glossary.md#listener) S3. Готовность показывает `/-/ready`:
    ответ `200` означает, что кластер прошёл начальное формирование, а инстанс загрузил свои
    группы размещения. Балансировщик проверяет именно `/-/ready` (см.
    [«Балансировка нагрузки»](load_balancing.md#load_balancing)). Состояние отдельных дисков на
    ответ `/-/ready` не влияет, поэтому за дисками и группами следят по метрикам и по
    `GET /v2/repair`.

Диагностические эндпоинты `/-/debug/*` и `/-/bench/*` тоже обслуживаются на порту S3 без подписи.
По умолчанию они выключены, а часть из них изменяет данные (см.
[«Диагностические эндпоинты»](../reference/endpoints.md#diagnostic_endpoints)).

### Признаки исправного кластера {: #healthy_cluster }

| Что смотреть | Исправный кластер | На что указывает отклонение |
| --- | --- | --- |
| `GET /-/ready` на каждом инстансе | ответ `200` | начальное формирование не завершено или инстанс не загрузил свои группы |
| `s3r_resync_outstanding` с меткой `kind` | 0 | [ресинхронизации](../reference/glossary.md#resync) ещё есть что исправить. Значение `needs_resync` равно числу групп, в которых [участник](../reference/glossary.md#member) хранит меньше, чем записано в [каталоге](../reference/glossary.md#catalog) (строках объектов в таблицах Picodata): обычно это замена диска, за которой ещё не поспело [перестроение](../reference/glossary.md#rebuild). Пока число не равно нулю, выведенный диск извлекать рано |
| `s3r_ec_reconstructions_total` | не растёт | [полосы](../reference/glossary.md#stripe) при чтении восстанавливаются из сохранившихся [фрагментов](../reference/glossary.md#chunk) |
| `s3r_scrub_inconsistent_total` | не растёт | расхождения данных чётности: ошибка записи или искажение данных |
| `s3r_worker_runs_total` | растёт, пока есть задания | если очередь растёт, а счётчик не меняется, фоновый процесс не выполняет задания |

Эти метрики контролируются в первую очередь. Остальные перечислены в разделе
[«Метрики»](#metrics); там же названы готовые панель Grafana и правила Prometheus.

## Состояние кластера {: #cluster_state }

Диски и группы размещения описаны глобальными таблицами, и их состояние доступно через запросы
SQL.

```sql
-- Диски, их принадлежность, домены отказа и ярусы
SELECT instance_name, path, site, failure_domain, tier, state,
       capacity_bytes, extent_count
  FROM s3r_disk
 ORDER BY instance_name;

-- Состояние кластера, шаг начального формирования, площадки и записанные ярусы
SELECT state, step, state_changed_at, sites, founding_members, tiers FROM s3r_cluster;

-- Регистрация инстансов
SELECT instance_name, replicaset_name, failure_domain, reason, updated_at
  FROM s3r_instance;

-- Группы размещения, их состояние, пределы и геометрия
SELECT pg_id, state, epoch, site, tier, k, m, stripe_bytes, owner, resynced_at_epoch,
       limit_blocks_large, limit_blocks_small, members
  FROM s3r_pg
 ORDER BY pg_id;

-- Раскладка групп: номер в цепочке, позиции плана, выбывающие диски
SELECT pg_id, layout, n, intended, leaving, reform_requested FROM s3r_pg
 ORDER BY pg_id;

-- Занятость дисков по числу экстентов
SELECT d.disk_id, d.extent_count, f.free_extents, d.state
  FROM s3r_disk d JOIN s3r_disk_free f ON f.disk_id = d.disk_id
 ORDER BY d.disk_id;

-- Распределение объектов тенанта 0 по способу хранения
SELECT encoding, count(*) FROM s3r_t0_object
 WHERE part_no = 0 GROUP BY encoding;

-- Распределение объектов тенанта 0 по классам хранения S3
SELECT storage_class, count(*) FROM s3r_t0_object
 WHERE part_no = 0 GROUP BY storage_class;
```

Таблицы объектов свои у каждого [тенанта](../reference/glossary.md#tenant): в примерах
`s3r_t0_object` означает таблицу тенанта 0.

Состояния диска перечислены в разделе
[«Идентификация диска»](../concepts/disks.md#disk_identification).

Группа размещения принимает записи в состоянии `active`, пока у неё есть
[владелец](../reference/glossary.md#owner) и владелец закончил её монтирование (см.
[«Группы размещения»](../concepts/placement_groups.md#placement_groups)).

Столбцы таблицы `s3r_pg`, по которым судят о состоянии группы:

| Столбец | Что означает |
| --- | --- |
| `limit_blocks_large`, `limit_blocks_small` | сколько блоков каждого класса группа выдаёт на каждом участнике |
| `epoch` | [эпоха](../reference/glossary.md#group_epoch) группы; увеличивается при смене состава группы |
| `resynced_at_epoch` | равен `epoch`, когда каждый участник сверен с владельцем и выделил свои [экстенты](../reference/glossary.md#extent), а [отстающие экстенты](../reference/glossary.md#extents_behind) проверены (см. [«Контроль целостности»](../concepts/background.md#integrity_control)). После смены состава значения перестают совпадать. Запись, которой не хватило фрагмента, столбец не меняет |
| `extents_behind` | отстающие экстенты в виде `[номер фрагмента, [[класс, номер экстента], …]]`; `NULL` означает, что таких экстентов нет. Пока столбец не пуст, `resynced_at_epoch` пуст |
| `members` | участники группы по порядку: номер в массиве является номером фрагмента. Каждый элемент содержит диск, инстанс, состояние участника и [номер форматирования](../reference/glossary.md#format_generation) диска |
| `leaving` | прежние диски, которые ещё не освободили экстенты группы |

Состояния участника в столбце `members`:

| Состояние | Что означает |
| --- | --- |
| `active` | обычное состояние |
| `new` | участник ещё не выделил все экстенты группы, например после замены выбывшего диска или после переформатирования диска. Его фрагменты не учитываются в [кворуме записи](../reference/glossary.md#write_quorum) |
| `draining` | участника переносит действие «Восстановить размещение» |

## Занятость и освобождение места {: #free_space }

Место, занятое удалённым объектом, освобождается не сразу и без участия администратора. Раздел
объясняет, когда его ждать и что на это влияет.

Удаление объекта не переписывает фрагменты на дисках. Место освобождается в три шага:

1. **Позиции блоков объекта становятся свободными.** Транзакция, которая исключает строку объекта
   из [пространства имён](../reference/glossary.md#namespace), добавляет в очередь удалённых
   фрагментов `s3r_chunkgc` запись об этом объекте. Процесс `chunkgc` на мастере репликасета
   отправляет записи владельцам групп размещения, и владелец освобождает
   [позиции блоков](../reference/glossary.md#block_position) объекта в своём учёте занятых и
   свободных позиций ([вид группы](../reference/glossary.md#group_view)). Запись остаётся в
   очереди, пока объект не освобождён во всех группах, где он лежит, поэтому её не теряют ни
   перезапуск мастера, ни смена владельца группы.
2. **Свободная позиция блока выдерживается `refill_after_s` секунд** и только потом выдаётся под
   запись: клиент, который уже прочитал строку объекта, может ещё читать его фрагменты.
3. **Экстент, все блоки которого свободны дольше `refill_after_s`, возвращается в свободный
   пул диска**, и группа больше его не использует. Процесс `extentgc` помечает такой экстент
   пустым к сроку, когда заканчивается [карантин](../reference/glossary.md#quarantine) последнего освободившегося в нём блока, а
   процесс `group` освобождает его на участниках.

!!! note "Примечание"
    Копирование на другую площадку читает полосу из очереди, а не в ходе запроса, поэтому задержка
    `refill_after_s` её не защищает.

Свободные позиции блоков считает владелец группы:

```sql
-- Группы и их владельцы: свободные позиции блоков считает владелец
SELECT pg_id, tier, epoch, owner FROM s3r_pg ORDER BY pg_id;
```

### Удаление тенанта {: #free_space_tenant }

Удаление тенанта освобождает место через ту же очередь: процесс `tenant` сначала удаляет строки
объектов тенанта, и каждое удаление ставит запись в `s3r_chunkgc`, а затем удаляет таблицы
тенанта. Сверка для этого не нужна. Поэтому удаление тенанта длится тем дольше, чем больше у него
объектов, а место возвращается по мере удаления строк.

### Очередь удалённых фрагментов {: #free_space_queue }

Удаления не ждут места в очереди. Массовое удаление по запросам клиентов, истечение срока по
правилам жизненного цикла, прерывание загрузок и очистка удалённого
[бакета](../reference/glossary.md#bucket) идут со скоростью, с которой
[мастер](../reference/glossary.md#master) принимает транзакции, а позиции блоков освобождаются по
мере того, как владельцы обрабатывают очередь.

- Владелец, который монтирует группу или уже не владеет ею, запись не принимает, и процесс
  `chunkgc` отправляет её снова: сначала через секунду, затем с паузой в половину возраста записи,
  но не больше минуты.
- Число записей в очереди показывает датчик `s3r_chunkgc_queued`, а счётчик
  `s3r_chunkgc_refused_total` растёт при каждой отправке записи, которую владелец группы не
  освободил.

Мастер отправляет запись, как только транзакция удаления записана в его журнал, и не ждёт реплик.
Если мастер аварийно остановится, не успев передать удаление репликам, новый мастер снова видит
строку объекта, а её позиции блоков уже могут занять другие объекты. Такой объект читается с
ошибкой, проверка целостности сообщает о повреждении, и объект можно удалить повторно. Так же при
аварийной смене мастера может перестать читаться объект, который в последние мгновения перед ней
был перенесён на другой уровень хранения или заменён ссылкой на общую копию при
[дедупликации](../reference/glossary.md#deduplication).

### Сверка позиций {: #free_space_reconcile }

Сверка позиций (процесс `reconcile`) освобождает место, о котором не знает ни один другой процесс.
Это позиции записи, исход фиксации которой неизвестен, и позиции строк, которые потерялись при
аварийной смене мастера асинхронного яруса.

- Владелец каждой группы выполняет сверку по запросу проверки (`POST /v2/repair`) и раз в шесть
  часов, поэтому такое место занято не дольше шести часов, а объекты при этом не теряются.
- Сверка читает каталог постранично, по одному бакету vshard за раз. Мастер отводит этим страницам
  около 5 % времени потока TX. Если другие чтения не занимают поток TX сверх этой доли, при
  миллиарде объектов сверка длится от 17 до 50 минут.
- Между страницами сверка ждёт не дольше 10 секунд, даже пока на том же мастере идёт монтирование
  группы. Страница, которую не удалось прочитать, читается снова через секунду, всего не больше
  трёх попыток.

Завершив сверку, владелец записывает в журнал строку уровня INFO. Она называет число прочитанных
бакетов vshard, число освобождённых, добавленных и непроверенных объектов и репликасеты, бакеты
которых сверка не прочитала:

```
reconcile pass over 1 group(s): 150 of 300 vshard bucket(s) read; freed 0, added 0, newer 0, replaced 0, unchecked 1; buckets not covered: default_1 tries used up (150)
```

| Причина в строке журнала | Что она означает |
| --- | --- |
| `did not answer` | репликасет недоступен, и остальные его бакеты в этой сверке не читались |
| `tries used up` | страницы бакета не прочитались за три попытки |

Позиции блоков объектов в таких бакетах остаются занятыми до следующей сверки. Первые 100 объектов,
которые сверка освободила в бакете vshard, называют строки журнала уровня INFO: идентификатор
объекта и номер бакета vshard его строки. Остальные учитывает строка с общим числом освобождённых
в бакете объектов.

## Наблюдение за репликацией между площадками {: #monitor_placements_replication }

[Репликация между площадками](../reference/glossary.md#site_replication) отдельной настройки не
требует: [площадка](../reference/glossary.md#site) задаётся компонентом `dc` [домена отказа](../reference/glossary.md#failure_domain)
инстанса. Её устройство описано на страницах
[Избыточность и домены отказа](../concepts/redundancy.md#multiple_sites) и
[Репликация между площадками](../concepts/site_replication.md).

```sql
-- Объекты тенанта 0, которые есть не на всех площадках
SELECT count(*) FROM s3r_t0_siterepl;

-- Карта размещения объекта по площадкам
SELECT name, placements FROM s3r_t0_object
 WHERE name = 'report.pdf' AND part_no = 0;
```

Пустая таблица `s3r_t<N>_siterepl` означает, что у тенанта нет ожидающих копий на другие площадки.

## Журнал {: #logging }

Плагин записывает сообщения в журнал инстанса Picodata и наследует уровень подробности от
настройки Picodata. Уровни соответствуют уровням самой Picodata:

- при уровне `verbose` выводятся отладочные сообщения плагина, например о решениях фоновых
  процессов и о каждом перестроенном фрагменте;
- при уровне `debug` ещё и сообщения о каждом соединении и запросе.

Сообщения, которые подтверждают штатный запуск:

| Сообщение | Значение |
| --- | --- |
| `s3r_storage started, configured with N disk(s), listening on ..., advertised as ...` | сервис принял конфигурацию; число дисков указано по конфигурации, до их монтирования |
| `disk <uuid> at <path> registered: tier ..., domain ...` | при первом запуске диск зарегистрирован в `s3r_disk`; указаны [ярус](../reference/glossary.md#storage_tier) и полный домен отказа |
| `disk <uuid> at <path> mounted: N bytes, M extents of E bytes, tier ...` | диск смонтирован для данных |
| `chunk endpoint serving on ... over mutual TLS` | [узел](../reference/glossary.md#node) принимает запросы обмена фрагментами; в конце указан режим шифрования |
| `the cluster moved to step forming`, `the cluster is active` | кластер перешёл на следующий шаг начального формирования или завершил его |

Сообщения, которые требуют внимания:

| Сообщение | Значение |
| --- | --- |
| `the cluster is new (registering) and waits for: ...` (или `new (forming)`) | начальное формирование ждёт; причины перечислены через точку с запятой (см. [«Если установка не завершается»](../install/troubleshooting.md#install_troubleshooting)) |
| `this instance's disk list registers nothing: ...` | список дисков инстанса отклонён при первом запуске |
| `this instance's disk list [...] differs from its registered disks [...]` | локальный список дисков после первой регистрации отличается от зарегистрированных дисков; инстанс работает с зарегистрированными дисками |
| `disk <id> is blank: ...`, `disk <id> is foreign: ...`, `disk <id> is corrupt: ...` | по пути диска нет его собственного накопителя; диск в названном состоянии |
| `the stored s3r_storage configuration breaks a rule: ...` | сохранённая конфигурация нарушает правило проверки (см. [«Сервис s3r_storage»](../reference/configuration.md#s3r_storage)) |
| `placement group N of <владелец> is asymmetric from birth: ...` | группа создана с заменой недоступной позиции плана (см. [«Позиции и порядок групп»](../concepts/placement_groups.md#group_positions)) |
| `pg N: the re-form ends: ...` | действие «Восстановить размещение» для группы завершено, причина указана |
| `tier <ярус>: new group pg N is given up before it became active, K in a row: ...` | новая группа отменена, указаны участник, его диск и причина; следующая группа яруса запрашивается после паузы (см. [Отмена новой группы](../concepts/placement_groups.md#group_given_up)) |
| `s3r_storage started with no disks and no listener; this instance stores nothing` | на инстансе нет дисков и слушателя `s3r_storage` |

## Метрики {: #metrics }

Плагин публикует метрики в формате Prometheus через эндпоинт Picodata `/metrics`. Каждый инстанс
публикует собственные ряды, а суммирование по кластеру выполняет Prometheus. Метки метрик имеют
ограниченное число значений, поэтому имя пользователя и имя бакета меткой не служат.

Метрики, которые контролируются в первую очередь, перечислены в разделе
[«Признаки исправного кластера»](#healthy_cluster).

В репозитории плагина поставляются:

- панель Grafana `deploy/grafana/s3r-dashboard.json` из четырёх рядов: обслуживание запросов,
  исправность кластера, нагрузка и свободное место;
- правила Prometheus `deploy/prometheus/s3r-alerts.yml`. Правила задают выражения, а условия
  оповещения определяет служба эксплуатации.

### Правила оповещения {: #alert_rules }

Файл `deploy/prometheus/s3r-alerts.yml` содержит восемь правил. Выражения и сроки приведены так,
как они записаны в файле.

| Правило | Выражение | Срок | Важность | Что означает и что делать |
| --- | --- | --- | --- | --- |
| `S3rPlacementGroupLost` | `s3r_pg_lost > 0` | 1 мин | `critical` | в группе осталось меньше участников, чем нужно для чтения: её объекты не читаются. Это не перестроение. Проверьте, какие диски признаны вышедшими из строя и можно ли вернуть их до замены |
| `S3rPlacementGroupDegraded` | `max(s3r_pg_degraded) > 0` | 15 мин | `warning` | избыточность неполная: участник группы утрачен, находится на вышедшем из строя или переформатированном диске либо поставлен на замену и ещё не проверен ресинхронизацией. Объекты читаются, но с меньшим запасом. Группы перечисляет `GET /v2/repair/data`; если участника некуда поставить, добавьте диск на этой площадке и в этом ярусе |
| `S3rStripeDamaged` | `s3r_damage_stripes > 0` | 5 мин | `critical` | в [реестре повреждённых полос](integrity.md#damage_registry) есть записи. Список выдаёт ответ `GET /v2/repair/data` |
| `S3rPlacementGroupAsymmetric` | `max by (site, tier) (s3r_pg_asymmetric) > 0` | 1 ч | `info` | группы стоят не на своих позициях. Они остаются так, пока администратор не выполнит [восстановление размещения](disks.md#reform) |
| `S3rDiskNearlyFull` | `sum by (disk) (s3r_extents) > 0 and sum by (disk) (s3r_extents{state="free"}) / sum by (disk) (s3r_extents) < 0.15` | 10 мин | `warning` | на диске свободно меньше 15 % экстентов. Добавьте ёмкость в ярус |
| `S3rDiskFull` | `sum by (disk) (s3r_extents) > 0 and sum by (disk) (s3r_extents{state="free"}) == 0` | 5 мин | `critical` | на диске не осталось свободных экстентов: он не принимает запись для группы, которой нужен новый экстент. Добавьте ёмкость в ярус |
| `S3rDiskBitrot` | `increase(s3r_disk_crc_failures_total[1h]) > 0` | — | `warning` | диск отдал фрагменты, не прошедшие проверку контрольной суммы. Каждый такой фрагмент перестраивается по другим участникам группы. Если счётчик продолжает расти, проверьте счётчики ошибок накопителя и выведите диск |
| `S3rScrubBehind` | `(s3r_scrub_groups > 0 and (time() - s3r_scrub_oldest_pass_timestamp_seconds) > s3r_scrub_period_seconds) unless on(instance_name) s3r_repair_paused == 1` | 15 мин | `warning` | проверка целостности данных яруса не укладывается в свой период `scrub_period_s`. Правило не срабатывает, пока фоновый контроль целостности приостановлен. Проверьте, что процесс `scrub` работает и у групп есть владельцы |

Правило `S3rPlacementGroupDegraded` намеренно отделено от `S3rPlacementGroupLost`: группа без
одного участника встречается при обычной работе кластера, а группа, в которой участников меньше,
чем нужно для чтения, означает потерю данных.

Ниже перечислены семейства метрик по сервисам. Тип указан словом: счётчик накапливает значение,
датчик отражает текущее значение, гистограмма показывает распределение.

| `s3r_pg_lost` | — | датчик числа групп размещения, в которых сохранившихся участников меньше, чем требуется для чтения. Значение относится ко всему кластеру |

Если значение больше нуля дольше 15 минут, срабатывает правило `S3rPlacementGroupDegraded`. Значение относится ко всему кластеру |

| `s3r_lifecycle_total` | `kind` | что сделали проходы правил жизненного цикла: `removed` (удалена версия или одиночный маркер удаления вместе с данными), `expired` (над текущей версией записан маркер удаления, данные остались в неактуальной версии), `aborted` (прервана незавершённая загрузка), `transitioned` (версия поставлена в очередь на перевод в другой класс хранения, перевод выполняет процесс `transition`), `skipped` (виртуальный бакет vshard пропущен после трёх неудачных попыток, его прочтёт следующий проход; остаток таблицы, пропущенный, когда страница не нашла свой виртуальный бакет, считается одним пропуском) |

| `s3r_transition_bytes_total` | — | объём данных, переписанных при переходах между классами |
| `s3r_chunkgc_refused_total` | — | счётчик пар из объекта и группы в очереди удалённых фрагментов, которые владелец группы не освободил при отправке: он монтирует группу, у группы нет владельца в представлении кластера или владелец не ответил. Такая запись отправляется повторно |
