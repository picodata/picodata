# Управление тенантами

Страница нужна администратору кластера, который создаёт и удаляет
[тенантов](../reference/glossary.md#tenant): изолированные пространства имён со своими [бакетами](../reference/glossary.md#bucket),
пользователями и ключами доступа. Здесь же описаны состояния тенанта, два служебных
тенанта, которые удалить нельзя, и правила CORS, которые получают новые бакеты тенанта. Столбцы
таблицы `s3r_tenant` перечислены в [справочнике таблиц](../reference/tables.md#tenant_columns),
устройство тенантов объясняет страница [Тенанты](../concepts/tenants.md).

## Состояния тенанта {: #tenant_states }

Запросы обслуживаются только для тенанта в состоянии `active`.

| Состояние | Что означает |
|---|---|
| `new` | тенант создаётся и ещё не готов |
| `active` | тенант работает |
| `draining` | тенант удаляется; аутентификацию он больше не проходит |
| `dropped` | тенант удалён; от него осталась только строка в `s3r_tenant` |

Создание бакета в тенанте, который не находится в состоянии `active`, отклоняется.

## Создание тенанта {: #tenant_create }

**Что должно быть выполнено заранее.** У пользователя есть роль `s3r_superuser` (см.
[Ролевая модель тенантов](../concepts/tenants.md#tenants_role_model)).

!!! warning "Не добавляйте строки в `s3r_tenant` командой `INSERT`"
    Такой запрос игнорирует проверку FQDN и обходит счётчик идентификаторов: следующий запрос к
    API получит уже занятый идентификатор и завершится ошибкой.

**Шаги.**

1. Отправьте запрос к [API управления](../reference/glossary.md#management_api) либо создайте тенанта на экране тенантов
   [консоли](console.md#console_tenants):

    ```shell
    curl -u ivanov -X POST https://console.example.net/s3gateway/api/v2/tenants \
      -H 'content-type: application/json' \
      -d '{"name": "acme", "fqdn": "acme.s3.example.net"}'
    ```

2. Действуйте по коду ответа:

    | Ответ | Что произошло | Что делать |
    |---|---|---|
    | `201` с идентификатором тенанта | тенант создан и уже активен | ничего |
    | `202` | тенант не стал активным за две минуты. Это успешный ответ: создание продолжается само | повторять запрос не нужно; следите за состоянием запросом `GET /v3/tenants/{id}` |
    | `503` | запись строки тенанта через [Raft](../../../overview/glossary.md#raft) не подтверждена за две минуты | проверьте `GET /v3/tenants`: запись может завершиться позже, и тогда тенант появится в списке |
    | `409` с кодом `NameInUse` | тенант с таким именем уже есть, в том числе созданный запросом, который получил `503` | — |

**Что происходит.** Запрос записывает строку в глобальную таблицу `s3r_tenant` в состоянии `new`.
Эта запись запускает фоновый процесс `tenant`, который создаёт таблицы нового тенанта и переводит
его в состояние `active`.

Две минуты отсчитываются от поступления запроса и ограничивают и запись строки тенанта через Raft,
и ожидание состояния `active`.

Идентификатор выдаёт счётчик `tenant_id` таблицы `s3r_seq` той же записью Raft, которая добавляет
строку тенанта, поэтому идентификатор никогда не выдаётся повторно.

### Ответ `202`: тенант ещё создаётся {: #tenant_create_pending }

- Поле `result` содержит тенанта в том виде, в каком его показывает `GET /v3/tenants/{id}`, с
  состоянием `pending`. В таблице `s3r_tenant` тенант при этом остаётся в состоянии `new`.
- Поле `message` рядом с `result` содержит идентификатор тенанта и запрос `GET /v3/tenants/{id}`.
  Этот запрос показывает состояние `pending`, пока тенант не станет активным.
- Если создание не завершается, процесс `tenant` при каждой попытке записывает причину в журнал
  [инстанса](../reference/glossary.md#instance) строкой `tenant <id> (new): ...`.

## Удаление тенанта {: #tenant_delete }

!!! danger "Удаление уничтожает данные тенанта и сразу отзывает доступ"
    Вместе с тенантом удаляются его бакеты и таблицы с объектами. Блокировки объектов удаление не
    останавливают. Тенант в состоянии `draining` больше не проходит аутентификацию: перевод в
    удаление отзывает доступ той же записью Raft.

Запроса на удаление в API управления нет, поэтому удаление выполняется командой SQL.

**Шаги.**

1. Переведите тенанта в состояние `draining`:

    ```sql
    UPDATE s3r_tenant SET state = 'draining' WHERE tenant_id = 1;
    ```

2. Дождитесь, пока строка тенанта в `s3r_tenant` перейдёт в состояние `dropped`.

**Что происходит.** Фоновый процесс `tenant` на [координаторе кластера](../reference/glossary.md#coordinator):

1. Помечает удалёнными все бакеты тенанта и ждёт, пока пометки применят [мастеры](../reference/glossary.md#master) всех [репликасетов](../reference/glossary.md#replicaset).
2. Удаляет строки объектов в бакетах тенанта так же, как очистка удалённого бакета. Каждое
   удаление строки ставит объект в очередь удалённых фрагментов `s3r_chunkgc`, а в очередь
   [дедупликации](../reference/glossary.md#deduplication) тенанта ставит освобождение ссылки
   дедупликации и удаление отпечатка содержимого из индекса `s3r_content_fingerprint`, если они у
   объекта есть.
3. Когда мастеры всех репликасетов обработают очередь дедупликации тенанта, удаляет таблицы
   тенанта, его строки учёта квот и строки его бакетов.
4. Оставляет строку тенанта в состоянии `dropped`.

Удаление длится тем дольше, чем больше у тенанта объектов, а место возвращается по мере удаления
строк (см. [Занятость и освобождение места](monitoring.md#free_space)).

## Служебные тенанты {: #builtin_tenants }

Два тенанта принадлежат самому кластеру и не удаляются.

| Тенант | Идентификатор | Назначение |
|---|---|---|
| Тенант по умолчанию | 0 | [пространство имён](../reference/glossary.md#namespace) по умолчанию |
| Системный тенант | 4294967295 (последний идентификатор) | в его таблицах хранятся данные, не принадлежащие ни одному пользовательскому тенанту, а именно объекты дедупликации |

У системного тенанта нет ни FQDN, ни ключей доступа. Если перевести его в состояние `draining`,
фоновый процесс `tenant` вернёт его в состояние `active`.

## Правила CORS тенанта по умолчанию {: #default_cors }

У [тенанта](../reference/glossary.md#tenant) можно задать набор правил CORS по
умолчанию. Набор копируется в бакет при его создании операцией `CreateBucket`
или запросом `POST /v2/buckets`, и бакет сразу отвечает на предварительные
запросы для источников из набора.

Например, так всем новым бакетам тенанта разрешается загрузка из веб-консоли,
открытой на любом порту адреса `console.example.net`:

```shell
curl -u ivanov -X PUT 'https://console.example.net/s3gateway/api/v2/tenants?tenant_id=1' \
  -H 'content-type: application/json' \
  -d '{"default_cors": [{"id": "console-uploads", "methods": ["GET", "PUT", "HEAD"],
       "origins": ["https://console.example.net:*"], "headers": ["*"],
       "expose": ["ETag"], "max_age": 3600}]}'
```

Набор задают суперпользователь и администратор тенанта: запросом к
[API управления](../reference/management_api.md) или в консоли (см.
[Тенанты](console.md#console_tenants)).

| Задача | Запрос |
| --- | --- |
| Задать или заменить набор | `PUT /v2/tenants` с полем `default_cors`. Правило записывается в том же формате, что и в запросе `PUT /v2/buckets/{bucket}/cors`, и проверяется так же, как правила `PutBucketCors` |
| Задать набор при создании тенанта | то же поле в запросе `POST /v2/tenants` |
| Удалить набор | `"default_cors": null`. Пустой список отклоняется ответом `400` |
| Оставить набор без изменений | запрос без поля `default_cors` |
| Прочитать набор | поле `default_cors` ответа `GET /v3/tenants/{id}`: строка с массивом правил в формате JSON. Если набор не задан или некорректен, поле равно `null`. Некорректный набор можно записать только командой SQL |

Набор применяется только при создании бакета:

- изменение и удаление набора не затрагивают существующие бакеты, а бакетам,
  созданным до появления набора, правила не добавляются; им правила задаются
  операцией `PutBucketCors`;
- полученные правила становятся обычными правилами бакета. Владелец бакета и
  все, кому разрешена операция `GetBucketCors`, видят их, в том числе адрес
  консоли. Изменить правила можно операцией `PutBucketCors`, а удалить —
  операцией `DeleteBucketCors`. После удаления правила консоли загрузка из
  консоли в этот бакет перестаёт работать;
- поле `cors` в запросе `POST /v2/buckets` заменяет набор целиком;
- без набора бакет создаётся без правил.
