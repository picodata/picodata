# Решение типовых проблем

Страница нужна инженеру эксплуатации, который видит отказ при установке или работе S3R и ищет
причину. Каждый раздел построен одинаково: признак, причина, что делать. Проблемы со входом в
консоль разобраны отдельно, в разделе
[Решение проблем со входом](console_login.md#troubleshooting_console_access).

| Признак | Раздел |
|---|---|
| плагин не включается, в сообщении две версии | [Несовпадение версий](#ts_versions_mismatch) |
| [инстанс](../reference/glossary.md#instance) не запускается, `has N disks but no listener` | [Нет слушателя](#ts_no_listener) |
| диск не переходит в состояние `active` или его нет в `s3r_disk` | [Диски не монтируются](#ts_no_disk_mounts) |
| группы размещения не создаются | [Группы не создаются](#ts_no_placement_groups) |
| запись получает `503 ServiceUnavailable` | [Запись возвращает `ServiceUnavailable`](#ts_service_unavailable) |
| `ALTER PLUGIN ... SET` для `s3r_storage` отклоняется | [Команда отклоняется](#ts_alter_refused) |
| после настройки TLS на [слушателе](../reference/glossary.md#listener) `s3r_storage` плагин не загружается | [TLS без `ca_file`](#ts_plugin_does_not_start) |
| неясно, шифруется ли обмен [фрагментами](../reference/glossary.md#chunk) | [Проверка шифрования](#ts_unclear_tls) |
| растёт время ответа на малых объектах | [Очереди `s3r_meta`](#ts_long_response) |
| чтения возвращают устаревшие данные | [`read_preference`](#ts_outdated_data) |

## Плагин не включается, в сообщении приведены две версии {: #ts_versions_mismatch }

**Признак.** Плагин не включается; в сообщении об ошибке указаны две версии.

**Причина.** Версия Picodata не совпадает с версией библиотеки `picodata-plugin`, с которой собран
плагин.

**Что делать.** Проверьте, что установлено, и поставьте сборку плагина для своей версии Picodata
(см. [Соответствие версий S3R и Picodata](../install/requirements.md#picodata_s3r_versions)):

```sql
SELECT name, version, enabled FROM _pico_plugin;
SELECT plugin, name, tiers FROM _pico_service WHERE plugin = 's3r';
```

## Инстанс не запускается, сообщение `has N disks but no listener` {: #ts_no_listener }

**Признак.** Инстанс не запускается; в сообщении есть `has N disks but no listener`.

**Причина.** На инстансе заданы диски и не задан слушатель `s3r_storage` в конфигурации Picodata.
Отказ предусмотрен: без слушателя диски недоступны остальным [узлам](../reference/glossary.md#node).

**Что делать.** Задайте слушатель `s3r_storage` в конфигурации инстанса (см.
[Слушатель s3r_storage](../reference/configuration.md#s3r_storage_listener)).

## Диски не монтируются {: #ts_no_disk_mounts }

**Признак.** В журнале инстанса нет записи `disk ... mounted`; диск не в состоянии `active` либо
отсутствует в таблице `s3r_disk`.

**Что проверить.**

1. Запись `disk ... mounted` в журнале инстанса.
2. Состояние диска в таблице `s3r_disk`.
3. Шаг нового диска (`step`) и ошибку шага (`step_error`) в ответе `GET /v2/disks`.

**Причина и что делать.** Состояния и шаги диска описаны в разделе
[Идентификация диска](../concepts/disks.md#disk_identification).

| Что видно | Причина | Что делать |
|---|---|---|
| состояние `new`, шаг `mounting` или `formatting` | диск не открылся: директория недоступна, в окружении нет `io_uring` или `O_DIRECT`, либо новый накопитель слишком мал для того, что группы занимали на заменяемом | причина записана в журнале и в поле `step_error`; устраните её |
| состояние `blank`, `foreign` или `corrupt` | по пути диска нет его [суперблока](../reference/glossary.md#superblock): файловая система не смонтирована, накопитель заменён или суперблок повреждён | смонтируйте файловую систему либо переформатируйте диск (см. [Действия с дисками](disks.md)) |
| шаг `waiting for the tier's shape` | у [яруса](../reference/glossary.md#storage_tier) диска ещё нет записанной схемы | схема яруса записывается при [начальном формировании](../reference/glossary.md#formation) (см. [Начальное формирование](../concepts/formation.md#initial_formation)) |
| диска нет в `s3r_disk` | список дисков инстанса отклонён при первом запуске. Список регистрируется только целиком, и один неоткрывшийся диск отклоняет его весь | причина записана в столбце `reason` таблицы `s3r_instance` |

## Группы размещения не создаются {: #ts_no_placement_groups }

**Признак.** [Группы размещения](../reference/glossary.md#placement_group) не создаются, запись
объектов отклоняется.

**Что делать.**

1. Проверьте ответ `/-/ready`.
2. Если кластер ещё не сформирован, разберите причины по разделу
   [Если установка не завершается](../install/troubleshooting.md#install_troubleshooting).
3. Если кластер сформирован, посмотрите поле `reasons` в ответе `/-/debug/topology`.

**Причины в поле `reasons`.**

| Причина | Что означает |
|---|---|
| `no_disks` | в ярусе нет дисков |
| `no_shape` | у яруса нет схемы |
| `not_enough_domains`, `no_failure_domain`, `not_enough_instances` | описаны в разделе [Раскладка группы](../concepts/placement_groups.md#group_layouts) |
| `no_position` | для [участника](../reference/glossary.md#member) нет позиции, сохраняющей правила |
| `wait` | позиция плана временно недоступна |

## Запись возвращает `ServiceUnavailable` {: #ts_service_unavailable }

**Признак.** Запись получает ответ `503 ServiceUnavailable`.

**Что это значит.** Ответ `503` означает ситуацию, которая может пройти, и клиент повторяет запрос
(см. [Ответы клиенту при отказе хранилища](../usage/errors.md#storage_errors)).

**Причина и что делать.**

| Что видно | Причина | Что делать |
|---|---|---|
| сообщение `the cluster is new (registering)` либо `the cluster is new (forming)` | кластер не прошёл начальное формирование | см. [Начальное формирование](../concepts/formation.md#initial_formation) |
| сообщение `this instance owns no placement group in tier ...` | у инстанса, принявшего запрос, нет дисков яруса этого объекта | проверьте, какие диски этого яруса есть у инстанса (таблица `s3r_disk`) |
| отказ длится недолго | группа только что создана, монтируется после перезапуска инстанса или ждёт, пока новый участник возьмёт её [экстенты](../reference/glossary.md#extent) | клиент повторяет запрос |
| в журнале инстанса строка `tier <ярус> needs a group and none can be formed: <причина>` | группы инстанса приостановлены из-за недоступного участника или заполнены, а новую группу получить не удаётся. Запись отклоняется, даже если на других инстансах место есть | устраните причину из раздела [Раскладка группы](../concepts/placement_groups.md#group_layouts) |

## Команда `ALTER PLUGIN ... SET` для `s3r_storage` отклоняется {: #ts_alter_refused }

**Признак.** Команда `ALTER PLUGIN ... SET` с параметром сервиса `s3r_storage` завершается ошибкой.

**Причина.** Новое значение нарушает правило проверки конфигурации. В сообщении указано нарушенное правило и сказано, что сделать. Чаще всего отклоняются:

- изменение `s3r_storage.disks` после регистрации дисков;
- изменение [схемы избыточности](../reference/glossary.md#erasure_shape) яруса, в котором уже есть группы.

**Что делать.** Диски меняйте [действиями API управления](disks.md). Схема избыточности яруса с
группами не меняется (см.
[Что нельзя изменить после установки](../concepts/redundancy.md#immutable)). Остальные правила
перечислены в разделе [Сервис s3r_storage](../reference/configuration.md#s3r_storage).

## Настроен TLS на слушателе `s3r_storage`, плагин не загружается {: #ts_plugin_does_not_start }

**Признак.** После настройки TLS на слушателе `s3r_storage` плагин не загружается.

**Причина.** Раздел `tls` задан без `ca_file`. Сертификат подтверждает право узла запрашивать
фрагменты, поэтому цепочка без удостоверяющего центра не принимается.

**Что делать.** Укажите `ca_file` в разделе `tls` (см. [Шифрование трафика](tls.md)).

## Неясно, шифруется ли обмен фрагментами {: #ts_unclear_tls }

**Что делать.** Найдите в журнале инстанса строку `chunk endpoint serving on ...`. Её окончание
отвечает на вопрос:

| Окончание строки | Что означает |
|---|---|
| `over mutual TLS` | обмен шифруется |
| `over plaintext; carry it over a trusted network` | обмен не шифруется |

## Растёт время ответа на малых объектах {: #ts_long_response }

**Признак.** Растёт время ответа на запросы к малым объектам.

**Что проверить.** Метрики `s3r_bridge_wait_seconds` и `s3r_bridge_queue_depth` по меткам `pool`.
Они показывают очереди, в которых обращения к таблицам ждут
[транзакционного потока](../reference/glossary.md#tx) (см.
[Зачем нужен отдельный сервис для таблиц](../concepts/architecture.md#tx_and_workers)).

| Что видно | Причина | Что делать |
|---|---|---|
| растёт очередь пулов `pool="local"` и `pool="routed"` | транзакционный поток достиг предела пропускной способности. Рост глубины очереди виден раньше, чем рост задержки запросов | транзакционный поток у инстанса один, поэтому предел поднимают числом [репликасетов](../reference/glossary.md#replicaset) (см. [Число инстансов](../install/requirements.md#instances_count)); если нагрузку создают объекты, хранимые в строке, уменьшите `inline_max` (см. [Что даёт такое устройство](../concepts/architecture.md#properties)). Параметры `bridge_queue` и `bridge_fibers` сервиса `s3r_meta` меняют только время ожидания в очереди и применяются при следующем запуске сервиса (см. [Сервис s3r_meta](../reference/configuration.md#s3r_meta)) |
| очередь к пулу `catalog` при пустых очередях `local` и `routed` | задержка [Raft](../../../overview/glossary.md#raft) | в сформированном кластере запросы `GetObject` и `PutObject` она не задерживает |

Ожидание в пулах `catalog` и `background` измеряется секундами и зависит прежде всего от скорости
Raft. Число [файберов](../../../overview/glossary.md#fiber) пула `background` задаёт параметр `bridge_fibers`.

!!! note "Во время начального формирования"
    Пока кластер формируется, очередь к пулу `catalog` задерживает и `PutObject`: запись, которой
    нужен новый экстент, ждёт, пока участник группы запишет число свободных экстентов через этот
    пул.

## Чтения возвращают устаревшие данные {: #ts_outdated_data }

**Признак.** Только что записанный объект не находится или не виден в списке, удалённый объект ещё
читается, отозванное разрешение ещё действует.

**Причина.** Параметр `read_preference` имеет значение `any`. Оно разрешает репликам обслуживать
запросы `GetObject`, `HeadObject`, `ListObjects`, `ListObjectsV2`, `ListObjectVersions`,
`ListMultipartUploads` и `ListParts`, и для этих запросов гарантии «чтение видит запись» нет.
Реплика, которая ещё не применила изменение с [мастера](../reference/glossary.md#master), отвечает по своей копии метаданных:

- объект, записанный после последнего применённого изменения, не находится и не показывается в
  списке, а удалённый объект ещё находится;
- список собирается по страницам, и каждая страница отражает копию, которая её обслужила. Ключи
  идут по порядку и не повторяются, но ключ из списка может вернуть `NoSuchKey` на запрос
  `GetObject`, который обслужила другая копия;
- изменения ACL объекта, его тегов и условий политики по тегам начинают действовать на реплике
  только после того, как реплика их применит. До этого отозванное разрешение продолжает открывать
  доступ на чтение;
- запрос `GetObject` объекта, удалённого на мастере, после повторного использования его места на
  дисках (через `refill_after_s` после удаления) возвращает внутреннюю ошибку или ответ `200` с
  укороченным телом. Данные другого объекта такой запрос не возвращает.

!!! warning "Задержка реплики не ограничена"
    Реплика, у которой остановилась репликация, продолжает отвечать по всё более устаревшей копии.

Запросы на изменение данных и чтения, по которым принимается решение о записи, всегда обслуживает
мастер. К таким чтениям относятся чтение источника в `CopyObject` и `UploadPartCopy`, проверка
пустоты [бакета](../reference/glossary.md#bucket) перед `DeleteBucket` и чтение частей при завершении [составной загрузки](../reference/glossary.md#multipart_upload).

**Что делать.**

1. Проверьте значение параметра `read_preference`. При значении `leader` метаданные читаются с
   мастера (см. [Сервис s3r_meta](../reference/configuration.md#s3r_meta)).
2. Проверьте состояние репликации на реплике в `box.info.replication`: у каждого источника поле
   `upstream.status` должно иметь значение `follow`, а поле `upstream.lag` показывает задержку в
   секундах.
