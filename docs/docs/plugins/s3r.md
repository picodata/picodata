# s3r

В данном разделе приведены сведения о s3r, плагине объектного хранилища для
СУБД Picodata. Это же руководство поставляется вместе со сборкой плагина.

!!! tip "Picodata Enterprise"
    Функциональность плагина доступна только в коммерческой версии Picodata.

## О документе {: #o_dokumente }

Документ описывает установку, настройку и эксплуатацию плагина s3r —
объектного хранилища с интерфейсом, совместимым с Amazon S3, работающего внутри
СУБД Picodata.

Описано текущее состояние плагина. В главе «Ограничения» приведён полный
перечень неподдерживаемых возможностей.

Версия плагина, под которой выполняются приведённые команды `ALTER PLUGIN`, —
`2.0.0`; она видна запросом `SELECT name, version FROM _pico_plugin`.

Документ предназначен для администраторов, разработчиков прикладных систем и
инженеров эксплуатации.

## Назначение и устройство {: #naznachenie_i_ustroistvo }

### Что представляет собой s3r {: #chto_predstavlyaet_soboi_s3r }

Плагин s3r хранит метаданные объектного хранилища — бакеты, объекты, каталоги,
карту размещения — в таблицах Picodata: глобальных, реплицируемых через
Raft-консенсус, и шардированных через vshard. Содержимое объектов размещается на
локальных дисках узлов в журнально-структурированном хранилище блоков и
защищается репликацией либо кодами Рида — Соломона.

Архитектура обеспечивает три свойства.

**Согласованность.** Отдельный слой метаданных с отложенной согласованностью и
внешние хранилища вида etcd или RocksDB не используются. Пространство имён
линеаризуемо за счёт Raft-консенсуса. Метаданные объекта размещаются в одном
шарде vshard. При `read_consistency = strong` (значение по умолчанию) операции
с одним ключом линеаризуемы и после успешной записи новые данные сразу доступны
для чтения. Значение `eventual` разрешает чтение с реплики и допускает
устаревший результат.

**Горизонтальная масштабируемость.** Производительность работы с метаданными
растёт с числом репликасетов и не ограничивается единственным узлом-мастером.

**Скорость обработки малых объектов.** Объект размером до `inline_max`
размещается в кортеже метаданных. Чтение такого объекта выполняется как
обращение к одной таблице в оперативной памяти, без обращения к диску.

### Состав плагина {: #sostav_plagina }

Плагин состоит из трёх логических сервисов. Все они должны быть назначены на
одни и те же тиры Picodata: разделение сервисов по разным группам узлов не
поддерживается и проверяется при запуске. Порядок запуска сервисов при этом не
определён, поэтому каждый из них ожидает готовности остальных.

| Сервис | Назначение |
| --- | --- |
| `s3r_api` | Приём запросов S3: разбор HTTP, проверка подписи SigV4, авторизация, разбиение объекта на блоки, кодирование и сборка |
| `s3r_meta` | Операции над таблицами пространства имён, взаимодействие между средой выполнения Tokio и транзакционным потоком TX |
| `s3r_storage` | Хранилище блоков на локальных дисках, регистрация дисков в кластере, обмен фрагментами блоков между узлами, ведение карты размещения |

Обычная установка размещает все три сервиса на одном тире.

### Путь запроса на запись {: #put_zaprosa_na_zapis }

Запись объекта, превышающего `inline_max`, выполняется по следующей схеме.

1. Сервис `s3r_api` принимает тело запроса и проверяет подпись.
2. Объект разбивается на блоки размером `block_bytes` выбранной группы
   размещения.
3. Каждый блок кодируется в `k` частей данных и `m` частей чётности либо
   копируется `R` раз — в зависимости от класса хранения.
4. Части передаются на диски, перечисленные в группе размещения. Транспорт —
   HTTP/2; единица передачи совпадает с единицей записи на диск.
5. Блок считается записанным, когда его приняло и сохранило на диске не менее
   `k + m − write_tolerance` дисков — но не менее `k`. Части, которые не были
   приняты, заносятся в очередь дозаписи.
6. После того как все блоки записаны, в пространстве имён создаётся одна строка
   объекта.

Метаданные не фиксируются раньше данных.

#### Кворум записи {: #kvorum_zapisi }

Параметр `write_tolerance` сервиса `s3r_storage` задаёт, сколько частей блока
запись вправе оставить недописанными. Значение по умолчанию — 1.

Значение 1 соответствует типичному отказу одного узла: диски одной группы
размещения находятся в разных доменах отказа, поэтому выход из строя одного
инстанса делает недоступной одну позицию группы. При значении 0 для записи
требуются все части, поэтому недоступность одного инстанса приводит к отказу
каждой записи в группу с его диском.

Нижняя граница — `k`. Блок из `k` частей доступен для чтения, но следующая
потеря части сделает чтение невозможным. При наличии от `k + 1` до `k + m`
частей блок остаётся доступным для чтения при ещё одном отказе, пока система
восстанавливает недостающие части. Значение `write_tolerance` больше `m`
приводится к нижней границе, а не отклоняется.

Если группа размещения, выбранная для объекта, не набирает кворума — например,
недоступны два инстанса из четырёх, — запись выполняется в следующую группу той
же площадки. Границу площадки выбор не пересекает.

Недостающие части записываются в таблицу `s3r_shortfall` и дописываются фоновым
процессом того инстанса, которому принадлежит соответствующий диск. Запись, для
которой не удалось создать запись в этой таблице, завершается ошибкой: без неё
недостача была бы невосполнимой и невидимой.

Состояние очереди:

```
SELECT object_id, slot, pg_id FROM s3r_shortfall;
```

Пустая таблица означает, что все части всех объектов записаны полностью.

Чтение выполняется в обратном порядке. Строка объекта содержит идентификатор
группы размещения и размер; из них выводится геометрия блоков, после чего
запрашиваются блоки, попадающие в запрошенный диапазон.

## Требования {: #trebovaniya }

| Компонент | Требование |
| --- | --- |
| СУБД | Picodata. Версия должна соответствовать версии библиотеки `picodata-plugin`, с которой собран плагин. При несовпадении плагин не загружается и выводит обе версии |
| Операционная система | Linux. Поддерживаются ALT p10 и Astra 1.8 |
| Ядро | 5.10 или новее |
| Подсистема ввода-вывода | `io_uring` и открытие файлов с флагом `O_DIRECT`. Резервная реализация отсутствует: при недоступности этих механизмов диск не монтируется, событие фиксируется в журнале |
| Файловая система | Локальная, с поддержкой `O_DIRECT` и `posix_fallocate` |

Окружение контейнера проверяется отдельно. Профиль seccomp может запрещать
системные вызовы `io_uring`, а оверлейная файловая система — открытие с
`O_DIRECT`. Причины независимы, отказ одного механизма не влечёт отказа другого.

## Установка {: #ustanovka }

### Промышленная установка {: #promyshlennaya_ustanovka }

Сборка архива с плагином:

```
cargo pike plugin pack
```

Архив содержит библиотеку `libs3r.so`, файл манифеста и каталог с миграциями.
Установка выполняется штатными средствами Picodata — ролью Ansible либо вручную.

При установке вручную архив распаковывается в каталог
`<share-dir>/s3r/<версия>`, после чего плагин устанавливается командами SQL:

```
CREATE PLUGIN s3r 2.0.0;

ALTER PLUGIN s3r 2.0.0 ADD SERVICE s3r_storage TO TIER default;
ALTER PLUGIN s3r 2.0.0 ADD SERVICE s3r_meta TO TIER default;
ALTER PLUGIN s3r 2.0.0 ADD SERVICE s3r_api TO TIER default;

ALTER PLUGIN s3r 2.0.0 SET migration_context.storage_tier = 'default';
ALTER PLUGIN s3r 2.0.0 SET migration_context.engine = 'memtx';
ALTER PLUGIN s3r 2.0.0 SET migration_context.unlogged = '';

ALTER PLUGIN s3r MIGRATE TO 2.0.0;
ALTER PLUGIN s3r 2.0.0 ENABLE;
```

Порядок команд определён: сервисы назначаются на тир и задаётся контекст
миграции до применения миграций, поскольку имя тира и движок хранения
подставляются в текст миграций.

Все три сервиса назначаются на один тир. Разделение по разным тирам не
поддерживается и не даёт выигрыша: три сервиса — это разделение кода, а не узлов.
Сервис `s3r_meta` предоставляет локальный мост к потоку TX, и без него конечная
точка S3 на узле теряет доступ к метаданным; фоновые процессы читают строки
своего же инстанса; вызовы между сервисами рассчитаны на соседа по узлу.
Плагин проверяет совпадение списков тиров при запуске и отказывается включаться,
если они различаются. Имя тира выбирает оператор: в примере это `default`, и то
же имя указывается в `migration_context.storage_tier`.

Пример создаёт схему и включает сервисы, но сам по себе не завершает
промышленную настройку. До приёма клиентского трафика настройте диски и
слушатель `s3r_storage` на каждом инстансе, настройте TLS для клиентского и
внутрикластерного контуров и убедитесь, что группы размещения созданы. Без
дисков объекты крупнее `inline_max` записать нельзя. Без раздела `tls`
соответствующий сетевой контур передаёт данные без шифрования.

### Тестовый кластер {: #testovyi_klaster }

Локальный кластер разворачивается средством Pike:

```
cargo install picodata-pike
cargo pike run
```

Pike собирает плагин, поднимает кластер по описанию из `topology.toml`,
устанавливает плагин, применяет миграции и включает сервисы. Остановка кластера
выполняется командой `cargo pike stop`.

### Удаление {: #udalenie }

```
ALTER PLUGIN s3r 2.0.0 DISABLE;
DROP PLUGIN s3r 2.0.0 WITH DATA;
```

Параметр `WITH DATA` применяет миграции вниз и удаляет таблицы плагина вместе с
метаданными объектов. Содержимое объектов на дисках сохраняется; каталоги дисков
очищаются отдельной операцией.

## Конфигурация {: #konfiguraciya }

Конфигурация плагина едина для всего кластера. Значения по умолчанию заданы в
манифесте и изменяются командой `ALTER PLUGIN ... SET`.

Параметры, различающиеся от узла к узлу, задаются конфигурацией самой Picodata
(раздел `instance.plugin`) и переменными окружения.

Сводный перечень всех параметров со значениями по умолчанию приведён в
приложении В.

### Контекст миграции {: #kontekst_migracii }

Значения задаются до применения миграций и после них не изменяются: они
подставляются в текст миграций как фрагменты SQL.

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `storage_tier` | `default` | тир Picodata, в котором создаются шардированные таблицы и работает хранилище блоков |
| `engine` | `memtx` | движок таблиц пространства имён: `memtx` или `vinyl` |
| `unlogged` | пусто | значение `UNLOGGED` отключает журнал упреждающей записи для таблиц пространства имён; допустимо для `memtx` и только там, где допустима потеря метаданных при перезапуске ведущего узла репликасета |

### Сервис s3r_api {: #servis_s3r_api }

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `listen` | `127.0.0.1:8000` | адрес и порт конечной точки S3, только если раздел слушателя отсутствует в конфигурации Picodata |
| `inline_max` | `4096` | верхняя граница класса `inline` |
| `max_body_bytes` | `268435456` | устаревший параметр для совместимости с сохранёнными конфигурациями; текущая версия его не использует |
| `credentials` | `[]` | начальный список ключей доступа только для арендатора 0; пустой список не отключает аутентификацию Picodata |
| `backend` | `picodata` | источник данных; значение `fs` — отладочный режим поверх файловой системы |
| `fs_root` | `null` | каталог для режима `backend = fs` |
| `region` | `default` | значение в ответе `GetBucketLocation` и допустимое значение `LocationConstraint` при создании бакета |
| `service_timeout_s` | `30` | предельное время ожидания внутренних ресурсов: памяти, очередей, дисков и узлов; время ожидания данных от клиента не учитывается |
| `api_memory` | четверть памяти, доступной процессу | общий предел памяти для содержимого объектов в обрабатываемых запросах; значение `0` выбирает предел автоматически |
| `diagnostics` | `health` | доступная часть пространства `/-/`: `health`, `debug` или `bench` |

Ограничения на полный размер тела запроса нет. Путь записи потоковый: байты
кодируются и передаются на диски по мере поступления, поэтому в памяти не
накапливается весь записываемый объект. Параметр `api_memory` учитывает буфер
приёма и одновременно созданные из него фрагменты. Для схемы `k+m` это
приблизительно объём буфера, умноженный на `1 + (k + m) / k`.

При чтении в памяти собирается весь запрошенный диапазон, и его размер также
резервируется из `api_memory`. Если память не освободится за
`service_timeout_s`, запрос завершается ответом `SlowDown`.

Параметры TLS в конфигурации плагина отсутствуют. Сертификат задаётся в
конфигурации Picodata, в том же разделе, что и для остальных слушателей.

Каждый экземпляр с этим сервисом открывает собственный порт и обслуживает
запросы к любым данным кластера. Балансировщик направляет запрос на любой узел.

### Сервис s3r_meta {: #servis_s3r_meta }

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `bridge_fibers` | `16` | число служебных волокон, обрабатывающих обращения к метаданным со стороны Tokio; ограничивает число одновременных операций |
| `bridge_queue` | `256` | предельное число заданий в очереди к служебным волокнам; при заполнении очереди приём новых запросов приостанавливается |
| `read_consistency` | `strong` | `strong` — чтение с ведущего узла репликасета, после успешной записи новые данные сразу доступны для чтения; `eventual` — чтение с реплики с меньшими затратами ресурсов, при котором возможны устаревшие данные |

### Сервис s3r_storage {: #servis_s3r_storage }

| Параметр | По умолчанию | Описание |
| --- | --- | --- |
| `disks` | `[]` | список каталогов под хранилище блоков, с необязательными доменом отказа, ярусом, ёмкостью и размером экстента |
| `erasure` | `[]` | формы групп размещения для кодирования: `k`, `m`, `block_bytes` (по умолчанию 2 МиБ), `tier` (ярус, по умолчанию `standard`) |
| `tiers` | `[]` | карта классов хранения S3: `{name, class}` в порядке от наиболее частого к наиболее редкому доступу; пусто — `standard` с `STANDARD` |
| `write_tolerance` | `1` | сколько частей блока запись вправе оставить недописанными; см. «Кворум записи» |

Пример объявления формы кодирования:

```
ALTER PLUGIN s3r 2.0.0 SET
  s3r_storage.erasure = '[{"k":8,"m":4,"block_bytes":1048576}]';
```

Формы для репликации не объявляются. Число копий определяется параметром
`replication_factor` тира Picodata, на котором работает хранилище.

Адрес обмена фрагментами блоков задаётся в конфигурации Picodata, поскольку различается на
каждом узле.

### Конфигурация Picodata {: #konfiguraciya_picodata }

Файл конфигурации инстанса содержит три параметра, которые конфигурация плагина
выразить не может.

```
instance:
  failure_domain:
    dc: msk
    rack: r3
  plugin:
    s3r:
      service:
        s3r_api:
          listener:
            enabled: true
            listen: "0.0.0.0:8000"
            tls:
              enabled: true
              cert_file: /etc/s3r/server.pem
              key_file:  /etc/s3r/server.key
              ca_file:   /etc/s3r/clients-ca.pem
        s3r_storage:
          listener:
            enabled: true
            listen: "0.0.0.0:8700"
            advertise: "node3.example.net:8700"
```

**Домен отказа инстанса** (`failure_domain`) Picodata определяет
самостоятельно. Компонент `dc` задаёт площадку: группа размещения не пересекает
границу площадки.

**Слушатель `s3r_api`** задаёт адрес конечной точки S3 и её сертификат. Параметр
`ca_file` включает двустороннюю аутентификацию TLS (mTLS): клиент без
сертификата отклоняется на этапе рукопожатия. Если раздел `listener` отсутствует,
применяются `S3R_API_LISTEN` и затем параметр `s3r_api.listen`. Явное
`listener.enabled: false` отключает конечную точку S3 и к запасному адресу не
переходит.

**Слушатель `s3r_storage`** задаёт адрес обмена фрагментами блоков. Объявленный
адрес (`advertise`) Picodata публикует в таблице `_pico_peer_address`; этот механизм
обеспечивает обнаружение узлов. Собственного реестра узлов плагин не ведёт.

Инстанс, на котором заданы диски и не задан слушатель `s3r_storage`, не
запускается. Такая конфигурация опубликовала бы диски, недоступные для остальных
узлов кластера, при внешне исправном состоянии узла.

| Переменная | Назначение |
| --- | --- |
| `S3R_DISKS` | список дисков инстанса; перекрывает параметр `s3r_storage.disks` |
| `S3R_API_LISTEN` | адрес конечной точки S3, только если раздел слушателя отсутствует в конфигурации Picodata |
| `S3R_WORKER_THREADS` | верхняя граница пула рабочих потоков Tokio |

Переменная `S3R_DISKS` задаётся как список дисков через запятую; диск описывается
полями через двоеточие: `путь[:КЛЮЧ=ЗНАЧЕНИЕ]*[:ёмкость[:размер_экстента]]`,
например `/mnt/d0:hba=a,/mnt/d1:hba=b:tier=hdd`. Поле со знаком `=` — свойство
диска: `tier=` задаёт ярус (метка оператора из `[a-z0-9_-]`, по умолчанию
`standard`), остальные свойства образуют поддомен отказа. Поля без `=`
позиционные: ёмкость, затем размер экстента. Параметр `disks` в конфигурации
плагина описывает установку с одинаковыми устройствами по одинаковым путям на
всех узлах. Если пути различаются, например из-за нескольких инстансов на одном
узле, их задают переменной окружения. На каждой площадке при этом должно
хватать дисков и независимых доменов отказа для каждого используемого яруса;
результат проверяется по полю `unsatisfied` в `/-/debug/topology`.

Переменная `S3R_WORKER_THREADS` применяется на узлах с несколькими инстансами.
Без неё каждый инстанс определяет размер пула по всей машине: на узле с четырьмя
инстансами суммарно запускается вчетверо больше рабочих потоков, чем есть
процессорных ядер. При ограничении инстансов средствами cgroup переменная не
требуется — `available_parallelism()` учитывает квоту.

## Шифрование трафика {: #shifrovanie_trafika }

Плагин обслуживает два независимых сетевых контура: клиентский, по которому
приходят запросы S3, и внутрикластерный, по которому узлы обмениваются
фрагментами блоков. Контуры настраиваются отдельно.

| Контур | Транспорт | Шифрование |
| --- | --- | --- |
| Клиентский (S3) | HTTP/1.1 | TLS, при заданном `ca_file` — mTLS |
| Внутрикластерный (обмен фрагментами блоков) | HTTP/2 | взаимный TLS, `ca_file` обязателен |

Оба контура по умолчанию работают без шифрования и включаются заданием раздела
`tls` в конфигурации соответствующего слушателя.

### Клиентский контур {: #klientskii_kontur }

TLS для конечной точки S3 задаётся разделом `listener` сервиса `s3r_api` в
конфигурации Picodata. Отдельных параметров TLS у плагина нет: сертификат
описывается там же, где и для остальных слушателей Picodata.

```
instance:
  plugin:
    s3r:
      service:
        s3r_api:
          listener:
            enabled: true
            listen: "0.0.0.0:8443"
            tls:
              enabled: true
              cert_file: /etc/s3r/server.pem
              key_file:  /etc/s3r/server.key
              ca_file:   /etc/s3r/clients-ca.pem
```

Параметр `ca_file` включает двустороннюю аутентификацию (mTLS). Клиент без
сертификата, подписанного указанным удостоверяющим центром, отклоняется на
этапе рукопожатия TLS, до разбора запроса S3.

Рукопожатие выполняется на среде выполнения Tokio средствами OpenSSL. Набор
шифров соответствует профилю Mozilla Intermediate v5.

#### Версии протокола и наборы шифров {: #versii_protokola_i_nabory_shifrov }

Плагин пользуется той библиотекой OpenSSL, с которой собрана Picodata, и не
вводит собственной криптографии. Отсюда следуют две вещи. Доступные версии
протокола и наборы шифров — те же, что у остальных слушателей Picodata;
поддерживается TLS 1.3, как для клиентского контура, так и для
внутрикластерного. И поддержка отечественных алгоритмов определяется сборкой:
в конфигурации с OpenSSL, поддерживающей ГОСТ, доступны и они, отдельной
настройки в плагине для этого нет.

#### Сертификат арендатора и выбор по SNI {: #sertifikat_arendatora_i_vybor_po_sni }

Слушатель `s3r_api` использует сертификат кластера, заданный в конфигурации
Picodata. Арендатор может отвечать по собственному доменному имени
(`s3r_tenant.domain`, см. раздел об изоляции арендаторов) с собственным
сертификатом. Материал сертификата
хранится в самой строке `s3r_tenant` — в столбцах `cert_chain`, `cert_key` и, для
взаимного TLS, `mtls_ca`, — а не в файле на узле: строка реплицируется на все узлы
в одной транзакции. При хранении в отдельных файлах их пришлось бы
распространять по узлам, а рассогласование привело бы к ошибкам TLS на части
узлов.

Материал задаётся как **PEM в кодировке Base64**. Закрытый ключ в формате PEM
содержит несколько строк, а не все способы передачи значения сохраняют
переносы. Представление Base64 состоит из одной строки и не зависит от способа
передачи.

Во время рукопожатия сервер по имени из SNI выбирает сертификат нужного
арендатора. Если у арендатора задан `mtls_ca`, сервер также требует клиентский
сертификат. Выбор выполняется до чтения заголовка `Host`, поскольку к этому
моменту TLS-рукопожатие уже завершено. Соединение без SNI обслуживается только
как арендатор по умолчанию и получает его сертификат и его режим проверки
клиентского сертификата; если у арендатора по умолчанию нет своего сертификата,
предъявляется сертификат кластера. Запрос, адресованный по `Host` любому другому
арендатору, отклоняется. Имя из SNI должно соответствовать арендатору запроса:
клиент не может предъявить сертификат одного арендатора и обратиться к данным
другого. Требование клиентского сертификата нельзя обойти, опустив SNI.

Сертификат арендатора заменяется командой `UPDATE` его строки. Изменение
реплицируется на все узлы и не прерывает обслуживание других арендаторов.

Ключ хранится в журнале упреждающей записи и в снимках до их уплотнения. Поэтому
компрометация ключа требует не только его смены, но и учёта того, что старый ключ
восстановим из резервной копии за тот период. Это в равной мере верно для секретов
TLS в Kubernetes. Таблица `s3r_tenant` не выдаётся связкам табличных разрешений:
строку читает только администратор, а сам плагин обращается к столбцу ключа
единственно чтобы собрать контекст TLS и не отражает его ни в журнале, ни в
диагностике.

### Внутрикластерный контур {: #vnutriklasternyi_kontur }

Обмен фрагментами блоков между узлами шифруется, если в конфигурации слушателя
`s3r_storage` задан раздел `tls`. Без него порт обмена фрагментами принимает и
передаёт содержимое объектов в открытом виде — это поведение по умолчанию, и для
кластера разработки на одном узле оно уместно.

Каждый узел выступает одновременно сервером и клиентом обмена фрагментами, поэтому
схема — взаимная аутентификация на общем удостоверяющем центре кластера. Узел
предъявляет собственный сертификат и проверяет сертификат узла на другом конце
соединения.

```
instance:
  plugin:
    s3r:
      service:
        s3r_storage:
          listener:
            enabled: true
            listen: "0.0.0.0:8700"
            advertise: "node3.example.net:8700"
            tls:
              enabled: true
              cert_file: /etc/s3r/node3.pem
              key_file:  /etc/s3r/node3.key
              ca_file:   /etc/s3r/cluster-ca.pem
```

| Параметр | Роль в схеме |
| --- | --- |
| `cert_file`, `key_file` | сертификат и ключ узла; предъявляются при приёме и установлении соединения |
| `ca_file` | удостоверяющий центр кластера; используется для проверки сертификата другого узла |

`ca_file` обязателен. Для клиентского контура он необязателен: там
сертификат подтверждает сервер публичному клиенту. Запрос фрагмента блока не
несёт подписи S3: право на запрос определяется принадлежностью узла к кластеру
и подтверждается его сертификатом. Без `ca_file` невозможно проверить, что
соединение установлено с доверенным узлом. Поэтому раздел `tls` без `ca_file`
останавливает загрузку плагина и выводит сообщение об ошибке.

При запуске узел сообщает выбранный режим:

```
shard endpoint serving on Some(127.0.0.1:9801) over mutual TLS, repair and
shortfall workers started
```

Фрагмент `over mutual TLS` означает, что включены шифрование и взаимная
аутентификация. Без раздела `tls` сообщение содержит `over plaintext; carry it
over a trusted network`: данные передаются без шифрования, поэтому порт следует
размещать в изолированной сети. Режим передачи не записывается в таблицы
`s3r_pg` и `s3r_disk`.

#### Имя узла не проверяется {: #imya_uzla_ne_proveryaetsya }

Адреса узлов берутся из таблицы `_pico_peer_address` в виде `IP:порт` — они
приходят из консенсуса самого кластера, а не от службы имён. Проверка имени
потребовала бы, чтобы каждый сертификат нёс IP в `subjectAltName` и
перевыпускался при переезде узла, и не добавила бы ничего к адресу, полученному
из Raft. Проверяется цепочка: подписан удостоверяющим центром кластера — или
рукопожатие не состоится.

Чего эта схема не даёт — различения узлов между собой: любой держатель
сертификата, подписанного центром кластера, может выступать любым узлом. Для
устранения нужна проверка имени, а для неё — устойчивые имена узлов, которых
установка пока не имеет.

Выпуск сертификатов узлов средствами `openssl`:

```
# Удостоверяющий центр кластера, один на установку.
openssl req -x509 -newkey rsa:4096 -days 3650 -nodes \
  -keyout cluster-ca.key -out cluster-ca.pem \
  -subj "/CN=s3r cluster CA"

# Сертификат узла.
openssl req -newkey rsa:2048 -nodes \
  -keyout node3.key -out node3.csr \
  -subj "/CN=node3.example.net"

openssl x509 -req -in node3.csr -days 825 \
  -CA cluster-ca.pem -CAkey cluster-ca.key -CAcreateserial \
  -extfile <(printf "subjectAltName=DNS:node3.example.net\nextendedKeyUsage=serverAuth,clientAuth") \
  -out node3.pem
```

Расширение `extendedKeyUsage` содержит оба назначения: узел использует один
сертификат и как сервер, и как клиент.

Реализация опирается на OpenSSL — ту же библиотеку, что обслуживает клиентский
контур. Выбор определяется требованиями сертификации: криптография наследуется
от Picodata и поддерживает отечественные алгоритмы через подключаемый модуль
OpenSSL.

Там, где шифрование не включено, внутрикластерный трафик изолируется сетевыми
средствами: отдельный сегмент или VLAN для межузлового обмена, фильтрация порта
обмена фрагментами блоков на границе сегмента, туннелирование через IPsec либо
WireGuard при передаче между площадками.

## Диски и домены отказа {: #diski_i_domeny_otkaza }

### Идентификация диска {: #identifikaciya_diska }

Диском для s3r выступает каталог локальной файловой системы. При первом запуске
в нём создаётся суперблок с постоянным идентификатором диска и идентификатором
кластера. Записи о размещении ссылаются на этот идентификатор, а не на путь или
имя инстанса.

Схема идентификации обеспечивает два свойства:

- диск переносится на другой узел вместе с данными, состав групп размещения при
  этом сохраняется;
- диск, отформатированный другим кластером, к монтированию не принимается;
  плагин выводит оба идентификатора кластера. Механизм исключает затирание
  данных при ошибке в конфигурации.

Параметр диска `capacity_bytes` может ограничить используемую ёмкость ниже
размера файловой системы. Параметр `extent_bytes` задаёт размер файла экстента:
по умолчанию 1 ГиБ, допустимы кратные 4096 значения от 16 МиБ до 2 ГиБ. Оба
поля можно указать в YAML либо позиционными полями `S3R_DISKS`. Размер экстента
и вычисленное из ёмкости число экстентов записываются при форматировании и не
меняются для диска с данными; другая ёмкость или размер экстента требуют нового
пустого каталога.

### Домен отказа диска {: #domen_otkaza_diska }

Домен отказа диска представляет собой домен отказа его инстанса, расширенный
поддоменом диска.

```
инстанс dc=msk,rack=r3   диск (не задан)  ->  dc=msk,rack=r3
инстанс dc=msk,rack=r3   диск hba=a       ->  dc=msk,rack=r3,hba=a
```

Поддомен диска указывает, отказывают ли два диска одного инстанса независимо.
Домен инстанса одинаков для всех его дисков и такую независимость выразить не
может.

Правило размещения едино для обоих классов: **`n` участников в `n` различных
доменах отказа** — `R` копий для класса `replica`, `k+m` частей для класса `ec`.

Диск без объявленного поддомена считается настолько же независимым, насколько
его инстанс. Несколько таких дисков на одном инстансе образуют один домен;
группа из `k+m` частей на них не собирается, применяется репликация. При
отсутствии сведений о независимости дисков кодирование не выполняется.

## Классы хранения и группы размещения {: #klassy_hraneniya_i_gruppy_razmescheniya }

Размещение объекта определяется двумя независимыми решениями.

| Ось | Что определяет | Чем задаётся |
| --- | --- | --- |
| Внутри площадки | как байты разложены по дискам: `inline`, `ec` или, при отсутствии групп кодирования, `replica` | параметром `inline_max` и формами в `s3r_storage.erasure` |
| Между площадками | на скольких площадках лежит копия объекта | составом доменов отказа: компонент `dc` в `failure_domain` |

Кодирование не пересекает границу площадки. Внутри площадки объект
кодируется по `k+m` устройствам; между площадками объект реплицируется целиком,
и каждая площадка хранит собственную, независимо закодированную копию. Столбец
Столбец `placements` строки объекта содержит отображение площадки в группу размещения, и
этот список выступает единицей межплощадочной избыточности.

Репликация между площадками не заменяет кодирование, а надстраивается над ним:
одна площадка — кодирование; несколько площадок — кодирование внутри каждой и
репликация между ними.

Ограничение связано с пропускной способностью межплощадочного канала.
При кодировании через границу площадки каждое чтение при потере частей
передавало бы по каналу `k` частей, каждое восстановление — объём в `k` раз
больше утраченного, а каждая запись ожидала бы самое медленное из `k+m`
соединений. Канал между
площадками имеет ограниченную пропускную способность, а кодирование увеличивает
объём передаваемых по нему данных.

Межплощадочная репликация асинхронна: успешный ответ на запись подтверждает
сохранение на местной площадке, но не ожидает создания копий на остальных.
Пока в `placements` есть только одна запись `live`, безвозвратная потеря этой
площадки приводит к недоступности содержимого, даже если его метаданные
сохранились в Raft. Перед плановым выводом площадки дождитесь пустой очереди
`s3r_t<N>_siterepl` соответствующего арендатора и проверьте наличие записей
`live` на других площадках.
Размещение голосующих реплик Picodata и сохранение кворума Raft настраиваются
отдельно от размещения содержимого объектов.

### Классы хранения внутри площадки {: #klassy_hraneniya_vnutri_ploschadki }

| Размер объекта | Класс | Размещение |
| --- | --- | --- |
| до `inline_max` включительно | `inline` | строка метаданных; избыточность обеспечивает Picodata |
| свыше `inline_max` | `ec` | `k` частей данных и `m` частей чётности на блок |
| свыше `inline_max`, если кодировать нечем | `replica` | `R` полных копий на `R` различных дисках |

Размер объекта решает единственный вопрос: попадёт содержимое в строку
метаданных или в хранилище блоков. Ниже `inline_max` кодирование не
применяется — содержимое лежит в строке, и избыточность обеспечивает Picodata.
Всё, что дошло до хранилища блоков, кодируется.

Класс `replica` остаётся запасным вариантом и выбирается там, где группу
кодирования собрать не из чего: ни один диск не объявил поддомена отказа. Отказ
в записи вместо этого лишил бы установку без поддоменов возможности хранить
что-либо крупнее `inline_max`.

Второй размерной границы — между репликацией и кодированием внутри хранилища
блоков — нет. Прежде она была: объект меньше блока реплицировался, больше —
кодировался. Правило отменено по двум причинам.

Первая относится к разделению обязанностей. Репликация содержимого внутри одной
площадки повторяет то, что СУБД уже выполняет: объект, для которого репликация
подходит по размеру, помещается в строку метаданных, а строки Picodata
реплицирует сама. Хранилищу блоков остаётся кодирование.

Вторая связана с расходом места. Каждая запись в хранилище блоков выравнивается
до 4 КиБ, что существенно для малых объектов. Для формы `k=8,m=4` в сравнении
с тремя копиями:

| Объект | `ec` 8+4 | 3 копии | Меньший объём |
| --- | --- | --- | --- |
| 5 КиБ | 48 КиБ | 24 КиБ | копии |
| 8 КиБ | 48 КиБ | 36 КиБ | копии |
| 16 КиБ | 48 КиБ | 60 КиБ | `ec` |
| 64 КиБ | 144 КиБ | 204 КиБ | `ec` |
| 1 МиБ | 1584 КиБ | 3084 КиБ | `ec` |

Диапазон, в котором репликация занимает меньше места, — от 4 до примерно
10 КиБ, то есть
`inline_max` и немного выше. Чтение требует больше операций ввода-вывода:
`k` обращений к дискам против одного. Для этого диапазона используется параметр
`inline_max`, задающий
границу хранения содержимого в оперативной памяти узла, а не второй механизм
избыточности внутри хранилища блоков.

### Классы хранения S3 и ярусы {: #klassy_hraneniya_s3_i_yarusy }

Класс хранения S3 (`x-amz-storage-class`) задаёт клиент, а ярус хранения
(`tier=` на диске) — администратор. Соответствие задаётся таблицей
`s3r_storage.tiers`: каждому ярусу соответствует один класс, а каждому классу —
один ярус. Список упорядочен от наиболее частого к наиболее редкому доступу.

```yaml
s3r_storage:
  tiers:
    - { name: standard, class: STANDARD }
    - { name: cold, class: STANDARD_IA }
  erasure:
    - { k: 4, m: 2, block_bytes: 2097152 }
    - { k: 8, m: 2, block_bytes: 4194304, tier: cold }
```

Объект создаётся в ярусе, соответствующем его классу. `PutObject`, `CopyObject` и
`CreateMultipartUpload` принимают `x-amz-storage-class`; без заголовка класс —
`STANDARD`, и у `CopyObject` класс назначения не наследуется от источника.
Части составной загрузки наследуют класс загрузки. Класс возвращается в ответах
`HeadObject`, `GetObject`, `GetObjectAttributes` и операций перечисления.

Класс, которого нет в карте, отвергается: `400 InvalidStorageClass`. Кластер с
единственным ярусом принимает любое имя класса AWS и хранит его как метку. Ярус
`standard` с классом `STANDARD` подразумевается, если карта не называет ни его,
ни класс `STANDARD`.

Привязка постоянна: строки объектов несут класс, а размещения называют группы
одного яруса, и изменение конфигурации не переносит данные. Команда
`ALTER PLUGIN`, которая пытается связать уже известный класс с другим ярусом
или ярус с другим классом, может завершиться успешно: Picodata не предоставляет
плагину отдельной проверки до сохранения конфигурации. Сервис регистрирует
ошибку с обеими привязками в журнале, игнорирует несовместимую карту и
продолжает использовать прежнюю. После изменения проверьте журнал и
действующую карту в таблице `s3r_tier`.

Объекты не крупнее `inline_max` хранятся в строке метаданных при любом классе;
класс у них — только метка. Если в площадке нет группы яруса, запись объекта
этого класса отвергается с `503`, именем класса, яруса и площадки, а не
размещается на дисках яруса с более частым доступом; отказы считает
`s3r_class_refused_total{class}`. Задание перехода в недоступный ярус остаётся
в очереди и выполняется после того, как администратор добавит диски и появится
подходящая группа.

Два правила, по которым строят кластер с ярусами: ярусу нужны диски не менее чем
в `k+m` доменах отказа на каждой площадке, иначе его формы не образуют групп, а
диски другого яруса не заимствуются; ярус на меньшинстве узлов сосредотачивает
свой трафик и восстановление на их сетевых интерфейсах. Подробнее — в главе
«Администрирование».

### Группы размещения {: #gruppy_razmescheniya }

Группа размещения представляет собой упорядоченный набор дисков в пределах одной
площадки и геометрию записи на них. Часть с номером `i` каждого блока,
размещённого в группе, хранится на `i`-м диске набора.

Группа перечисляет диски. Инстанс с четырьмя дисками, потерявший один из них,
сохраняет прежний репликасет и теряет копию данных; запись, перечисляющая
репликасеты, показывала бы исправное размещение для неполных данных.

Группы формируются автоматически. Менеджер топологии периодически сверяет состав
кластера и создаёт группу, когда объявленную форму есть на чём разместить.

Реплицированная группа не создаётся, пока на площадке есть работоспособная
группа кодирования: запись к ней не обратится, а диски она заняла бы.

Одновременно поддерживается не более одной незанятой группы каждой формы.
Группа размещения постоянна: объекты записываются против её конкретного состава.
Ёмкость выделяется по мере заполнения кластера — новая группа создаётся после
того, как все прежние группы этой формы приняли данные.

Отсюда следует порядок ввода в эксплуатацию: форма кодирования объявляется до
начала заполнения кластера, иначе свободных дисков под неё не остаётся.

#### Выбор формы кодирования {: #vybor_formy_kodirovaniya }

Число частей ограничено сверху величиной, до которой на практике не доходит:
`k + m` до 32768. Ограничение, с которым приходится считаться, другое — форма
`k + m` требует `k + m` различных доменов отказа, потому что части одного блока
не кладутся в один домен.

Испытаниями охвачены формы от 2+2 до 12+4. Более широкие схемы (17+3, 61+3)
кодировщик принимает, но на стенде они не проверялись.

Избыточность формы `k+m` равна `(k + m) / k`. Полезная ёмкость пула равна сырой,
делённой на эту величину: 8+4 даёт 1.5, то есть две трети сырой ёмкости
теряются; 12+3 даёт 1.25; 10+2 — 1.2. Форму следует выбирать вместе с составом
дисков, а не после него.

Форма, под которой уже есть данные, не изменяется: изменение отклоняется при
загрузке конфигурации. Геометрия хранится в строке группы размещения, а не в
строке объекта, и одинакова для всех записанных в группу блоков.

#### Контроль целостности {: #kontrol_celostnosti }

Каждая часть хранится вместе с контрольными суммами: заголовок покрыт своей
суммой, массив сумм — суммой в заголовке, каждый участок содержимого — своей
записью в массиве. Проверка выполняется при каждом чтении, а не только фоновым
процессом: часть, не сошедшаяся с контрольной суммой, не отдаётся, а
восстанавливается по остальным частям блока.

Проверка выполняется двумя фоновыми процессами. Процесс `orphan` последовательно
обходит запечатанные экстенты, проверяет контрольные суммы записей и удаляет
фрагменты, на которые не ссылаются метаданные. Возраст экстента, допустимый для
такого обхода, задаётся `orphan_grace_s`.

Процесс `scrub` проверяет избыточное кодирование: повторно вычисляет фрагменты
чётности по `k` фрагментам данных и сравнивает результат с сохранёнными
`m` фрагментами. Параметр `scrub_staleness_s` задаёт наибольший допустимый
возраст полной проверки группы размещения, а не период запуска процесса.

### Межплощадочная репликация {: #mezhploschadochnaya_replikaciya }

Запись фиксируется на местной площадке, остальные площадки получают копию
асинхронно. Пространство имён едино для кластера, поэтому объект существует с
момента фиксации своей строки; читатель на площадке, куда копия ещё не пришла,
запрашивает её по каналу и получает содержимое, а не `NoSuchKey`.

Блок передаётся между площадками **в исходном виде и однократно**; принимающая
площадка кодирует его в собственные `k+m` частей средствами своей группы
размещения. Передача `k+m` готовых частей израсходовала бы на канал между
площадками ровно тот объём, ради экономии которого кодирование и применяется.

Столбец `placements` содержит по записи на каждую площадку:

| Состояние | Значение |
| --- | --- |
| `live` | копия записана и читается |
| `pending` | копия ещё не записана |
| `lost` | площадка или её устройства утрачены |

Досылку ведёт фоновый процесс `siterepl`, сверку содержимого площадок между
собой — `siterepl-reconcile`.

#### Репликация — свойство кластера, а не арендатора {: #replikaciya_svoistvo_klastera_a_ne_arendatora }

Набор площадок задаётся при развёртывании кластера и действует на весь кластер.
Включить или отключить межплощадочную репликацию для отдельного арендатора
нельзя: все арендаторы следуют одному набору площадок, и объект любого из них
получает копию на каждой из них.

Это не ограничение реализации, а следствие устройства: площадка — это свойство
группы размещения, а группы размещения общие для кластера. Арендатор — это
пространство имён (свой набор таблиц), а не собственный набор оборудования.
Поэтому и вопрос «что делать с уже созданными копиями, если арендатор
отключит репликацию» не возникает: отключить её для арендатора не предлагается.

Арендаторам с разными требованиями к географии данных нужны разные кластеры.

## Изоляция арендаторов {: #izolyaciya_arendatorov }

Один кластер обслуживает несколько арендаторов (tenant), и каждый из них —
отдельное пространство имён: свои таблицы бакетов, объектов и учётных данных
(`s3r_t<N>_bucket`, `s3r_t<N>_object`, `s3r_t<N>_credential` и прочие). Изоляция
здесь структурная, а не предикат поверх общих таблиц: запрос не может обратиться
к чужим данным, потому что не может назвать чужую таблицу.

Арендатор с номером 0 (имя `default`) — арендатор по умолчанию. Кластер, в котором
не создан ни один другой арендатор, целиком принадлежит ему, и всё описанное в
остальных главах происходит внутри него.

### Создание и удаление арендатора {: #sozdanie_i_udalenie_arendatora }

Управление выполняется командами SQL над глобальной таблицей `s3r_tenant`,
доступной роли `s3r_superuser` (см. «Ролевая модель арендаторов»).
Для создания добавьте строку со `state = 'creating'`. Изменение таблицы
запускает процесс согласования, который создаёт таблицы нового арендатора и
переводит `state` в `active`. Удаление выполняется через состояние `draining`.
Обслуживается
только арендатор в состоянии `active` — `creating` ещё не готов, а `draining` и
`dropped` перестают аутентифицировать, чем удаление арендатора отзывает его
доступ той же записью Raft, что его пометила.

Два арендатора принадлежат самому кластеру и удалению не подлежат: арендатор 0
(пространство имён по умолчанию) и системный арендатор с последним идентификатором
(4294967295), в таблицах которого хранится то, что не принадлежит ни одному
пользовательскому арендатору — объекты дедупликации. У системного арендатора нет ни
домена, ни ключей; выставленный ему `draining` сверяющий процесс возвращает в `active`.

Дедупликация включается на арендатора и по умолчанию выключена:
`UPDATE s3r_tenant SET dedup = true WHERE tenant_id = ...`. Пока она выключена, запись
не оставляет за собой ничего — ни заметки в очереди, ни строки в индексе хэшей; включение
действует на записи с этого момента, ранее записанное в индекс не попадает. Замысел и
границы описаны в `doc/dev/DEDUP.md`.

```sql
INSERT INTO s3r_tenant (tenant_id, name, domain, state, created_at)
VALUES (1, 'acme', 'acme.s3.example.com', 'creating', CURRENT_TIMESTAMP);
```

Ключевые столбцы: `tenant_id` — малое стабильное число, которое несут имена таблиц
и заголовки фрагментов блоков (переименование арендатора не меняет эти данные);
`name` — уникальное имя, которое вводит оператор; `domain` — FQDN, на котором
арендатор отвечает (см. «Адресация»), или `NULL`; `cert_chain`, `cert_key`,
`mtls_ca` — материал TLS (см. «Сертификат арендатора и выбор по SNI»); `state` —
одно из `creating | active | draining | dropped`.

#### Поля описания оборудования {: #polya_opisaniya_oborudovaniya }

Столбец `appliance` хранит поля, которые спецификация помещает на арендатора и
которые описывают его развёртывание на программно-аппаратном комплексе:
`ns_count`, `os_count`, `s3gw_count`, `storage_lvl` и `failure_domain`.
Управляющий интерфейс принимает их при создании и изменении арендатора,
возвращает в том же виде — и **ни на что их не применяет**.

Соответствия у них нет и быть не может: арендаторы s3r делят один кластер и один
набор инстансов. Сервисы `s3r_api`, `s3r_meta` и `s3r_storage` размещаются на
одном тире, поэтому любое «настоящее» число, выведенное из кластера, оказалось бы
одним и тем же числом трижды. Поля сохраняются, чтобы клиент, который их задал,
прочитал их обратно; молча отбросить присланное поле — единственный заведомо
худший ответ.

`redundancy_lvl` — исключение: он проверяется. Значение задаётся строкой `k+m`
(например, `2+2`) из числа тех, что перечисляет
`GET /v2/cluster/tiers-redundancy-levels`; уровень, которого в кластере нет,
отклоняется при создании арендатора с ответом `400`, называющим доступные. Проверка
выполняется потому, что иначе арендатор создался бы успешно, а отказ пришёл бы при
первой записи — далеко от вызова, который его вызвал. Размещение к этому уровню
**не привязывается**: объекты по-прежнему попадают туда, куда их направляет класс
хранения.

### Разрешение арендатора запроса {: #razreshenie_arendatora_zaprosa }

У запроса два возможных признака арендатора, и решение принимается по ним обоим:

- **`Host`** — FQDN арендатора из `s3r_tenant.domain` называет арендатора ещё до
  разбора запроса;
- **ключ доступа** — `s3r_credential.tenant_id` содержит идентификатор
  арендатора, которому принадлежит ключ.

Если запрос содержит оба признака, они обязаны **совпасть**. Рассогласование —
ключ одного арендатора, пришедший на FQDN другого, — отклоняется (403), а не
разрешается в пользу одного из них: молчаливый выбор был бы тем самым способом,
которым обслуживается межарендное чтение. Запрос без обоих признаков относится к
арендатору 0.

### Адресация арендатора {: #adresaciya_arendatora }

Арендатор с заданным `domain` отвечает по своему FQDN в обеих формах:

```
# Стиль пути: FQDN арендатора, бакет и ключ — в пути
https://acme.s3.example.com/documents/report.pdf

# Виртуально-хостовая: бакет — меткой перед FQDN арендатора
https://documents.acme.s3.example.com/report.pdf
```

Точка входа по умолчанию (обращение по IP или по имени узла, без FQDN арендатора)
работает в стиле пути и разрешается в арендатора ключа — по умолчанию арендатора 0.
Хост, похожий на схему арендатора, но не принадлежащий ни одному, **отклоняется**,
а не обслуживается арендатором по умолчанию: обслужить его было бы межарендной
утечкой под видом удобства.

Собственный сертификат и обязательный клиентский сертификат арендатора описаны
в разделе «Сертификат арендатора и выбор по SNI»; роли `s3r_superuser` и
`s3r_tenant_admin_<id>` — в разделе «Ролевая модель арендаторов».

## Работа с хранилищем {: #rabota_s_hranilischem }

### Учётные данные {: #uchetnye_dannye }

Ключ доступа S3 сопоставляется с пользователем Picodata. Права и записи аудита
для операций S3 разбираются штатными средствами СУБД; отдельная система
управления доступом не применяется.

Ключ действителен, пока существует названный им пользователь.

```
CREATE USER "alice" WITH PASSWORD '...' USING chap-sha1;

ALTER PLUGIN s3r 2.0.0 SET s3r_api.credentials =
  '[{"access_key":"AKIA...","secret_key":"...","pico_user":"alice"}]';
```

Параметр `credentials` заполняет учётные данные только начального арендатора с
`tenant_id = 0`. Ключи остальных арендаторов выдаются через административный
API арендатора. При `backend = picodata` пустой список не переводит конечную
точку в режим без аутентификации: продолжают действовать строки таблицы
`s3r_credential`, а неизвестные ключи отклоняются. Обращение без подписи
возможно только когда это разрешено списком управления доступом или политикой
бакета.

Отладочный `backend = fs` не использует таблицу Picodata: при пустом списке
`credentials` только этот режим обслуживает запросы без аутентификации.

Без параметра `pico_user` пользователем становится сам ключ доступа.
Пользователь с таким именем, как правило, отсутствует, и подписанные запросы
отклоняются с сообщением о неизвестном ключе доступа.

Просмотр действующих ключей:

```
SELECT access_key, pico_user, state FROM s3r_credential;
```

Роли создаются миграциями плагина; см. «Ролевая модель арендаторов».

#### Несколько ключей на пользователя и их смена {: #neskolko_klyuchei_na_polzovatelya_i_ih_smena }

Одному пользователю можно выдать несколько пар ключей: в списке
`credentials` заводится вторая запись с тем же `pico_user`. Смена ключа без
перерыва в обслуживании выполняется в три шага: выдать новую пару, перевести на
неё приложение, удалить старую запись.

```
ALTER PLUGIN s3r 2.0.0 SET s3r_api.credentials =
  '[{"access_key":"AKIAOLD...","secret_key":"...","pico_user":"alice"},
    {"access_key":"AKIANEW...","secret_key":"...","pico_user":"alice"}]';
```

Ключ отзывается удалением его записи из списка. Чтобы отозвать все права
пользователя, удалите или заблокируйте самого пользователя средствами SQL: ключ,
названный несуществующим пользователем, к работе не допускается.

Пароль служебной учётной записи меняется штатной командой Picodata:

```
ALTER USER "alice" WITH PASSWORD '...';
```

Срок действия ключа доступа не задаётся; ключ действует, пока существуют
запись о нём и названный ею пользователь.

### Адресация {: #adresaciya }

Используется адресация в стиле пути: `http://узел:8000/бакет/ключ`. Клиент
настраивается параметром `addressing_style: path` либо флагом
`force_path_style`. На точке входа по умолчанию (по IP или имени узла) это
единственная поддерживаемая форма.

Виртуально-хостовая адресация именем бакета в имени узла (`бакет.домен`)
поддерживается для арендатора, которому задан FQDN: он отвечает и по своему FQDN,
и в форме `бакет.FQDN`. Это требует записи DNS с подстановочным знаком на домен
арендатора. См. главу «Изоляция арендаторов».

### Совместимость с клиентами {: #sovmestimost_s_klientami }

Работает любой клиент, говорящий по протоколу S3 с подписью версии 4:
`aws-sdk-go`, `aws-sdk-java`, `boto3`, `aws-sdk-cpp`, `aws-cli`, `s3cmd`,
`rclone`, `mc`. Своего протокола плагин не вводит; в настройках клиента задаются
адрес конечной точки, ключ доступа и адресация в стиле пути.

### Ключи объектов и логическая структура {: #klyuchi_obektov_i_logicheskaya_struktura }

Ключ — произвольная строка. Символ `/` в ключе образует логическую структуру
каталогов: перечисление с разделителем `/` возвращает объекты текущего уровня в
`Contents`, а вложенные уровни — в `CommonPrefixes`.

```
aws s3api list-objects-v2 --bucket documents --prefix проекты/ --delimiter /
```

Строки каталогов создаются при записи объекта и удаляются фоновым процессом,
когда каталог становится пустым. Поэтому перечисление уровня не требует обхода
всех ключей бакета.

Префикс — это и единица разграничения доступа: политика бакета с ресурсом
`arn:aws:s3:::documents/проекты/*` действует на весь подкаталог, в том числе при
массовом удалении, где право проверяется по каждому ключу отдельно.

### Метаданные объекта {: #metadannye_obekta }

Пользовательские метаданные передаются заголовками `x-amz-meta-*` и
возвращаются `GET` и `HEAD`. Сохраняются также тип содержимого и связанные с ним
заголовки: `Content-Type`, `Content-Encoding`, `Content-Disposition`,
`Content-Language`, `Cache-Control`, `Expires`.

```
aws s3api put-object --bucket documents --key report.pdf --body report.pdf \
    --content-type application/pdf \
    --metadata 'author=alice,department=finance'

aws s3api head-object --bucket documents --key report.pdf
```

При копировании метаданные по умолчанию переносятся; `--metadata-directive
REPLACE` заменяет их значениями из запроса.

### Примеры обращения {: #primery_obrascheniya }

Настройка профиля и работа через AWS CLI:

```
aws configure set aws_access_key_id AKIA...
aws configure set aws_secret_access_key ...

aws --endpoint-url http://node1:8000 s3 mb s3://documents
aws --endpoint-url http://node1:8000 s3 cp report.pdf s3://documents/
aws --endpoint-url http://node1:8000 s3 ls s3://documents/
aws --endpoint-url http://node1:8000 s3 rm s3://documents/report.pdf
```

Обращение из Python:

```
import boto3
from botocore.config import Config

s3 = boto3.client(
    "s3",
    endpoint_url="http://node1:8000",
    aws_access_key_id="AKIA...",
    aws_secret_access_key="...",
    config=Config(s3={"addressing_style": "path"}),
)
s3.put_object(Bucket="documents", Key="report.pdf", Body=data)
```

Далее в примерах вместо `aws --endpoint-url http://node1:8000` пишется `aws`.

### Права доступа к объектам {: #prava_dostupa_k_obektam }

Владельцем объекта становится загрузивший его пользователь. Владелец бакета прав
на объект не получает; такое поведение определено спецификацией S3.

Поддерживаются готовые наборы прав (`private`, `public-read`,
`public-read-write`, `authenticated-read`, `bucket-owner-read`,
`bucket-owner-full-control`) и явные разрешения для отдельных пользователей и
для групп «все пользователи» и «все аутентифицированные пользователи». По
умолчанию объект доступен владельцу и документа прав не хранит, поэтому его
чтение обходится без разбора такого документа.

## Справочник операций {: #spravochnik_operacii }

Глава описывает операции, обращение к которым не сводится к одному вызову.
Примеры приведены для AWS CLI; тот же порядок действий воспроизводится любым
SDK, работающим по протоколу S3.

### Чтение диапазона {: #chtenie_diapazona }

Поддерживаются диапазоны вида `bytes=начало-конец`, `bytes=начало-` и
`bytes=-длина`. Читаются только те части блоков, в которые попадает диапазон.

```
aws s3api get-object --bucket documents --key big.bin \
    --range bytes=1048576-2097151 part.bin
```

Для объекта, собранного составной загрузкой, диапазон можно задать номером
части:

```
aws s3api get-object --bucket documents --key big.bin --part-number 3 part3.bin
```

Ответ содержит `Content-Range`, а для запроса по номеру части — ещё и
`x-amz-mp-parts-count`.

### Составная загрузка {: #sostavnaya_zagruzka }

Объект передаётся частями и собирается на стороне хранилища. Номера частей —
от 1 до 10000. Все части, кроме последней, должны быть не менее 5 МиБ;
нарушение возвращает `EntityTooSmall` при завершении загрузки.

Обычно составная загрузка выполняется клиентом автоматически: `aws s3 cp`
переходит на неё для файлов больше порога `multipart_threshold`. Явная
последовательность:

```
# 1. Начать загрузку
aws s3api create-multipart-upload --bucket documents --key big.bin
# { "UploadId": "0197f2c1..." }

# 2. Передать части
aws s3api upload-part --bucket documents --key big.bin \
    --upload-id 0197f2c1... --part-number 1 --body part1.bin
# { "ETag": "\"9b2c...\"" }

# 3. Собрать объект
aws s3api complete-multipart-upload --bucket documents --key big.bin \
    --upload-id 0197f2c1... \
    --multipart-upload '{"Parts":[{"PartNumber":1,"ETag":"\"9b2c...\""}]}'
```

`ETag` собранного объекта имеет вид `"<md5 склеенных md5 частей>-<число
частей>"` и намеренно не совпадает с MD5 содержимого — так же устроен Amazon S3.

Незавершённые загрузки видны и отменяются:

```
aws s3api list-multipart-uploads --bucket documents
aws s3api list-parts --bucket documents --key big.bin --upload-id 0197f2c1...
aws s3api abort-multipart-upload --bucket documents --key big.bin \
    --upload-id 0197f2c1...
```

Часть можно взять из существующего объекта, а не передавать по сети:

```
aws s3api upload-part-copy --bucket documents --key merged.bin \
    --upload-id 0197f2c1... --part-number 2 \
    --copy-source documents/source.bin --copy-source-range bytes=0-5242879
```

Загрузка, с которой не выполнялись операции дольше `mpu_abandon_after_s`, отменяется
фоновым процессом; её части освобождаются. Тот же результат даёт правило
жизненного цикла `AbortIncompleteMultipartUpload`.

`CompleteMultipartUpload`, как и `PutObject`, принимает условные заголовки
`If-Match` и `If-None-Match`: проверка выполняется в момент публикации
собранного объекта.

### Контрольные суммы S3 {: #kontrolnye_summy_s3 }

При записи вычисляются контрольные суммы SHA-256 и CRC64/NVME. Клиент может
передать `ChecksumSHA256` или `ChecksumCRC64NVME` в `PutObject` и `UploadPart`;
значение кодируется в Base64. Несовпадение с принятым содержимым возвращает
`400 BadDigest`, и запись не публикуется.

```
sha256=$(openssl dgst -sha256 -binary report.pdf | base64 -w0)
aws s3api put-object --bucket documents --key report.pdf \
    --body report.pdf --checksum-sha256 "$sha256"

aws s3api head-object --bucket documents --key report.pdf \
    --checksum-mode ENABLED
aws s3api get-object-attributes --bucket documents --key report.pdf \
    --object-attributes Checksum
```

`GetObject` и `HeadObject` возвращают контрольные суммы только при
`ChecksumMode=ENABLED`. Для диапазонного чтения и чтения по номеру части
контрольная сумма целого объекта не возвращается, поскольку ответ содержит
лишь часть его байтов.

Для объекта из нескольких частей возвращается составная контрольная сумма
SHA-256: SHA-256 от последовательности двоичных SHA-256 всех частей,
закодированный в Base64, и суффикс `-<число частей>`. Составная CRC64/NVME
сейчас не возвращается. `GetObjectAttributes` с атрибутом `Checksum` выдаёт ту
же сумму без чтения содержимого.

### Копирование {: #kopirovanie }

Копия создаётся на стороне сервера: содержимое объекта по сети не передаётся.

```
aws s3api copy-object --bucket archive --key report-2026.pdf \
    --copy-source documents/report.pdf
```

Источником может быть конкретная версия:

```
aws s3api copy-object --bucket archive --key report-old.pdf \
    --copy-source 'documents/report.pdf?versionId=0000019874f3a1c2'
```

Метаданные по умолчанию копируются (`--metadata-directive COPY`). Значение
`REPLACE` заменяет пользовательские метаданные и тип содержимого значениями из
запроса. Так же ведут себя `--tagging-directive` для тегов и
`--x-amz-copy-source-if-match` и родственные заголовки для условного
копирования.

Заголовок `x-amz-expected-bucket-owner` защищает операцию с бакетом,
переизданным другому владельцу: при несовпадении сервер возвращает
`AccessDenied`. В s3r ожидаемое значение — имя пользователя Picodata,
владеющего бакетом, а не идентификатор учётной записи AWS. Для источника
`CopyObject` и `UploadPartCopy` применяется
`x-amz-source-expected-bucket-owner`.

Копирование объекта в самого себя допускается только вместе с
`--metadata-directive REPLACE`; иначе возвращается `InvalidRequest`.

### Условная запись {: #uslovnaya_zapis }

`PutObject` принимает два условных заголовка. `If-None-Match: *` записывает
объект, только если ключа ещё нет. `If-Match: "<etag>"` записывает его, только
если текущее содержимое имеет указанный `ETag`. На этих двух проверках строятся
взаимное исключение и оптимистическое обновление без внешнего координатора.

```
# Создать, только если ключа нет
aws s3api put-object --bucket documents --key lock --body /dev/null \
    --if-none-match '*'
# Второй такой же вызов вернёт PreconditionFailed (412)

# Обновить, только если содержимое не менялось
aws s3api put-object --bucket documents --key state.json --body new.json \
    --if-match '"d41d8cd98f00b204e9800998ecf8427e"'
```

`If-Match` на отсутствующем ключе возвращает `NoSuchKey` (404), а не 412.

Условные заголовки `If-Match`, `If-None-Match`, `If-Modified-Since` и
`If-Unmodified-Since` поддержаны и на чтении.

### Версионирование {: #versionirovanie }

Версионирование включается на бакете. Выключить его нельзя, можно только
приостановить.

```
aws s3api put-bucket-versioning --bucket documents \
    --versioning-configuration Status=Enabled
aws s3api get-bucket-versioning --bucket documents
```

Каждая запись создаёт новую версию с собственным `VersionId`; чтение без
указания версии возвращает последнюю. Удаление без указания версии не удаляет
данные, а создаёт маркер удаления.

```
aws s3api list-object-versions --bucket documents --prefix report

# Прочитать конкретную версию
aws s3api get-object --bucket documents --key report.pdf \
    --version-id 0000019874f3a1c2 old.pdf

# Удалить конкретную версию — данные исчезают
aws s3api delete-object --bucket documents --key report.pdf \
    --version-id 0000019874f3a1c2
```

Ответ на удаление содержит `x-amz-delete-marker: true` и `x-amz-version-id`
созданного маркера. Чтение объекта, поверх которого стоит маркер удаления,
возвращает `NoSuchKey` (404), а `HEAD` — 405 с заголовком
`x-amz-delete-marker`.

Состояние `Suspended` останавливает создание новых версий: запись заменяет
«нулевую» версию, а прежние версии сохраняются и остаются доступны по
`VersionId`.

### Теги {: #tegi }

Теги задаются на бакете и на объекте, до 10 тегов в обоих случаях.

```
aws s3api put-object-tagging --bucket documents --key report.pdf \
    --tagging 'TagSet=[{Key=class,Value=confidential}]'
aws s3api get-object-tagging --bucket documents --key report.pdf
aws s3api delete-object-tagging --bucket documents --key report.pdf
```

Теги объекта используются правилами жизненного цикла и условиями политики
(`s3:ExistingObjectTag/<ключ>`, `s3:RequestObjectTag/<ключ>`).

### Списки управления доступом {: #spiski_upravleniya_dostupom }

```
aws s3api put-object-acl --bucket documents --key report.pdf --acl public-read
aws s3api get-object-acl --bucket documents --key report.pdf

# Явное разрешение отдельному пользователю
aws s3api put-object-acl --bucket documents --key report.pdf \
    --grant-read 'id=bob'
```

Идентификатором получателя прав служит имя пользователя Picodata. Группы
задаются URI `http://acs.amazonaws.com/groups/global/AllUsers` и
`.../AuthenticatedUsers`.

### Политика бакета {: #politika_baketa }

Политика — второй источник разрешений, независимый от списков управления
доступом. Порядок разбора: явный запрет побеждает всегда; при отсутствии
запрета разрешение даёт либо политика, либо список управления доступом.

```
cat > policy.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam:::user/bob"},
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::documents/public/*"]
    },
    {
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::documents/secret/*"
    }
  ]
}
EOF

aws s3api put-bucket-policy --bucket documents --policy file://policy.json
aws s3api get-bucket-policy --bucket documents
aws s3api get-bucket-policy-status --bucket documents
aws s3api delete-bucket-policy --bucket documents
```

Субъект доступа задаётся именем пользователя Picodata. Распознаётся имя без
ARN и ARN вида `arn:aws:iam::<учётная-запись>:user/<имя>`; значимой является
последняя составляющая. `"Principal": "*"` разрешает анонимное обращение.

Поддержаны `Action` и `NotAction`, `Resource` и `NotResource` с подстановочными
знаками `*` и `?`, а также условия с операторами `StringEquals`,
`StringNotEquals`, `StringLike`, `StringNotLike` и суффиксом `IfExists`.
Доступные ключи условий: `s3:prefix`, `s3:ExistingObjectTag/<ключ>`,
`s3:RequestObjectTag/<ключ>` и заголовки запроса вида `s3:x-amz-acl`,
`s3:x-amz-copy-source`, `s3:x-amz-metadata-directive`.

Неизвестный оператор условия трактуется в сторону отказа. Инструкция
`Allow` с оператором, который плагин не реализует, доступа не даёт; инструкция
`Deny` с таким оператором запрещает.

### Совместное использование ресурсов между источниками (CORS) {: #sovmestnoe_ispolzovanie_resursov_mezhdu_istochnikami_cors }

Правила определяют, каким источникам браузер разрешит обратиться к бакету.
Без них браузер отклоняет ответ до того, как его увидит приложение.

```
cat > cors.json <<'EOF'
{
  "CORSRules": [
    {
      "AllowedMethods": ["GET", "PUT"],
      "AllowedOrigins": ["https://app.example.com", "https://*.example.com"],
      "AllowedHeaders": ["x-amz-*"],
      "ExposeHeaders": ["ETag", "x-amz-request-id"],
      "MaxAgeSeconds": 3000
    }
  ]
}
EOF

aws s3api put-bucket-cors --bucket documents --cors-configuration file://cors.json
aws s3api get-bucket-cors --bucket documents
aws s3api delete-bucket-cors --bucket documents
```

Разрешены методы `GET`, `PUT`, `POST`, `DELETE` и `HEAD`, не более 100 правил.
Документ проверяется при записи: неизвестный метод или больше одного символа
`*` в образце отклоняются.

Образец источника содержит не более одного символа `*` и сопоставляется
целиком. Образец `*suffix` совпадает с `foo.suffix` и не совпадает с
`foo.suffix.get`; `start*end` совпадает с `startend` и `start12end`, но не с
`0start12end`. Одиночный `*` разрешает любой источник, и в ответе возвращается
именно `*`, а не имя источника, — такой ответ браузер кэширует для всех
источников сразу.

Применяется первое правило, у которого совпали источник, метод **и** все
заголовки из `Access-Control-Request-Headers`. Правило, не перечисляющее
запрошенный заголовок, не считается совпавшим, и предварительный запрос
получает `403`.

Предварительный запрос обслуживается без подписи (браузер её не присылает) и
не обращается к объекту: `OPTIONS` для несуществующего ключа возвращает `200`.
Запрос без заголовка `Origin` или без `Access-Control-Request-Method`
возвращает `400`.

Заголовки `Access-Control-*` добавляются и к обычным ответам, включая ответы с
ошибкой: браузер не покажет приложению даже код ошибки, если их нет.

### Блокировка публичного доступа {: #blokirovka_publichnogo_dostupa }

Четыре флага на бакете, которые действуют поверх списков управления доступом и
политики: что бы те ни разрешали, флаг сильнее.

```
aws s3api put-public-access-block --bucket documents \
    --public-access-block-configuration \
    'BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true'

aws s3api get-public-access-block --bucket documents
aws s3api delete-public-access-block --bucket documents
```

| Флаг | Действие |
| --- | --- |
| `BlockPublicAcls` | отклоняет запись списка прав, дающего доступ группам «все пользователи» и «все аутентифицированные пользователи» |
| `IgnorePublicAcls` | сохраняет такие разрешения и не учитывает их при проверке |
| `BlockPublicPolicy` | отклоняет запись политики с `"Principal": "*"` без условий |
| `RestrictPublicBuckets` | не применяет публичную политику к запросам без подписи |

Различие первых двух флагов существенно при разборе инцидента.
`BlockPublicAcls` не даёт разрешению появиться; `IgnorePublicAcls` оставляет его
в документе и перестаёт учитывать, поэтому `GetBucketAcl` и `GetObjectAcl`
по-прежнему показывают его. Снятие флага возвращает разрешение в силу.

Запрос `GetPublicAccessBlock` на бакете, для которого настройка не задавалась,
возвращает `NoSuchPublicAccessBlockConfiguration` (404). Настройка из четырёх
значений `false` — это заданная настройка, и она читается обратно.
`PutPublicAccessBlock` заменяет её целиком: опущенный флаг означает `false`, а
не «оставить как было».

### Правила жизненного цикла {: #pravila_zhiznennogo_cikla }

Правило описывает, что и когда удалить.

```
cat > lifecycle.json <<'EOF'
{
  "Rules": [
    {
      "ID": "expire-logs",
      "Status": "Enabled",
      "Filter": {"Prefix": "logs/"},
      "Expiration": {"Days": 30}
    },
    {
      "ID": "tidy-versions",
      "Status": "Enabled",
      "Filter": {},
      "NoncurrentVersionExpiration": {"NoncurrentDays": 7},
      "AbortIncompleteMultipartUpload": {"DaysAfterInitiation": 1}
    },
    {
      "ID": "large-temp",
      "Status": "Enabled",
      "Filter": {
        "And": {
          "Prefix": "tmp/",
          "ObjectSizeGreaterThan": 10485760,
          "Tags": [{"Key": "class", "Value": "scratch"}]
        }
      },
      "Expiration": {"Days": 1}
    }
  ]
}
EOF

aws s3api put-bucket-lifecycle-configuration --bucket documents \
    --lifecycle-configuration file://lifecycle.json
aws s3api get-bucket-lifecycle-configuration --bucket documents
aws s3api delete-bucket-lifecycle --bucket documents
```

Поддержаны действия `Expiration` (по `Days`, по абсолютной `Date`, а также
`ExpiredObjectDeleteMarker`), `NoncurrentVersionExpiration` с
`NewerNoncurrentVersions`, и `AbortIncompleteMultipartUpload`. Фильтры:
`Prefix`, `Tag`, `ObjectSizeGreaterThan`, `ObjectSizeLessThan` и их сочетание
через `And`.

Переходы между классами хранения (`Transition` и `NoncurrentVersionTransition`)
вычисляются тем же проходом: версия, срок которой наступил, ставится в очередь
`s3r_t0_transition`, а фоновый процесс `transition` переписывает её байты в
группу яруса нового класса тем же путём, что и запись, меняет строку и добавляет
прежние фрагменты в очередь сборки мусора. До завершения операции объект
читается в прежнем размещении.
Строка в памяти (`inline`) лишь меняет метку. Переход выполняется только к
классу с более редким доступом: класс назначения должен находиться в карте
классов ниже текущего, иначе конфигурация отклоняется с `InvalidArgument`.
`Days` считаются
от создания объекта с округлением до полуночи UTC, как в AWS; `Date` принимается
с точностью до секунды и исполняется в указанный момент. Это расширяет
поведение AWS, где требуется полночь. В кластере с единственным ярусом переход — смена
метки, и в качестве класса назначения принимается любое имя класса AWS.

Объект, срок которого истёк, получает заголовок `x-amz-expiration` в ответах
`GET` и `HEAD` до того, как будет удалён.

Правила выполняет фоновый процесс `lifecycle`; проверить их действие, не
дожидаясь его очередного прохода, можно диагностической конечной точкой — см.
главу «Администрирование».

### Блокировка объектов {: #blokirovka_obektov }

Блокировка включается только при создании бакета и требует версионирования.

```
aws s3api create-bucket --bucket vault --object-lock-enabled-for-bucket

# Режим и срок по умолчанию для всех новых объектов
aws s3api put-object-lock-configuration --bucket vault \
    --object-lock-configuration \
    'ObjectLockEnabled=Enabled,Rule={DefaultRetention={Mode=GOVERNANCE,Days=30}}'

# Срок для отдельной версии
aws s3api put-object-retention --bucket vault --key contract.pdf \
    --retention 'Mode=COMPLIANCE,RetainUntilDate=2027-01-01T00:00:00Z'

# Юридическое удержание, срока не имеет
aws s3api put-object-legal-hold --bucket vault --key contract.pdf \
    --legal-hold Status=ON
```

Пока срок не истёк или удержание не снято, версия не удаляется и не
перезаписывается; попытка возвращает `AccessDenied`.

`GOVERNANCE` обходится заголовком
`x-amz-bypass-governance-retention: true`, если у обращающегося есть право
`s3:BypassGovernanceRetention`; сокращать срок и снимать удержание тоже
разрешено. `COMPLIANCE` не обходится никем, включая владельца бакета, и срок
можно только продлить.

```
aws s3api delete-object --bucket vault --key contract.pdf \
    --version-id 0000019874f3a1c2 --bypass-governance-retention
```

### Атрибуты объекта {: #atributy_obekta }

`GetObjectAttributes` возвращает запрошенные сведения об объекте одним ответом,
без чтения содержимого.

```
aws s3api get-object-attributes --bucket documents --key big.bin \
    --object-attributes ETag ObjectSize StorageClass ObjectParts
```

Для объекта, собранного составной загрузкой, `ObjectParts` перечисляет части с
номерами и размерами и поддерживает постраничный обход
(`--max-parts`, `--part-number-marker`).

В отличие от Amazon S3, поле `ETag` этой операции сейчас возвращается в
кавычках из-за представления в используемой библиотеке протокола. Если
значение применяется для проверки содержимого, используйте атрибут
`Checksum`.

### Массовое удаление {: #massovoe_udalenie }

```
cat > delete.json <<'EOF'
{"Objects": [{"Key": "a.txt"}, {"Key": "b.txt", "VersionId": "0000019874f3a1c2"}],
 "Quiet": false}
EOF

aws s3api delete-objects --bucket documents --delete file://delete.json
```

За один запрос принимается до 1000 ключей. Права проверяются по каждому ключу
отдельно, поэтому в ответе часть ключей может оказаться в `Deleted`, а часть — в
`Errors`.

### Предподписанные ссылки и анонимный доступ {: #predpodpisannye_ssylki_i_anonimnyi_dostup }

Ссылка с подписью в параметрах запроса позволяет передать доступ к объекту тому,
у кого нет ключа:

```
aws s3 presign s3://documents/report.pdf --expires-in 3600
```

Анонимное обращение разрешается либо готовым набором прав `public-read`, либо
политикой бакета с `"Principal": "*"`.

```
aws s3api put-object-acl --bucket documents --key public/logo.png --acl public-read
curl http://node1:8000/documents/public/logo.png
```

### Потоковая загрузка {: #potokovaya_zagruzka }

Клиент, подписывающий тело по частям
(`Content-Encoding: aws-chunked`, `x-amz-content-sha256:
STREAMING-AWS4-HMAC-SHA256-PAYLOAD`), поддерживается. Тело при этом не
буферизуется целиком: части блоков кодируются и рассылаются по мере поступления
данных, поэтому размер объекта ограничен только свободным местом.

## Администрирование {: #administrirovanie }

### Квоты и ограничение скорости {: #quotas }

Квоты задаются консолью или API управления: разделы `/v2/quotas/tenant_quota` и
`/v2/quotas/bucket_quota`, а для бакета — ещё и `/v2/buckets/{бакет}/quota`. Это
поддерживаемый способ, и в установке с включённым `control_api` следует
пользоваться им.

Ниже описана таблица, в которую эти запросы пишут. Знать её устройство полезно
в двух случаях: когда поверхность управления не опубликована и квоту нужно
задать средствами SQL, и когда нужно понять, что именно означает выставленное
ограничение. В остальном таблицы плагина — не его интерфейс, и их состав меняется
между выпусками без предупреждения.

Квоты хранятся строками глобальной таблицы `s3r_quota`; отсутствие строки
означает отсутствие соответствующего ограничения. Каждая строка содержит
`tenant_id`, область (`scope`), цель (`target`), вид (`kind`), предел (`value`)
и, для скоростных ограничений, допустимый кратковременный всплеск (`burst`).
Изменять таблицу может пользователь с ролью `s3r_superuser`.

Области:

- `tenant`: весь арендатор; значение `target` должно быть пустой строкой;
- `user`: пользователь Picodata, указанный в `target`;
- `bucket`: бакет, указанный в `target`.

К одному запросу могут одновременно относиться ограничения нескольких
областей: например, арендатора, пользователя и бакета. Запрос должен пройти
каждое из них.

| `kind` | Единица и действие при достижении предела |
| --- | --- |
| `read_rate`, `write_rate` | запросы в секунду; сервер отвечает `503 SlowDown` и передаёт `Retry-After` |
| `read_bytes`, `write_bytes` | байты в секунду; передача замедляется до заданной скорости; ожидание при приёме данных ограничено сроком внутренней обработки, после чего возможен `503 SlowDown` |
| `buckets` | число бакетов; `CreateBucket` отвечает `TooManyBuckets` |
| `bytes`, `objects` | хранимый объём и число версий объектов; отказ возвращается как `403 QuotaExceeded` |

Значение `burst` измеряется в запросах для `*_rate` и в байтах для `*_bytes`.
Для остальных видов оно должно быть `NULL`. Потребление хранимого объёма и
числа объектов находится в `s3r_quota_usage`; скоростные доли данного инстанса
и дерево их распределения показывает `GET /-/debug/quota`.

```
-- Весь арендатор 0: не более 100 бакетов
INSERT INTO s3r_quota
       (tenant_id, scope, target, kind, value, burst)
VALUES (0, 'tenant', '', 'buckets', 100, NULL);

-- Пользователь alice: 200 запросов на чтение в секунду,
-- с кратковременным всплеском до 400 запросов
INSERT INTO s3r_quota
       (tenant_id, scope, target, kind, value, burst)
VALUES (0, 'user', 'alice', 'read_rate', 200, 400);

-- Бакет archive: не более 1 ТБ
INSERT INTO s3r_quota
       (tenant_id, scope, target, kind, value, burst)
VALUES (0, 'bucket', 'archive', 'bytes', 1000000000000, NULL);

SELECT scope, target, kind, value, burst
  FROM s3r_quota WHERE tenant_id = 0;
SELECT scope, target, kind, used
  FROM s3r_quota_usage WHERE tenant_id = 0;

-- Удаление строки снимает только это ограничение
DELETE FROM s3r_quota
 WHERE tenant_id = 0 AND scope = 'user'
   AND target = 'alice' AND kind = 'read_rate';
```

Изменение квоты не перекодирует и не удаляет уже записанные данные. При первом
добавлении квоты `bytes` или `objects` имеющиеся объекты учитываются
сканированием пространства имён. Известные границы точности и восстановления
учёта после аварии перечислены в разделе «Ограничения квот».

### Состояние кластера {: #sostoyanie_klastera }

Диски и группы размещения описаны глобальными таблицами, их состояние доступно
запросами SQL.

```
-- Диски, их принадлежность, домены отказа и ярусы
SELECT instance_name, path, site, failure_domain, tier, state,
       capacity_bytes, extent_count
  FROM s3r_disk
 ORDER BY instance_name;

-- Группы размещения и их геометрия
SELECT pg_id, epoch, site, tier, k, m, block_bytes, state, members
  FROM s3r_pg
 ORDER BY pg_id;

-- Занятость дисков по числу экстентов
SELECT disk_id, count(*) FROM s3r_extent GROUP BY disk_id;

-- Распределение объектов арендатора 0 по внутреннему способу размещения
SELECT class, count(*) FROM s3r_t0_object
 WHERE part_no = 0 GROUP BY class;

-- Распределение по классам хранения S3
SELECT storage_class, count(*) FROM s3r_t0_object
 WHERE part_no = 0 GROUP BY storage_class;
```

Состояния диска: `formatting`, `active`, `draining`, `lost`. Состояния группы
размещения: `clean`, `degraded`, `repairing`, `verifying`. Столбец `members`
содержит отображение идентификатора диска в номер его позиции в группе.

#### Замена исправного диска {: #zamena_ispravnogo_diska }

`draining` — это перевод диска в обслуживание, а не отказ. Диск продолжает
отвечать на чтения, планировщик перестаёт размещать на нём новые группы, а его
слоты переносятся на другие диски по одной группе за раз в пределах площадки и
яруса, так что записи не прекращаются. Диск можно вынимать, когда `GET /v2/disks`
показывает `drained: true` — то есть когда его не называет ни одна группа
размещения. Порядок действий описан в [Операциях](https://git.picodata.io/picodata/plugin/s3r/-/blob/main/doc/operations.md#disk-replacement).

Помечать `lost` исправный диск не нужно: это утверждение об отказе, которое
восстанавливает данные из избыточности вместо того, чтобы скопировать их, и
переводит в `degraded` группы, с которыми ничего не случилось.

### Диагностические конечные точки {: #diagnosticheskie_konechnye_tochki }

Конечные точки обслуживаются на порту S3, по путям, начинающимся с `/-/`, и
подписи не требуют. Набор доступных конечных точек задаётся параметром
`s3r_api.diagnostics`:

| Значение | Что открыто |
| --- | --- |
| `health` (по умолчанию) | только `/-/health` |
| `debug` | конечные точки `/-/debug/*`, кроме средств внесения ошибок и повреждения данных |
| `bench` | все конечные точки `/-/bench/*`, а также средства внесения ошибок и повреждений |

Порт S3 обычно доступен клиентам, а `/-/` отвечает до проверки подписи:
проверка наличия процесса должна работать и при ошибках аутентификации.
Уровень `debug` раскрывает состав кластера, адреса узлов, план размещения и пути
к дискам. Уровень `bench` выполняет ресурсоёмкие операции и открывает средства
намеренного повреждения данных. Его следует применять только в изолированном
испытательном контуре. Значение по умолчанию открывает только `/-/health`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /-/health` | проверка наличия процесса; не проверяет готовность дисков, групп размещения и фоновых процессов |
| `/-/debug/cluster` | состав кластера: инстансы, пригодные для размещения данных |
| `/-/debug/peers` | адреса обмена фрагментами блоков из таблицы `_pico_peer_address` |
| `/-/debug/replicasets` | репликасеты тира Picodata, их состав и фактор репликации |
| `/-/debug/topology` | группы размещения, которые были бы созданы для заданной формы; параметры `k`, `m`, `replicas` |
| `/-/debug/disks` | диски данного инстанса, их ярус и число хранимых фрагментов блоков |
| `/-/debug/repair` | очередь восстановления: что подлежит перестроению и на какой стадии |
| `/-/debug/quota` | состояние распределения квот частоты запросов на данном инстансе |
| `/-/debug/admission` | общий объём памяти `api_memory`, свободная и занятая части |
| `/-/debug/bucket-id` | вычисление номера шарда vshard для ключа |
| `/-/debug/frag-in` | вычисление служебного фрагмента для заданного шарда vshard |
| `/-/debug/bucket-ref` | проверка получения ссылки vshard для чтения или записи |
| `/-/debug/binary-sql` | проверка представления двоичных данных в текстовых столбцах |
| `/-/debug/shard` | поиск указанного фрагмента блока на дисках данного инстанса |
| `/-/debug/run/<процесс>` | выполнить один проход фонового процесса немедленно |
| `/-/debug/pause/<процесс>` | приостановить фоновый процесс |
| `/-/debug/resume/<процесс>` | возобновить фоновый процесс |
| `/-/bench/bridge` | измерение пропускной способности взаимодействия с потоком TX |
| `/-/bench/access` | измерение стоимости проверки прав |
| `/-/bench/list` | измерение отдельных этапов перечисления объектов |
| `/-/debug/errinj` | включение точки внесения ошибок; требует уровня `bench` |
| `POST /-/debug/drop-shard` | удаление указанного фрагмента с диска; требует уровня `bench` |
| `POST /-/debug/corrupt` | намеренное изменение содержимого фрагмента; требует уровня `bench` |

Последние три конечные точки изменяют поведение или данные и предназначены
только для автоматизированных испытаний. Уровни `debug` и `bench` не являются
интерфейсом мониторинга со стабильной схемой ответа.

Число фрагментов берётся из индекса самого диска. Столбец `s3r_extent.used_bytes`
отвечает на другой вопрос: он записывается при закрытии экстента, поэтому
открытый экстент показывает ноль независимо от того, сколько в него дописано.
Конечная точка отвечает только за диски того инстанса, к которому обращён
запрос.

Проверка возможности собрать группу вида 8+4 в текущей топологии:

```
curl -s "http://node1:8000/-/debug/topology?k=8&m=4"
```

Ответ содержит число дисков-кандидатов, перечень групп, которые были бы созданы,
и для каждой невыполнимой формы — причину, по которой разместить её не удалось.

### Фоновые процессы {: #fonovye_processy }

Работу, которая не выполняется в ходе запроса, ведут фоновые процессы. Они не
опрашивают состояние с коротким фиксированным интервалом: процессы запускаются
изменениями таблиц, наступлением сохранённого срока или резервным таймером на
случай пропущенного уведомления.

| Имя для `/-/debug/run` | Назначение |
| --- | --- |
| `repair` | восстановление потерянного фрагмента группы размещения по сохранившимся фрагментам |
| `scrub` | проверка согласованности данных и фрагментов чётности в группах размещения |
| `compact` | уплотнение экстентов, в которых доля живых данных ниже `compact_live_percent` |
| `gc` | освобождение фрагментов объектов, удалённых из пространства имён |
| `dirgc` | удаление строк опустевших каталогов, созданных для перечисления |
| `orphan` | обход запечатанных экстентов, проверка контрольных сумм и удаление фрагментов без строки объекта |
| `mpu` | отмена составных загрузок, заброшенных дольше `mpu_abandon_after_s` |
| `lifecycle` | применение правил жизненного цикла |
| `transition` | перенос объектов между ярусами по правилам жизненного цикла |
| `siterepl` | досылка объектов на площадки, где их ещё нет |
| `siterepl-reconcile` | сверка содержимого площадок между собой |
| `shortfall` | дозапись фрагментов, не принятых в момент записи |
| `tenants` | согласование состояния арендаторов и их таблиц |
| `dedup` | перенос сведений о совпадениях содержимого в индекс дедупликации |
| `seal` | закрытие открытого экстента на каждом локальном диске |
| `superblock` | обновление сведений о группах размещения в суперблоках дисков |
| `views` | принудительное обновление представлений кластера и карты размещения |

Имена `seal` и `views` обозначают служебные действия, а не постоянно
работающие процессы. Проход или действие выполняется немедленно обращением к
`/-/debug/run/<имя>`:

```
# Применить правила жизненного цикла сейчас
curl -s "http://node1:8000/-/debug/run/lifecycle"

# Применить их так, как если бы наступило заданное время (секунды эпохи Unix)
curl -s "http://node1:8000/-/debug/run/lifecycle?as_of=1800000000"

# Освободить место после удаления объектов
curl -s "http://node1:8000/-/debug/run/gc"
curl -s "http://node1:8000/-/debug/run/compact"
```

Параметр `as_of` у процесса `lifecycle` задаёт момент, на который вычисляются
сроки. Правило со сроком в тридцать дней проверяется сразу, без перевода
системного времени.

Пара `pause`/`resume` поддерживается для `gc`, `dirgc`, `siterepl`,
`shortfall`, `repair`, `superblock`, `compact`, `orphan`, `scrub`, `tenants`,
`transition` и `dedup`. Например, так можно приостановить восстановление на
время испытаний под клиентской нагрузкой.

### Целостность и восстановление {: #celostnost_i_vosstanovlenie }

Отказ диска обнаруживается по невозможности его открыть, а порча данных — по
несовпадению контрольной суммы. И то, и другое приводит к постановке задания в
очередь восстановления.

```
-- Очередь восстановления: слот группы, целевой диск, стадия
SELECT pg_id, slot, target_disk, state, blocks_done, blocks_failed
  FROM s3r_repair ORDER BY pg_id;

-- Ход проверки контрольных сумм запечатанных экстентов по дискам
SELECT disk_id, cursor_extent, cursor_offset, last_full_sweep_at,
       chunks_verified, chunks_bad, repaired, quarantined
  FROM s3r_scrub ORDER BY disk_id;

-- Блоки, восстановить которые не удалось
SELECT * FROM s3r_t0_quarantine;
```

Восстановление читает больше `k` сохранившихся частей, поэтому результат
проверяется по избыточным данным и расхождение обнаруживается.
Блок, для которого сохранившихся частей недостаточно, попадает в карантин и
перечисляется в `s3r_t<N>_quarantine` соответствующего арендатора вместе с
объектом, которому принадлежит.

Ход восстановления виден и через `/-/debug/repair`.

### Занятость и освобождение места {: #zanyatost_i_osvobozhdenie_mesta }

При удалении объекта его строка исключается из пространства имён, а фрагменты
добавляются в очередь освобождения. Фрагменты освобождаются не сразу: между
чтением строки объекта и чтением его фрагментов есть промежуток, а межплощадочная
репликация может восстановить объект, если удаление завершится раньше неё.
Задержку задаёт
`gc_reclaim_after_s`.

Освобождённое место становится доступным для повторного использования после
уплотнения: экстент, в котором доля
живых данных упала ниже `compact_live_percent`, переписывается, а его файл
используется повторно.

```
-- Сколько экстентов на каждом диске и сколько в них занято
SELECT disk_id, count(*), sum(used_bytes) FROM s3r_extent GROUP BY disk_id;

-- Очередь освобождения
SELECT count(*) FROM s3r_t0_gc;
```

### Наблюдение за межплощадочной репликацией {: #nablyudenie_za_mezhploschadochnoi_replikaciei }

Устройство репликации описано в главе «Классы хранения и группы размещения».
Отдельной настройки она не требует: площадка — это составляющая `dc` домена
отказа инстанса.

```
-- Объекты, которые есть не на всех площадках
SELECT count(*) FROM s3r_t0_siterepl;

-- Карта размещения объекта по площадкам
SELECT name, placements FROM s3r_t0_object
 WHERE name = 'report.pdf' AND part_no = 0;
```

Пустая выборка из `s3r_t<N>_siterepl` означает, что для данного арендатора нет
ожидающих межплощадочных копий.

### Журнал {: #zhurnal }

Записи плагина поступают в журнал инстанса Picodata. Уровень подробности плагин
наследует от настройки Picodata: при повышении уровня журнала до `debug`
отладочные сообщения плагина выводятся вместе с сообщениями СУБД.

Записи, подтверждающие штатный запуск:

| Сообщение | Значение |
| --- | --- |
| `s3r_storage started: N disk(s), listening on ...` | сервис принял конфигурацию и занял порт обмена фрагментами блоков |
| `disk <uuid> at <path> mounted: ... domain ...` | диск смонтирован; выведен его полный домен отказа |
| `disk <uuid> at <path> recovered: N shard(s)` | индекс диска восстановлен после перезапуска; указано число найденных фрагментов |
| `shard endpoint serving on ...` | узел принимает запросы обмена фрагментами |
| `placement group N created in site ...` | создана группа размещения; выведен признак устойчивости к отказу домена |

### Балансировка нагрузки {: #balansirovka_nagruzki }

Каждый инстанс с сервисом `s3r_api` открывает собственный порт и обслуживает
обращение к любым данным кластера: строка объекта и его части находятся по
кластерной карте размещения, а не по тому, куда пришёл запрос. Поэтому
балансировщик вправе направлять запросы на любой узел, и привязка клиента к
узлу не нужна.

Для проверки доступности процесса балансировщик может использовать конечную
точку `/-/health`: она отвечает до проверки подписи и подписи не требует.
Ответ `200` подтверждает только работу слушателя S3, но не готовность дисков,
групп размещения и фоновых процессов. Состояние хранилища следует контролировать
отдельно по метрикам и очередям.

```
curl -sf http://node1:8000/-/health && echo up
```

Узел, который не отвечает на пробу, выводится балансировщиком из ротации;
данные при этом остаются доступны через остальные узлы.

### Отказы и восстановление {: #otkazy_i_vosstanovlenie }

**Отказ диска.** Группа размещения, потерявшая до `m` участников, продолжает
обслуживать чтение: недостающие части восстанавливаются во время чтения.
Одновременно в очередь `s3r_repair` ставится задание на перестроение потерянного
слота на другой диск. Запись продолжается, пока в группе остаётся
`k + m - write_tolerance` доступных участников.

**Отказ узла хранения.** Участники группы находятся в различных доменах отказа,
поэтому отказ одного узла отнимает у группы один слот — тот же случай, что и
отказ диска. При обычном перезапуске хранилище блоков восстанавливает индекс из
снимка и журнала на диске, а недостающее дописывается процессами `repair` и
`shortfall`. Исключённый из кластера инстанс не допускается к обмену
фрагментами.

**Отказ площадки.** Объект читается с другой площадки только после того, как её
запись в `placements` перешла в состояние `live`. Если межплощадочная копия ещё
находилась в состоянии `pending`, потеря единственной площадки с данными делает
содержимое недоступным. Доступность метаданных дополнительно зависит от
сохранения кворума Raft средствами Picodata.

**Сетевой сбой.** Отдельных действий не требуется. Части, не принятые в момент
записи, перечислены в `s3r_shortfall` и дописываются процессом `shortfall`
после восстановления связности; объекты, ещё не переданные на другую площадку,
перечислены в `s3r_t<N>_siterepl` и досылаются процессом `siterepl`.

Проверить, что работа завершена:

```
SELECT count(*) FROM s3r_repair;      -- 0: перестраивать нечего
SELECT count(*) FROM s3r_shortfall;   -- 0: недописанных частей нет
SELECT count(*) FROM s3r_t0_siterepl; -- 0: нет ожидающих копий арендатора 0
```

### Добавление и вывод дисков {: #dobavlenie_i_vyvod_diskov }

1. Подготовить каталог на новом устройстве.
2. Добавить путь в переменную `S3R_DISKS` инстанса либо в параметр
   `s3r_storage.disks`, если пути совпадают на всех узлах.
3. Перезапустить инстанс.

Перезапускается один инстанс, обслуживание кластером при этом не прерывается:
остальные узлы продолжают принимать запросы, а данные отсутствующего узла
читаются по кодированию.

Новый диск форматируется, регистрируется в таблице `s3r_disk` и становится
кандидатом для новых групп размещения. Состав существующих групп сохраняется:
существующие фрагменты блоков между группами не переносятся, см. главу
«Ограничения». Это не относится к штатной перебалансировке шардов vshard:
Picodata переносит строки метаданных между репликасетами, а путь обращения
повторяет запрос при устаревшем маршруте.

Изменение списка дисков на работающем сервисе фиксируется в журнале
предупреждением и вступает в силу при следующем запуске.

Диски разной ёмкости и разных типов используются одновременно: ёмкость диска
учитывается при размещении. Автоматического определения NVMe, SSD или HDD нет;
оператор назначает носителю `tier=`, а карта классов хранения направляет
объекты в группы соответствующего яруса.

Вывод диска из эксплуатации — удаление его пути из списка и перезапуск
инстанса. Группы, в которые он входил, переходят в состояние `degraded`, и их
слоты перестраиваются на оставшиеся диски.

### Добавление и вывод узлов {: #dobavlenie_i_vyvod_uzlov }

Узел добавляется в кластер средствами Picodata; его диски регистрируются при
первом запуске сервиса `s3r_storage` и становятся кандидатами для новых групп
размещения.

Вывод узла выполняется его исключением из кластера средствами Picodata. Группы,
в которые входили его диски, переходят в `degraded`, и их слоты перестраиваются
на оставшиеся; до завершения перестроения избыточность понижена, поэтому узлы
выводятся по одному, с ожиданием опустошения очереди `s3r_repair`.

### Перезапуск {: #perezapusk }

Перезапуск инстанса выполняется без дополнительных действий. При запуске
хранилище блоков восстанавливает индекс из снимка и хвоста журнала на диске,
после чего дочитывает открытый экстент. Номер открытого экстента и порядковый
номер записи, начиная с которого его содержимому следует доверять, хранятся в
кластере.

Инстанс возвращается на прежних адресах: Picodata отклоняет перезапуск инстанса
с изменённым объявленным адресом iproto.

## Ограничения {: #ogranicheniya }

Глава перечисляет то, чего плагин не делает.

### Интерфейс S3 {: #interfeis_s3 }

**MFA Delete.** Удаление версий с обязательным многофакторным подтверждением
не поддерживается. Поле `MFADelete` в настройке версионирования и заголовок
`x-amz-mfa` не обеспечивают эту защиту; для неизменяемых данных используйте
блокировку объектов и внешнее управление учётными данными.

**Шифрование на стороне сервера.** Операции `PutBucketEncryption`,
`GetBucketEncryption` и `DeleteBucketEncryption` не реализованы, заголовки
`x-amz-server-side-encryption` не обрабатываются, схема SSE-C с ключом клиента
не поддерживается, интеграции с внешними хранилищами секретов нет. Данные на
дисках хранятся в незашифрованном виде; шифрование выполняется средствами
носителя или файловой системы. Обмен по сети шифруется — см. главу «Шифрование
трафика».

**Загрузка формой из браузера (`POST Object`).** Работает: форма разбирается,
подпись политики проверяется, срок её действия и условия `eq`, `starts-with` и
`content-length-range` применяются. Не поддержаны подстановка `${filename}` в
имени объекта, перенаправление по `success_action_redirect` и теги, переданные
полем формы; условие, которое не выполнилось, возвращает `400`, а не `403`. Всё
перечисленное — поведение библиотеки s3s текущей версии.

**Уведомления о событиях.** Отправка сообщений об изменениях в очередь или
функцию не поддерживается. Отслеживать изменения следует опросом перечисления
или запросом SQL к таблице `s3r_t<N>_object` соответствующего арендатора
(`part_no = 0` для строк объектов).

**Статический веб-сайт.** Конфигурация сайта сохраняется, читается и удаляется
(`PutBucketWebsite`, `GetBucketWebsite`, `DeleteBucketWebsite`), но сам сайт не
отдаётся: обращение к корню бакета не возвращает индексный документ, ошибка не
подменяется страницей ошибки и правила перенаправления не применяются. Для этого
нужна отдельная конечная точка, которой нет.

**Журналирование обращений в бакет (`PutBucketLogging`).** Не поддерживается.
Каждый запрос попадает в журнал инстанса, но выделенного журнала обращений в
формате S3 нет. См. также «Аудит».

**S3 Select.** `SelectObjectContent` не поддерживается: выборка внутри объекта
на стороне сервера не выполняется.

**Каталожные бакеты S3 Express (`ListDirectoryBuckets`).** Не поддерживаются.

**Настройка репликации через S3 API.** Межплощадочная репликация работает, но
управляется топологией кластера, а не операциями `PutBucketReplication`.

**Классы хранения S3.** Класс выбирается при записи и переносится правилом
жизненного цикла — см. главу «Классы хранения и ярусы». Не поддерживается
`RestoreObject`: классы с отложенным доступом (`GLACIER`, `DEEP_ARCHIVE`) можно
объявить в карте ярусов, но объект в них остаётся доступным для чтения сразу, и
операции восстановления нет. Правила не выполняют обратный перенос в класс с
более частым доступом.

**Дедупликация.** Одинаковые объекты хранятся независимо: общего содержимого
между объектами нет. Подготовка к дедупликации выполнена — при включённом
`s3r_tenant.dedup` для каждой части считается SHA-256 и ведётся индекс
совпадений, а его датчики показывают, сколько места освободило бы разделение
содержимого. Само разделение не реализовано и в срок ближайшего выпуска не
входит: решение принимается по этим измерениям, а не заранее.

**Сжатие объектов.** Выполняется zstd поблочно и включается на бакет
(`s3r_bucket.compress`) или на арендатора (`s3r_tenant.compress`); уровень
задаётся на арендатора (`s3r_tenant.compress_level`, по умолчанию 3). Не
поддерживается выбор кодека клиентом, сжатие объектов, уже записанных без него,
и сжатие объектов класса `inline`: их содержимое лежит в строке метаданных.

**Временные учётные данные (STS) и Bearer-токены.** Не поддерживаются.
Обращение подписывается постоянным ключом доступа. Срок действия ключа не
задаётся: ключ действителен, пока существует названный им пользователь и запись
о ключе.

**Интеграции.** Отправка событий в Kafka, вызов функций, интеграция с системами
биллинга, драйвер CSI для контейнерных платформ, векторный поиск и RDMA не
поддерживаются.

### Адресация и многоарендность {: #adresaciya_i_mnogoarendnost }

**Адресация именем бакета в имени узла.** На точке входа по умолчанию (по IP или
имени узла) поддерживается только адресация в стиле пути. Виртуально-хостовая
адресация работает для арендатора с заданным FQDN — по его домену и в форме
`бакет.FQDN`; общего базового домена для арендатора по умолчанию нет. См. главы
«Адресация» и «Изоляция арендаторов».

**Изоляция арендаторов.** Реализована: у каждого арендатора своё пространство имён
бакетов, объектов и учётных данных (два арендатора могут владеть одноимёнными
бакетами), свой FQDN, свой сертификат и mTLS, своя административная роль и свои
квоты. Чего пока нет — отдельного пула дисков на арендатора (столбец
`s3r_tenant.pool_id` зарезервирован, но маршрутизация его не использует).

### Ограничения квот {: #ogranicheniya_kvot }

Поддерживаются квоты на число бакетов, объём и число хранимых объектов, частоту
запросов и скорость передачи данных. Квоты задаются для арендатора,
пользователя или бакета в таблице `s3r_quota`. Отсутствие строки означает
отсутствие соответствующего ограничения.

Ограничения частоты запросов и скорости передачи распределяются между
инстансами. Пока инстанс не получил свою долю общего предела, он временно
применяет локальное ограничение. В этот период суммарная частота может
превысить заданное значение.

Учёт объёма и числа объектов ведётся в таблице `s3r_quota_usage`. Автоматическая
сверка этой таблицы с фактически хранимыми объектами пока не выполняется, поэтому
после аварийного завершения между резервированием квоты и записью объекта
возможно завышение учтённого объёма.

### Хранение {: #hranenie }

**Классы носителей.** Диск не объявляет своего типа, поэтому пул нельзя
ограничить накопителями определённого вида, а кэширование на твердотельных
накопителях не выполняется. Разные по объёму диски используются одновременно.

**Перебалансировка содержимого.** Расширение кластера не влечёт перемещения
существующих фрагментов блоков между группами размещения: новые диски становятся
кандидатами для новых групп, состав существующих групп сохраняется.
Перебалансировка шардированных таблиц пространства имён средствами vshard
поддерживается и является отдельным механизмом.

**Кворум записи.** Запись подтверждается, когда её приняли
`k + m - write_tolerance` участников группы, но не менее `k`. При
`write_tolerance = 0` недоступность одного участника делает невозможной запись
во всю группу.

**Межплощадочная репликация для отдельного арендатора.** Набор площадок —
свойство кластера, и включить или отключить репликацию для одного арендатора
нельзя. Подробнее — «Межплощадочная репликация», раздел «Репликация — свойство
кластера, а не арендатора».

### Наблюдаемость и управление {: #nablyudaemost_i_upravlenie }

**Публикация метрик.** Плагин публикует метрики в формате Prometheus через
конечную точку Picodata `/metrics`, отдельно для сервисов `s3r_api`, `s3r_meta`
и `s3r_storage`: частоту и длительность запросов, объём переданных данных,
число запросов в обработке, расход выделенной запросам памяти и отказы
аутентификации. Сервис `s3r_storage` дополнительно публикует метрики блочного
хранилища: обмен фрагментами блоков с разбивкой на локальный путь и сеть
(`s3r_shard_ops_total`, `s3r_shard_bytes_total`, `s3r_shard_network_seconds`) —
сеть является ограничивающим ресурсом, а кодирование увеличивает объём, идущий по
ней; длительность операций ввода-вывода по каждому диску (`s3r_disk_io_seconds`);
ёмкость дисков (`s3r_disk_capacity_bytes`); а также частоту восстановлений блока из
сохранившихся фрагментов (`s3r_ec_reconstructions_total`) — на исправном кластере она нулевая,
и её рост виден раньше, чем накопление очереди восстановления.

Отдельно публикуются метрики фоновых процессов: восстановления, проверки
целостности, сборки мусора и межплощадочной репликации. Метрика
`s3r_worker_runs_total` содержит метку процесса. Если очередь растёт, а счётчик
проходов не изменяется, соответствующий процесс не выполняет задания.
Состояние избыточности показывает `s3r_placement_groups` с меткой состояния — число
групп в состоянии `degraded` есть показатель пониженной избыточности, на который
настраивается предупреждение. Глубину очереди восстановления показывает
`s3r_repair_queue_depth`, число ожидающих дозаписи фрагментов —
`s3r_shortfall_pending`, а несовпадение чётности при проверке целостности —
`s3r_scrub_inconsistent_total` (не износ носителя, а ошибка записи
или искажение). Отказы по квотам наблюдаемы через `s3r_quota_rejected_total`
(число бакетов, объём и число объектов) и `s3r_ratelimit_rejected_total` (частота
запросов и скорость передачи); обе несут только метки ограниченной мощности — область и вид предела, но
не имя пользователя или бакета. Дополнительно наблюдение ведётся по
журналу инстанса, диагностическим конечным точкам `/-/` и запросам SQL к таблицам
плагина. **Статистика обращений в разрезе бакетов метрикой не является**: число
бакетов не ограничено, а метка неограниченной мощности умножает все ряды, поэтому имя
бакета никогда не становится меткой.

**Панель Grafana и правила Prometheus.** В репозитории плагина поставляются
`deploy/grafana/s3r-dashboard.json` и `deploy/prometheus/s3r-alerts.yml`. Панель
собрана из четырёх рядов по вопросам, которые оператор задаёт по порядку:
обслуживает ли кластер запросы, здоров ли он, успевает ли он и есть ли место.
Правила описывают выражения, а не политику оповещения: что считать поводом
разбудить человека, решает эксплуатация. Оба файла версионируются вместе с
метриками, которые они читают, — панель, выложенная отдельно от кода, устаревает
при первом же переименовании метрики.

**Аудит.** Выделенного журнала действий пользователей в терминах S3 нет, как
и его выгрузки по протоколу syslog и формата CEF. Административные действия
выполняются средствами SQL и попадают в аудит Picodata; его файлы передаются во
внешнюю систему сбора событий средствами операционной системы.

**Ролевая модель.** Плагин создаёт роли трёх видов — `s3r_superuser`,
`s3r_observer` и по одной роли администратора на каждого арендатора,
`s3r_tenant_admin_<идентификатор>`. Роль арендатора создаётся вместе с
арендатором и удаляется вместе с ним; остальные создаются миграцией. Выдаются
они средствами SQL Picodata; конструктора ролей нет. Отдельной роли аудитора нет: чтение журнала входит в полномочия наблюдателя,
а обладатель `s3r_superuser` в любом случае читает таблицы напрямую.

**Внешние поставщики аутентификации.** Учётные записи S3 — это пользователи
Picodata. Вход в консоль управления выполняется либо через внешнего поставщика
по протоколу OpenID Connect (раздел «Первый вход в консоль управления»), либо по
паролю пользователя Picodata, когда поставщика нет (раздел «Запуск без внешнего
поставщика аутентификации»). Создание учётных записей из каталога LDAP
средствами самого плагина и двухфакторная аутентификация не поддерживаются: и то
и другое настраивается на стороне поставщика, а значит, в режиме без поставщика
недоступно.

Ключи доступа S3 внешнего поставщика не используют и от его доступности не
зависят: подпись SigV4 проверяется по таблице учётных данных кластера. Это
сделано намеренно — недоступность поставщика не должна останавливать работу с
данными.

**Ограничение по адресу обращения.** Операторы условий `IpAddress` и
`NotIpAddress` в политике бакета не реализованы. Инструкция, использующая их,
трактуется в сторону отказа.

**Настройка плагина.** Консоль управления и API управления обслуживают
пользователей, ключи доступа, бакеты, права доступа, квоты и арендаторов — см.
«Первый вход в консоль управления». Настройка самого плагина по-прежнему
выполняется командой `ALTER PLUGIN`: REST-интерфейса, который изменял бы
конфигурацию плагина или состав кластера, нет. Присоединение и исключение
инстансов — операции Picodata, а не плагина.

**Резервное копирование и восстановление.** Встроенной операции, которая
создаёт согласованную резервную копию метаданных Picodata и файлов хранилища
блоков, нет. Снимок только таблиц Picodata не содержит данные объектов, а копия
только каталогов дисков не содержит пространство имён и карту размещения.
Поддерживаемая процедура физического резервного копирования и восстановления
кластера не определена.

**Обновление между версиями.** Версия 2.0.0 — первый помеченный выпуск.
Обновление кластера с данными с более ранних сборок и поочерёдное обновление
инстансов разных версий не входят в проверенные сценарии.

### Проверенные границы {: #proverennye_granicy }

Перечисленные ниже величины не проверялись и в приёмочные испытания не входят.

**Объём хранилища свыше 64 ПБ.** Программных ограничений нет; на таком объёме
установка не испытывалась.

**Схемы кодирования с числом частей больше двадцати** (например 61+3).
Теоретически выполнимы, на практике не проверялись и целевым сценарием не
являются.

## Запуск без внешнего поставщика аутентификации {: #zapusk_bez_vneshnego_postavschika_autentifikacii }

Поставщика OpenID Connect может не быть: изолированный контур, испытательный
стенд, установка, куда Keycloak придёт позже. В таком кластере вход в консоль
проверяет сама Picodata.

Для этого в настройке `s3r_api.iam` указывается `auth_type` со значением
`picodata`. Консоль тогда спрашивает имя пользователя и пароль Picodata — те же,
с которыми администратор подключается к кластеру через `picodata connect`. Ни
поставщика, ни клиента, ни области (realm) не требуется.

Консоль и API управления работают полностью. Принципал — тот же пользователь
Picodata, полномочия — те же роли: на них способ входа не влияет.

### 1. Кластер с установленным плагином {: #1_klaster_s_ustanovlennym_plaginom }

Порядок установки описан в разделе «Установка» и от способа входа не зависит:
плагин ставится, миграции применяются, сервисы включаются. Для локального стенда
достаточно `cargo pike run`, для установки вручную — команды от `CREATE PLUGIN`
до `ENABLE` оттуда же.

Настройка `iam` для запуска не нужна. Инстанс поднимается и конечная точка S3
работает без неё: без `iam` недоступен только вход в консоль. Задать её можно
когда угодно, на работающем кластере и без перезапуска.

Дополнительно потребуется один параметр конфигурации Picodata —
`instance.http_listen`. На этом порте Picodata отдаёт консоль и API управления.

```yaml
instance:
  http_listen: "0.0.0.0:6006"
```

Проверка того, что плагин установлен и включён:

```sql
SELECT name, version, enabled FROM _pico_plugin;
```

### 2. Настройка плагина {: #2_nastroika_plagina }

Выполняется через `ALTER PLUGIN`, перезапуск не требуется.

```sql
ALTER PLUGIN s3r 2.0.0 SET s3r_api.control_api = 'true';
ALTER PLUGIN s3r 2.0.0 SET s3r_api.iam = '{"auth_type": "picodata"}';
```

Весь раздел `iam` состоит из одной настройки: `issuer`, `audience`, `client_id`
и адреса поставщика не указываются, потому что поставщика нет.

`control_api` по умолчанию выключен: существующая установка не должна получать
поверхность управления просто оттого, что её обновили. Консоль и API управления
обслуживаются встроенным HTTP-сервером Picodata — тем же, на котором работает её
собственный веб-интерфейс, и на том же порте (шаг 1).

Значение `picodata` указывается явно. Кластер, в котором раздел `iam` не задан,
во входе отказывает — и это намеренно: умолчание со смыслом «пускать всех»
оставляет установку открытой по недосмотру.

### 3. Первый администратор {: #3_pervyi_administrator }

Выполняется через административную консоль узла:

```sql
CREATE USER "ivanov" WITH PASSWORD 'Sup3rSecret...' USING chap-sha1;
GRANT "s3r_superuser" TO "ivanov";
```

Оба идентификатора — в двойных кавычках. Без кавычек Picodata приводит их к
верхнему регистру, а роли создаются в нижнем, и выдача завершится ошибкой
«нет такой роли».

Пароль здесь — это пароль от консоли. В установке с поставщиком он задаётся
лишь потому, что Picodata требует указать способ аутентификации при создании
пользователя, и при входе не спрашивается.

Роли те же, что и при работе с поставщиком: `s3r_superuser`,
`s3r_tenant_admin_<идентификатор>`, `s3r_observer` — см. таблицу в разделе
«Первый вход в консоль управления».

### 4. Вход {: #4_vhod }

Адрес консоли — `https://<адрес>:<порт>/s3gateway/console/`. Вместо кнопки
перенаправления к поставщику страница показывает форму с именем пользователя и
паролем.

API управления в этом режиме принимает те же учётные данные в виде HTTP Basic:

```bash
curl -u ivanov -k https://mhd.example.ru:6006/s3gateway/api/v2/rights
```

Ответ содержит имя принципала и его роли — это самый короткий способ проверить,
что вход настроен и роль выдана.

### Чем этот режим отличается от работы с поставщиком {: #chem_etot_rezhim_otlichaetsya_ot_raboty_s_postavschikom }

Пароль передаётся с каждым запросом. Сессии не создаётся, проверяется каждый
запрос, поэтому нет ни таблицы сессий, ни ключа подписи, ни срока действия.
Расплата за это — пароль в открытом виде на каждом запросе, поэтому консоль
следует публиковать по HTTPS. На незащищённом соединении консоль предупреждает
об этом на странице входа.

Отзыв выполняется средствами SQL и действует немедленно. `ALTER USER` с новым
паролем или `DROP USER` закрывают доступ со следующего запроса; списка отозванных
токенов здесь нет, потому что нет и токенов.

Ключи доступа S3 от режима входа не зависят. Подпись SigV4 проверяется по
таблице учётных данных кластера и при любом `auth_type` работает одинаково.

Поставщик добавляется позже без перенастройки хранилища. Ключи доступа,
бакеты и объекты от него не зависят: достаточно заменить раздел `iam` на
настройки поставщика и продолжить с раздела «Первый вход в консоль управления».
Пользователи Picodata при этом сохраняются — совпасть должно только имя, которое
придёт в утверждении токена.

## Первый вход в консоль управления {: #pervyi_vhod_v_konsol_upravleniya }

Этот раздел описывает путь от пустой установки до работающего входа в консоль
через внешнего поставщика аутентификации. Шаги выполняются один раз и в
указанном порядке.

> **Поставщика нет?** Кластер умеет проверять пароль сам — см. раздел «Запуск
> без внешнего поставщика аутентификации». Разворачивать Keycloak только ради
> входа в консоль не требуется.

Первый администратор создаётся средствами SQL: создать его через консоль нельзя,
потому что для входа в консоль администратор уже нужен. Дальше всё делается
через API управления.

### 1. Поставщик аутентификации {: #1_postavschik_autentifikacii }

s3r доверяет ровно одному издателю токенов (`issuer`). Обычно это Keycloak. Если
пользователи приходят из Google или другого внешнего каталога, Keycloak
выступает посредником, и для s3r это ничего не меняет.

В области (realm) поставщика нужно создать клиента для консоли:

* тип клиента — **публичный** (public), без секрета. Консоль — это код,
  выполняющийся в браузере: любой секрет, попавший в сборку, попадает и к
  пользователю. Вместо секрета используется PKCE;
* разрешённый способ получения токена — **код авторизации** (authorization
  code) с PKCE (метод `S256`);
* разрешённый адрес возврата (redirect URI) — адрес консоли со слешем на
  конце, например `https://mhd.example.ru:6006/s3gateway/console/`;
* аудитория (`aud`) токена — значение, которое будет указано в настройке
  `audience` плагина. Токен без нужной аудитории отклоняется.

### 2. Утверждение с именем пользователя {: #2_utverzhdenie_s_imenem_polzovatelya }

Принципал s3r — это пользователь Picodata, и его имя берётся из утверждения
(claim) токена. По умолчанию — `preferred_username`.

Форму имени стоит выбрать заранее. При посредничестве Keycloak имя локальной
учётной записи часто заполняется из адреса электронной почты, и тогда
`preferred_username` приходит в виде `ivanov@example.ru`. Для Picodata это
допустимое имя, и работать будет всё. Но это же имя попадёт в каждую запись
ACL, в каждую строку квоты и в каждую запись аудита. Если такая форма
нежелательна, на стороне Keycloak настраивается отображение (claim mapper),
выдающее короткое имя. Через год после первого входа сменить его гораздо
дороже.

Имя утверждения меняется настройкой `username_claim`.

### 3. Первый пользователь Picodata {: #3_pervyi_polzovatel_picodata }

Выполняется через административную консоль узла:

```sql
CREATE USER "ivanov" WITH PASSWORD 'Sup3rSecret...' USING chap-sha1;
GRANT "s3r_superuser" TO "ivanov";
```

Оба идентификатора — в двойных кавычках. Без кавычек Picodata приводит их к
верхнему регистру, а роли создаются в нижнем, и выдача завершится ошибкой
«нет такой роли».

Имя пользователя должно совпадать с тем, что придёт в утверждении токена
(см. шаг 2). Если имена приходят в виде адресов почты, то и пользователь
создаётся с таким именем: `CREATE USER "ivanov@example.ru" ...`.

В установке, где пользователей заводит `argus` из каталога LDAP, пользователь
уже существует — нужна только выдача роли.

Пароль в этой команде консолью не используется: вход выполняется по токену
поставщика, и пароля консоль не спрашивает. Задать его приходится потому, что
Picodata требует указать способ аутентификации при создании пользователя. Самая
частая ошибка на этом шаге — принять его за пароль от консоли.

#### Роли {: #roli }

| Роль | Полномочия |
| --- | --- |
| `s3r_superuser` | Весь кластер: арендаторы и их сертификаты, ярусы, обслуживание, все экраны и все операции |
| `s3r_tenant_admin_<идентификатор>` | Пользователи, ключи и бакеты **одного** арендатора, чей идентификатор указан в имени роли |
| `s3r_observer` | Только чтение: состояние кластера, ёмкость, группы размещения, восстановление |

Роль администратора арендатора создаётся вместе с арендатором. Для арендатора
по умолчанию это `s3r_tenant_admin_0`.

> **При обновлении с версии, где роль называлась `s3r_tenant_admin`,** выдачу
> нужно повторить с новым именем: `GRANT "s3r_tenant_admin_0" TO "ivanov"`.
> Старой роли больше нет, и администратор арендатора без новой выдачи получит
> «не найдено» на свой собственный арендатор.

### 4. Настройка плагина {: #4_nastroika_plagina }

Выполняется через `ALTER PLUGIN`, перезапуск не требуется.

```sql
ALTER PLUGIN s3r 2.0.0 SET s3r_api.control_api = 'true';

ALTER PLUGIN s3r 2.0.0 SET s3r_api.iam = '{
  "auth_type": "keycloak",
  "auth_path": "https://keycloak.example.ru/realms/mhd/protocol/openid-connect/auth",
  "token_path": "https://keycloak.example.ru/realms/mhd/protocol/openid-connect/token",
  "issuer": "https://keycloak.example.ru/realms/mhd",
  "audience": "s3gateway",
  "client_id": "console",
  "username_claim": "preferred_username"
}';
```

`control_api` по умолчанию выключен: существующая установка не должна получать
поверхность управления просто оттого, что её обновили.

`auth_path` и `token_path` указываются целиком, потому что их вид различается у
разных поставщиков. Если они не заданы, адреса берутся из документа
`/.well-known/openid-configuration` издателя.

Консоль и API управления обслуживаются встроенным HTTP-сервером Picodata — тем
же, на котором работает её собственный веб-интерфейс. Порт задаётся параметром
`instance.http_listen` в конфигурации Picodata (в программе испытаний — 6006).

### 5. Вход {: #5_vhod }

Адрес консоли — `https://<адрес>:<порт>/s3gateway/console/`.

Дальше происходит следующее. Консоль запрашивает у API адрес поставщика,
отправляет туда браузер, получает обратно код авторизации и передаёт его
серверу, а сервер меняет код на токен. Обмен выполняется на сервере намеренно: браузер не получает
токен обновления, а секретов клиента в нём нет.

### Если войти не удалось {: #esli_voiti_ne_udalos }

| Что видно | Что это значит |
| --- | --- |
| Страница сообщает, что кластер не может никого аутентифицировать | Настройка `s3r_api.iam` не задана. Шаг 4 |
| Вход проходит, но консоль отвечает «нет такого принципала» (403) | Токен подлинный, но пользователя Picodata с таким именем нет. Сравните утверждение токена с именем из шага 3 — чаще всего расходится форма имени |
| Вход проходит, экранов нет, операции запрещены (403) | Пользователь есть, роль не выдана. Шаг 3 |
| Арендатор отвечает «не найдено» (404) | Нет роли `s3r_tenant_admin_<идентификатор>` этого арендатора. Ответ «не найдено», а не «запрещено», намеренно: ответ «запрещено» подтвердил бы, что такой арендатор существует |
| Ответ 503 с указанием, что поставщик недоступен | Поставщик не отвечает. Это не выход из системы: уже выданные токены продолжают работать до истечения срока, а операции с данными по ключам S3 от поставщика не зависят вовсе |
| Страница сообщает, что консоль не собрана | Сборка плагина выполнена без консоли. Соберите её и пересоберите плагин |

### Где живёт принципал консоли {: #gde_zhivet_principal_konsoli }

Принципал, вошедший в консоль, относится к системному арендатору, а не к
какому-либо из пользовательских. Обычно каждый принципал принадлежит своему
арендатору, и вход в консоль — исключение из этого правила. Тем, каким
арендатором такой принципал управляет, распоряжаются выданные ему роли.

Системный арендатор не перечисляется в списке арендаторов и недоступен по
номеру: он хранит то, что не принадлежит ни одному пользовательскому арендатору,
и администрировать его нельзя.

## Что умеет консоль управления {: #chto_umeet_konsol_upravleniya }

Консоль — веб-интерфейс, собранный в двоичный файл плагина и доступный по адресу
`https://<адрес>:<порт>/s3gateway/console/`. Отдельного развёртывания она не
требует, обновляется вместе с плагином и работает поверх того же API управления,
что описано в следующей главе: всё перечисленное здесь можно выполнить и
запросом.

Снимков экранов в руководстве нет намеренно: расположение элементов меняется от
выпуска к выпуску, а перечень возможностей — нет. Ниже — что доступно и на каком
разделе искать.

### Разделы кластера {: #razdely_klastera }

Эти разделы доступны обладателям `s3r_superuser` и `s3r_observer`; наблюдателю —
только чтение.

**Обзор.** Занятый и свободный объём по кластеру и по каждому диску, логический и
физический объём по отдельности, расход памяти под метаданные с долей от квоты
инстанса и указанием худшего инстанса, время работы, версии Picodata и плагина,
ссылка на метрики. Здесь же счётчик того, что требует внимания.

**Кластер.** Инстансы и диски с их состоянием. Диск переводится в режим
обслуживания и возвращается из него; консоль показывает, безопасно ли извлекать
диск сейчас и что на нём ещё лежит. Состав выгружается в файл.

**Группы размещения.** Участники каждой группы, их домены отказа и ответ на
вопрос, переживёт ли группа потерю домена — с объяснением, почему переживёт или
нет. Группы под угрозой перечислены отдельно.

**Восстановление.** Очередь перестроения: работы с их стадией и долей
выполненного, нехватка фрагментов, тишина как отдельное состояние. Отсюда же
включается ручной режим и выполняются действия над отдельной работой —
приостановить, возобновить, отказаться, повторить (см. «Управление
восстановлением» в главе про API).

**Репликация.** Состояние межплощадочной репликации: что скопировано, что ещё
должно, где отставание велико.

**Целостность.** Что нашла фоновая проверка данных и чётности, и что помещено в
карантин.

### Разделы арендатора {: #razdely_arendatora }

**Арендаторы.** Создание и удаление арендатора, его FQDN, сертификат TLS и
материал mTLS, включая передачу сертификата и режим обязательного mTLS, срок
действия и замену. Создание арендатора — операция, которая выполняется не
мгновенно, и консоль показывает ожидание явно.

**Пользователи и ключи.** Создание пользователя, блокировка и разблокировка;
выдача ключа доступа, замена секрета с сохранением ключа и удаление ключа.
Секретный ключ показывается один раз, в момент выдачи.

**Бакеты.** Список бакетов с владельцем и признаком версионирования, создание и
удаление, передача бакета другому владельцу, включение блокировки объектов.
Настройки бакета: версионирование, CORS, политика, сжатие, квота. Правила
жизненного цикла редактируются отдельным разделом — срок жизни, переход в другой
класс хранения, обращение со старыми версиями, обрыв незавершённых загрузок — и
доступны также в виде JSON. Права на бакет задаются матрицей выдач.

**Объекты.** Обзор бакета по папкам, загрузка файла, скачивание и получение
ссылки, которой можно поделиться. Загрузка и скачивание идут напрямую между
браузером и конечной точкой S3 по подписанной ссылке, минуя плоскость
управления; если бакет не разрешает обращение из браузера, консоль объясняет это
и предлагает добавить нужное правило CORS.

### Чего в консоли нет {: #chego_v_konsoli_net }

Установка плагина, его конфигурация (`ALTER PLUGIN`), создание пользователей
Picodata и выдача ролей выполняются средствами SQL: это операции уровня СУБД, и
консоль их не подменяет. Состав кластера — тоже: узел вводится и выводится
средствами Picodata (см. «Добавление и вывод узлов»).

## API управления {: #api_upravleniya }

Консоль не делает ничего, чего нельзя сделать запросом: она целиком построена на
этом API. Поэтому всё, что описано в главах про арендаторов, пользователей,
квоты и обслуживание, доступно и из скрипта — для автоматизации, разовой
операции на сотне бакетов или интеграции с чужой системой управления.

Точное описание запросов и ответов — в файле `doc/api/openapi.yaml` репозитория
плагина. Это спецификация OpenAPI: из неё генерируется клиент консоли, и она
описывает каждое поле каждого ответа. Настоящая глава объясняет устройство и
правила, спецификация определяет формат.

### Адрес и включение {: #adres_i_vklyuchenie }

API обслуживает встроенный HTTP-сервер Picodata, тот же, на котором работает её
собственный веб-интерфейс. Порт задаётся параметром `instance.http_listen`,
базовый путь — `/s3gateway/api`, и публикуется поверхность настройкой
`s3r_api.control_api = 'true'` (по умолчанию выключена).

Отвечает любой инстанс, на котором включён сервис `s3r_api`. Сессий нет, так что
балансировщику не нужны «липкие» соединения: два последовательных запроса могут
прийти на разные инстансы.

### Аутентификация {: #autentifikaciya }

Способ тот же, что и у консоли, и определяется настройкой `s3r_api.iam`.

При работе с поставщиком OpenID Connect запрос несёт маркер доступа:

```bash
curl -H "Authorization: Bearer $TOKEN" \
  https://mhd.example.ru:6006/s3gateway/api/v2/capacity
```

При `auth_type: "picodata"` — имя и пароль пользователя Picodata в виде
HTTP Basic:

```bash
curl -u ivanov https://mhd.example.ru:6006/s3gateway/api/v2/capacity
```

Полномочия в обоих случаях определяют роли Picodata: `s3r_superuser`,
`s3r_tenant_admin_<идентификатор>`, `s3r_observer`. Что даёт каждая, описано в
разделе «Ролевая модель арендаторов» приложения А. Запрос к арендатору, роли
которого у принципала нет, получает ответ «не найдено», а не «запрещено».

Начать удобно с `GET /v2/rights`: он отвечает именем принципала и списком его
ролей, то есть сразу показывает, что учётные данные приняты и что этому
принципалу разрешено.

### Формат ответа {: #format_otveta }

Успех и отказ имеют одну оболочку:

```json
{"errors": [], "result": {"...": "..."}}
```

При отказе `errors` содержит сообщения для человека, а рядом приходит
`error_details` — массив записей `{code, resource, message}`. Поле `code`
устойчиво и предназначено для программы: `Unauthenticated`, `Forbidden`,
`NotFound`, `NameInUse`, `StaleVersion`, `PayloadTooLarge`,
`RouteNotImplemented`, `ProviderUnavailable` и коды уровня управления. Разбирать
текст сообщений не нужно и не следует: тексты меняются, коды — нет.

Коды состояния HTTP обычные, с двумя, которые стоит знать заранее. Ответ `206`
приходит на пакетную операцию, часть которой не удалась: выполненное перечислено
в `result`, невыполненное — в `errors` и `error_details`. Ответ `409` с кодом
`NameInUse` означает, что объект с таким именем уже есть.

### Правила, о которых лучше знать заранее {: #pravila_o_kotoryh_luchshe_znat_zaranee }

Создание не идемпотентно. Повторный `POST` с тем же именем — это `409`, а не
повторная выдача уже созданного: два администратора, создающих одного арендатора,
должны узнать об этом, а не получить по успешному ответу. Клиент, потерявший
ответ, выполняет `GET`.

Постраничный вывод устроен по курсору, а не по номеру страницы. Ответ содержит
курсор — непрозрачную метку последней выданной записи; следующая страница
запрашивается с ней. Номеров страниц и общего числа записей нет: SQL Picodata не
имеет `OFFSET`, и выдача по курсору вдобавок не пропускает и не повторяет записи
при одновременном изменении данных.

Секретный ключ доступа возвращается один раз — в ответе на его выдачу или замену.
Больше его не отдаёт ни один запрос: в таблице он хранится в виде, из которого
исходный ключ не восстанавливается.

Одновременное изменение одного объекта разрешается по версии: запрос с
устаревшей версией получает `StaleVersion`, и его следует повторить, прочитав
свежее состояние.

### Из чего состоит поверхность {: #iz_chego_sostoit_poverhnost }

Полный перечень — в спецификации; здесь разделы, чтобы понимать, где искать.

| Раздел | Маршруты | О чём |
| --- | --- | --- |
| Сессия | `/v2/start`, `/v2/code`, `/v2/rights`, `/v2/health` | способ входа, обмен кода на маркер, кто я и что мне можно, живость |
| Арендаторы | `/v2/tenants`, `/v2/tenants/extra_rights`, `/v2/tenants/{id}/mtls`, `/v2/tenants/{id}/set_mtls`, `/v2/tenants/{id}/load_mtls_cert` | создание и удаление арендаторов, их домены и клиентские сертификаты |
| Пользователи и ключи | `/v2/users`, `/v2/credentials`, `/v2/credentials/{ключ}` | учётные записи арендатора, выдача, замена и удаление ключей доступа, блокировка |
| Бакеты | `/v2/buckets`, `/v2/buckets/{бакет}/settings`, `/versioning`, `/cors`, `/policy`, `/lifecycle`, `/compression`, `/quota` | список бакетов, передача бакета другому владельцу (`PUT /v2/buckets`), настройки, те же, что задаются средствами S3 |
| Доступ и квоты | `/v2/acl`, `/v2/quotas/tenant_quota`, `/v2/quotas/bucket_quota` | права на бакеты, ограничения по объёму и числу объектов |
| Объекты | `/v2/objects`, `/v2/objects/presign` | обзор содержимого бакета и подписанная ссылка на объект |
| Ёмкость и кластер | `/v2/capacity`, `/v2/cluster/servers`, `/v2/cluster/attention` | сколько занято и сколько осталось, состав кластера, что требует внимания |
| Диски | `/v2/disks`, `/v2/disks/{диск}/maintenance` | список дисков и перевод диска в обслуживание |
| Целостность | `/v2/integrity`, `/v2/repair`, `/v2/replication`, `/v2/memory` | проверка целостности, очередь восстановления, межплощадочная репликация, расход памяти под метаданные |
| Управление восстановлением | `/v2/repair/mode`, `/v2/repair/{группа}/{слот}` | ручной режим и действия над отдельной перестройкой; только `s3r_superuser` |

Ввод и вывод узла кластера в этот перечень не входит, хотя маршруты для него
предусмотрены спецификацией: `add_server_to_storage`, `del_server_from_storage` и
их аналоги для S3 отвечают `501` и называют команду, которой это делается. Состав
кластера меняет Picodata, а не плагин, — см. «Добавление и вывод узлов».

Обзорные разделы (`/v2/capacity`, `/v2/cluster/*`, `/v2/disks`, `/v2/integrity`,
`/v2/repair`, `/v2/replication`) доступны и наблюдателю: они ничего не меняют.
Всё, что меняет состояние кластера, требует `s3r_superuser`, а операции в
пределах арендатора — его роли администратора.

### Управление восстановлением {: #upravlenie_vosstanovleniem }

Перестройка потерянного фрагмента запускается сама: группа размещения, лишившаяся
участника, ставится в очередь, и плагин перестраивает её на свободный диск. Обычно
вмешиваться не нужно. Но бывает и иначе: идут работы в стойке и лишний трафик
некстати; диск, на который идёт перестройка, ведёт себя подозрительно; перестройка
трижды не удалась и стоит разобраться, прежде чем пробовать снова.

Состояние очереди читается запросом `GET /v2/repair`: он отвечает списком работ с
их стадией, числом перестроенных и не перестроенных блоков, числом попыток,
причиной последнего отказа и временем следующей, а также глубиной очереди и общим
режимом.

Режим переключается запросом на `/v2/repair/mode`:

```bash
curl -u ivanov -X PUT https://mhd.example.ru:6006/s3gateway/api/v2/repair/mode   -H 'content-type: application/json' -d '{"mode": "manual"}'
```

В режиме `manual` новые перестройки не начинаются; уже идущие доводятся до конца.
Значение `auto` возвращает обычное поведение. Переключение записывается в журнал
инстанса и в таблицу с именем того, кто его выполнил: вопрос «почему ничего не
восстанавливается» задают через несколько часов и обычно не тот, кто переключал.

Отдельная работа управляется запросом на `/v2/repair/<группа>/<слот>`:

```bash
curl -u ivanov -X PUT https://mhd.example.ru:6006/s3gateway/api/v2/repair/12/3   -H 'content-type: application/json' -d '{"action": "pause"}'
```

| Действие | Что делает |
| --- | --- |
| `pause` | остановить на ближайшей контрольной точке, сохранив позицию |
| `resume` | вернуть приостановленную работу в очередь |
| `cancel` | отказаться от работы; группа возвращается в то же состояние, что и после отказа |
| `retry` | начать заново работу, завершившуюся отказом, обнулив счётчик попыток |

Отдельного «запустить» нет: возобновление приостановленной работы и повторный
запуск неудавшейся — это один и тот же переход, отличающийся только обнулением
счётчика.

Неудавшаяся перестройка повторяется сама: три попытки с паузами в одну минуту,
пять минут и час. После третьей работа остаётся в состоянии отказа и ждёт
человека — дальнейшие автоматические попытки только повторяли бы одну и ту же
ошибку. Причина отказа сохраняется и видна в ответе `/v2/repair`: недоступность
источника, невозможность перестроить блок по сохранившимся фрагментам, ошибка
записи на целевой диск.

### Отличия от спецификации {: #otlichiya_ot_specifikacii }

Описание API управления, принятое в программе испытаний, в трёх местах
расходится с тем, что здесь реализовано, и расхождения намеренные: постраничный
вывод по курсору вместо номеров страниц, набор кодов состояния шире табличного,
базовый путь `/s3gateway/api`. Перечень с обоснованием каждого — в
`doc/dev/CONTROL-API.md`.

## Диагностика типовых ситуаций {: #diagnostika_tipovyh_situacii }

**Плагин не включается, в сообщении приведены две версии.** Несовпадение версии
Picodata и версии библиотеки `picodata-plugin`, с которой собран плагин.
Проверка установки:

```
SELECT name, version, enabled FROM _pico_plugin;
SELECT plugin, name, tiers FROM _pico_service WHERE plugin = 's3r';
```

**Инстанс не запускается, сообщение `has N disk(s) but no listener`.** На
инстансе заданы диски и не задан слушатель `s3r_storage` в конфигурации
Picodata. Отказ предусмотрен: без слушателя диски недоступны остальным узлам.

**Диски не монтируются.** Проверить наличие записи `disk ... mounted` в журнале
инстанса. Отсутствие записи означает недоступность каталога, отсутствие
поддержки `io_uring` или `O_DIRECT` в окружении либо принадлежность диска
другому кластеру; в последнем случае журнал содержит оба идентификатора.

**Группы размещения не создаются.** Проверить ответ `/-/debug/topology` для
нужной формы. Поле `reason` различает причины: `no_disks` — диски не объявлены;
`no_declared_subdomains` — диски есть, но их поддомены отказа не позволяют
собрать безопасную форму; `not_enough_disks` — в указанном ярусе и площадке
недостаточно свободных дисков; `not_enough_instances` — недостаточно
инстансов. Все диски также могут уже входить в группы, если форму кодирования
добавили после начала заполнения кластера.

**Запись возвращает `ServiceUnavailable`.** Ни одна группа размещения не
принимает запись: группы отсутствуют либо каждая из них содержит недоступный
узел.

**Настроен TLS на слушателе `s3r_storage`, плагин не загружается.** Раздел
`tls` задан без `ca_file`. Сертификат подтверждает право узла запрашивать
фрагменты блоков, поэтому цепочка без удостоверяющего центра не принимается;
см. главу
«Шифрование трафика».

**Неясно, шифруется ли обмен фрагментами блоков.** Найдите в журнале инстанса строку
`shard endpoint serving on ...`: она заканчивается либо `over mutual TLS`, либо
`over plaintext; carry it over a trusted network`.

**Растёт время ответа на малых объектах.** Смотреть метрику `s3r_bridge_wait_seconds`
(и `s3r_bridge_queue_depth`): рост времени ожидания в мосту — это то, что двигают
параметры `bridge_queue` и `bridge_fibers` сервиса `s3r_meta`. Заполнение очереди
означает, что поток TX достиг предела пропускной способности, и видно это как рост
глубины очереди раньше, чем как рост задержки запросов.

**Чтения возвращают устаревшие данные.** Проверить параметр
`read_consistency`: значение `eventual` разрешает чтение с реплик и гарантии
«чтение видит запись» не даёт.

## Приложение А. Таблицы плагина {: #prilozhenie_a_tablicy_plagina }

Глобальные таблицы имеют постоянные имена. Таблицы пространства имён создаются
отдельно для каждого арендатора и физически называются
`s3r_t<tenant_id>_<суффикс>`: например, `s3r_t0_object` для арендатора 0 и
`s3r_t7_gc` для арендатора 7. Обозначение `<N>` ниже — числовой
`tenant_id`, а не часть имени таблицы.

| Таблица | Размещение | Содержимое |
| --- | --- | --- |
| `s3r_tenant` | глобальная | арендаторы, домены, состояние, сертификаты и параметры сжатия |
| `s3r_seq` | глобальная | счётчики выдаваемых идентификаторов |
| `s3r_bucket` | глобальная | бакеты: владельцы, права, политика, версионирование, правила жизненного цикла, блокировка объектов, теги |
| `s3r_credential` | глобальная | ключи доступа и сопоставление с пользователями |
| `s3r_quota` | глобальная | ограничения ресурсов |
| `s3r_quota_usage` | шардированная по арендатору | учтённое потребление хранимого объёма и числа объектов |
| `s3r_hash` | шардированная по SHA-256 | индекс совпадающего содержимого для дедупликации |
| `s3r_disk` | глобальная | диски кластера, владельцы, домены отказа, ёмкость |
| `s3r_pg` | глобальная | группы размещения: состав, геометрия, эпоха |
| `s3r_tier` | глобальная | соответствие класса хранения тиру и геометрии |
| `s3r_repair` | глобальная | задания на восстановление потерянного слота группы |
| `s3r_shortfall` | глобальная | части, не принятые при записи и подлежащие дозаписи |
| `s3r_clock` | глобальная | нижняя граница гибридных логических часов репликасета |
| `s3r_scrub_pg` | глобальная | ход проверки данных и чётности в разрезе групп размещения |
| `s3r_t<N>_object` | шардированная | версии объектов: метаданные, теги, блокировка, внутренний способ размещения, класс хранения и карта размещения; `part_no = 0` означает строку целого объекта |
| `s3r_t<N>_dir` | шардированная | каталоги для перечисления с разделителем |
| `s3r_t<N>_mpu` | шардированная | начатые составные загрузки |
| `s3r_t<N>_mpu_part` | шардированная | принятые части составных загрузок |
| `s3r_t<N>_gc` | шардированная | очередь освобождения фрагментов удалённых объектов |
| `s3r_t<N>_dir_gc` | шардированная | очередь проверки опустевших каталогов |
| `s3r_t<N>_siterepl` | шардированная | объекты, которые есть не на всех площадках |
| `s3r_t<N>_quarantine` | шардированная | блоки, восстановить которые не удалось |
| `s3r_t<N>_transition` | шардированная | очередь переходов между классами хранения |
| `s3r_t<N>_hash_pending` | шардированная | очередь обновления индекса дедупликации |
| `s3r_extent` | шардированная по диску | экстенты диска и их состояние |
| `s3r_scrub` | шардированная по диску | состояние фоновой проверки целостности диска |

Таблицы пространства имён распределены по производным от бакета, каталога и
фрагмента ключам; таблицы блокового хранилища — по диску. Они размещаются в тире
Picodata, указанном параметром `storage_tier`. Строки видны запросу SQL,
выполненному на инстансе этого тира.

Доступ к перечисленным таблицам дают связки табличных разрешений
`s3r_table_reader` и `s3r_table_writer`. Их не выдают человеку: они входят в
роли `s3r_observer` и `s3r_superuser` (см. «Ролевая модель арендаторов»).

### Ролевая модель арендаторов {: #rolevaya_model_arendatorov }

Миграции создают три роли. Субъект доступа S3 соответствует пользователю SQL
Picodata, поэтому ролевая модель использует роли Picodata, а не отдельную
таблицу плагина.

Роль выдаётся обычным оператором SQL; оба имени берутся в кавычки, иначе они
приводятся к нижнему регистру:

```
GRANT "s3r_superuser" TO "kosipov";
```

**`s3r_superuser`** — полные полномочия над плагином в кластере: тиры и уровни
избыточности, режим обслуживания, арендаторы и их сертификаты, а также доступ
SQL ко всем таблицам плагина. Роль получает доступ к `s3r_tenant`: её обладатель
создаёт арендаторов и их сертификаты, а также получает список арендаторов и
сведения об их ёмкости с помощью SQL. Это единственная роль с правом чтения
`s3r_tenant`, поскольку она же записывает в таблицу сертификаты.

**`s3r_observer`** — только чтение: ёмкость, состояние кластера и дисков, группы
размещения, восстановление, проверка целостности. Роль для того, кто наблюдает за
кластером и ничего в нём не меняет; без неё такому человеку пришлось бы выдать
полномочия администратора. Секреты наблюдателю недоступны: `s3r_credential`
хранит секретные ключи, `s3r_tenant` — закрытые ключи TLS, и обе таблицы выданы
только `s3r_superuser`.

**`s3r_tenant_admin_<идентификатор>`** управляет пользователями, ключами и
бакетами одного арендатора — того, чей идентификатор указан в имени роли. Такая
роль создаётся для каждого арендатора: само полномочие нельзя выразить табличным
разрешением, потому что `s3r_credential` — глобальная таблица, а разрешение SQL
нельзя сузить до строк одного арендатора. Область действия задаёт выдача роли.

Операции предоставляет API управления. Он принимает маркер доступа OIDC и
арендатора в самом запросе — поэтому именно выданная роль определяет, к какому
арендатору обращение допустимо. Арендатор, роли которого нет, отвечает
«не найдено», а не «запрещено»: ответ «запрещено» подтвердил бы, что такой
арендатор существует.

Роли не наследуют друг друга: если человеку нужны полномочия двух видов, ему
выдают две роли. Имя роли администратора содержит идентификатор арендатора, а не
его имя: идентификатор не переиспользуется после удаления арендатора, поэтому
выданная роль никогда не станет означать другого арендатора, и переименование
арендатора её не ломает.

Ответ на создание или замену ключа содержит секретный ключ доступа только один
раз — больше его не возвращает ни один запрос:

| Запрос | Действие |
| --- | --- |
| `GET /v2/users?tenant_id=<id>` | перечислить пользователей арендатора и их ключи (без секретов) |
| `POST /v2/users` | зарегистрировать пользователя |
| `PUT /v2/users?tenant_id=<id>` | заблокировать или разблокировать пользователей (`state`) |
| `DELETE /v2/users?tenant_id=<id>` | удалить пользователей |
| `POST /v2/credentials?tenant_id=<id>` | выдать ключ доступа |
| `PUT /v2/credentials/<ключ>?tenant_id=<id>` | заменить секрет, сохранив ключ |
| `DELETE /v2/credentials/<ключ>?tenant_id=<id>` | удалить ключ |

Бакет можно передать другому владельцу: `PUT /v2/buckets` с именем бакета и
именем нового владельца, он же — действие «передать» в консоли. Новый владелец
должен быть принципалом того же арендатора. Прежний владелец не сохраняет ничего:
передача, оставляющая ему полный доступ, передачей не является. В ответе назван
тот, кто владение потерял, — больше нигде прежний владелец не записан.

Блокировка действует на пользователя, а не на отдельный ключ: все ключи
пользователя переходят в состояние «отключён» вместе. Операция обратима — ключи
остаются, и разблокировка возвращает то, что было.

`CREATE USER` — полномочие уровня кластера, которое нельзя сузить до арендатора.
Поэтому администратор арендатора не получает это полномочие напрямую:
пользователя Picodata создаёт плагин.

## Приложение Б. Сетевые порты {: #prilozhenie_b_setevye_porty }

| Назначение | Источник значения |
| --- | --- |
| Конечная точка S3 | `instance.plugin.s3r.service.s3r_api.listener` либо `S3R_API_LISTEN` |
| Обмен фрагментами блоков между узлами | `instance.plugin.s3r.service.s3r_storage.listener` |
| Диагностика плагина | порт конечной точки S3, пути `/-/` |

Обмен фрагментами блоков ведётся по протоколу HTTP/2 между узлами кластера.
Соответствующий порт предназначен для внутрикластерного трафика и должен быть
недоступен клиентам.

## Приложение В. Параметры конфигурации {: #prilozhenie_v_parametry_konfiguracii }

Параметры задаются командой `ALTER PLUGIN` и действуют на весь кластер, кроме
отмеченных как инстансные — те задаются в конфигурационном файле Picodata или
переменными окружения.

### `s3r_api` {: #s3r_api }

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `listen` | `127.0.0.1:8000` | адрес конечной точки S3 (инстансный, `S3R_API_LISTEN`) |
| `max_body_bytes` | `268435456` | устаревший параметр для совместимости; не ограничивает размер запроса |
| `region` | `default` | значение, возвращаемое `GetBucketLocation`, и допустимое значение `LocationConstraint` |
| `credentials` | пусто | начальные ключи доступа; при запуске они добавляются в `s3r_credential`, но не удаляют созданные администратором ключи |
| `inline_max` | `4096` | верхняя граница размера объекта класса `inline` |
| `api_memory` | четверть доступной памяти | предел памяти для содержимого объектов в запросах; `0` выбирает предел автоматически |
| `service_timeout_s` | `30` | предельное время ожидания внутренних ресурсов; ожидание данных от клиента не учитывается |
| `diagnostics` | `health` | объём открытой поверхности `/-/`: `health`, `debug`, `bench` |
| `backend` | `picodata` | реализация хранилища; `fs` используется при разработке |
| `fs_root` | — | каталог для `backend = fs` |

### `s3r_meta` {: #s3r_meta }

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `bridge_fibers` | `16` | число волокон, обслуживающих обращения к потоку TX |
| `bridge_queue` | `256` | глубина очереди к потоку TX |
| `read_consistency` | `strong` | `strong` — чтение с мастера; `eventual` — разрешено чтение с реплики |

### `s3r_storage` {: #s3r_storage }

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `disks` | пусто | пути к дискам, их поддомены отказа, ярус (`tier`, по умолчанию `standard`), ёмкость и размер экстента (инстансный, `S3R_DISKS`) |
| `erasure` | пусто | формы кодирования: `k`, `m`, `block_bytes` (по умолчанию 2 МиБ), `tier` |
| `tiers` | пусто | карта классов хранения: `{name, class}` в порядке от наиболее частого к наиболее редкому доступу |
| `write_tolerance` | `1` | сколько фрагментов блока запись вправе оставить недописанными |
| `gc_reclaim_after_s` | `60` | задержка перед освобождением фрагментов удалённого объекта |
| `dirgc_grace_s` | при `0`: `max(2, 2 × service_timeout_s)`, сейчас 60 с | выдержка перед проверкой опустевшего каталога; ненулевое значение задаёт её явно |
| `orphan_grace_s` | `86400` | возраст запечатанного экстента, с которого проверяются контрольные суммы и удаляются фрагменты без строки объекта |
| `mpu_abandon_after_s` | `604800` | срок, после которого заброшенная составная загрузка отменяется |
| `scrub_staleness_s` | `604800` | наибольший допустимый возраст полной проверки данных и чётности группы размещения |
| `compact_live_percent` | `50` | доля живых данных, ниже которой экстент уплотняется |

`block_bytes` по умолчанию — 2 МиБ. Форма кодирования, под которой уже есть
данные, не изменяется: изменение отклоняется при загрузке конфигурации.

Значения `gc_reclaim_after_s`, `dirgc_grace_s` и `orphan_grace_s` — не
периоды опроса, а границы корректности. Каждое из них задаёт, сколько нужно
подождать, чтобы отличить незавершённую работу от несделанной. Уменьшение до
нуля допустимо только в испытательном контуре.

## Приложение Г. Глоссарий {: #prilozhenie_g_glossarii }

В названиях операций, параметров, заголовков и состояний сохранены обозначения
из API Amazon S3 и интерфейсов Picodata. В пояснительном тексте используются
русские термины, принятые в документации S3-совместимых хранилищ.

В русскоязычных руководствах для термина *bucket* встречаются варианты
«бакет», «корзина» и «сегмент». В этом документе используется наиболее
распространённый среди S3-совместимых российских сервисов термин **бакет**.

| Термин | Обозначение в API или коде | Определение |
| --- | --- | --- |
| Арендатор | tenant, `s3r_tenant` | Изолированное пространство имён S3 в одном кластере. В именах таблиц, параметров и ролей используется английское обозначение `tenant`. |
| Бакет | bucket | Контейнер объектов S3. Бакет имеет уникальное имя в пределах арендатора и собственные настройки доступа, версионирования и жизненного цикла. |
| Блок | block | Единица разбиения содержимого крупного объекта перед избыточным кодированием. Размер задаётся параметром `block_bytes`. |
| Версионирование | versioning | Режим, в котором бакет хранит несколько версий объекта с одним ключом. |
| Восстановление | repair | Создание утраченного фрагмента на другом диске по сохранившимся данным и фрагментам чётности. В именах процесса, таблиц и метрик используется обозначение `repair`. |
| Группа размещения | placement group, PG | Упорядоченный набор дисков одной площадки с фиксированной схемой репликации или избыточного кодирования. |
| Домен отказа | failure domain | Группа компонентов, которые могут отказать одновременно, например узел, стойка или площадка. Фрагменты одного блока размещаются в разных доменах отказа. |
| Доступность для чтения | readability | Возможность восстановить содержимое блока из имеющихся фрагментов. Для чтения требуется не менее `k` фрагментов. |
| Избыточное кодирование | erasure coding, EC | Разделение блока на `k` фрагментов данных и `m` фрагментов чётности. Позволяет восстановить блок при потере не более `m` фрагментов. |
| Идентификатор ключа доступа | Access Key ID, `access_key` | Открытая часть учётных данных S3, которая указывает, каким ключом подписан запрос. |
| Инстанс | instance | Экземпляр процесса Picodata. На одном физическом узле может работать несколько инстансов. |
| Кворум записи | write quorum | Минимальное число дисков, которые должны подтвердить запись блока. |
| Класс хранения | storage class, `x-amz-storage-class` | Атрибут S3, который клиент выбирает при записи объекта. В s3r класс хранения сопоставляется с ярусом хранения. |
| Ключ объекта | object key | Имя объекта внутри бакета. Символ `/` в ключе может использоваться для логического представления каталогов. |
| Конечная точка S3 | S3 endpoint | Адрес HTTP(S), на который клиент отправляет запросы S3. |
| Кэш | cache | Данные в оперативной памяти, повторное получение которых из основного источника не требуется до их изменения. |
| Квота | quota | Изменяемое администратором ограничение для арендатора, пользователя или бакета. Не следует смешивать с техническим пределом реализации. |
| Маркер удаления | delete marker | Специальная версия, которую S3 создаёт при удалении объекта из бакета с включённым версионированием. |
| Межплощадочная репликация | site replication | Асинхронное копирование объекта между площадками одного кластера. |
| Метаданные | metadata | Сведения об объекте или бакете, не являющиеся содержимым объекта: ключ, размер, тип содержимого, теги и другие атрибуты. |
| Ограничение частоты запросов | rate limiting | Ограничение числа запросов за единицу времени. Для ограничения объёма передаваемых данных используется термин «ограничение скорости передачи». |
| Предподписанная ссылка | presigned URL | URL с подписью SigV4 и сроком действия, который предоставляет ограниченный доступ без передачи секретного ключа. |
| Пространство имён | namespace | Совокупность бакетов, ключей, версий и связанных метаданных, доступных арендатору. |
| Репликация | replication | Хранение нескольких полных копий данных. Не следует смешивать с избыточным кодированием. |
| Секретный ключ доступа | Secret Access Key, `secret_key` | Закрытая часть учётных данных S3, используемая для вычисления подписи SigV4. |
| Составная загрузка | multipart upload, MPU | Загрузка объекта отдельными частями с последующей операцией завершения. Названия операций `CreateMultipartUpload`, `UploadPart` и `CompleteMultipartUpload` не переводятся. |
| Сохранность данных | durability | Вероятность того, что записанные данные не будут безвозвратно утрачены. Не следует смешивать с доступностью сервиса. |
| Субъект доступа | principal | Пользователь или группа, которым правило доступа разрешает или запрещает действие. |
| Тир Picodata | Picodata tier | Группа инстансов Picodata, на которой размещаются сервисы и таблицы. Тир Picodata и ярус хранения s3r — разные понятия. |
| Фоновая проверка целостности | scrub | Сопоставление данных и фрагментов чётности в группах избыточного кодирования, выполняемое независимо от клиентских чтений. Проверку контрольных сумм записей при обходе экстентов выполняет процесс `orphan`. |
| Фрагмент блока | shard | Часть блока после репликации или избыточного кодирования. Не следует смешивать с шардом vshard. В именах протокола и метрик сохранено слово `shard`. |
| Шард vshard | vshard shard | Единица распределения строк шардированных таблиц Picodata. |
| Экстент | extent | Файл фиксированного размера в хранилище блоков, содержащий множество записей с фрагментами. |
| Ярус хранения | storage tier, `tier` | Группа дисков с одинаковыми эксплуатационными характеристиками. Ярус сопоставляется с одним классом хранения S3. |
