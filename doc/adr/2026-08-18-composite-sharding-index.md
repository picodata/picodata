# Составной индекс распределения для шардированных таблиц

## Контекст

В каждой шардированной таблице Picodata хранит служебную колонку `bucket_id`.
Ее значение вычисляется по ключу распределения. Функция вычисления может быть
задана плагином, поэтому SQL не знает ее свойств.

Сейчас для `bucket_id` обычно создается отдельный индекс. Его основная задача —
найти строки бакета при ребалансе vshard. Селективности обычных SQL-запросов он
почти не помогает.

Например, для таблицы

```sql
CREATE TABLE t (
    a INTEGER PRIMARY KEY,
    b INTEGER
) DISTRIBUTED BY (b);
```

условие `b = 42` позволяет вычислить номер бакета. Но индекс `(bucket_id)`
находит весь бакет, а условие по `b` остается фильтром. В большом бакете придется
проверить много строк. Для диапазона по `b` нельзя вычислить небольшой набор
бакетов: произвольная хэш-функция не обязана сохранять порядок значений.

Добавлять `bucket_id` в каждый первичный ключ тоже нельзя. Для
`PRIMARY KEY (a) DISTRIBUTED BY (b)` это изменит физический ключ и ухудшит
доступ по `a`. Связывать `bucket_id` нужно с ключом распределения, из которого
он вычислен.

## Решение

Для новых шардированных таблиц индекс распределения начинается с
`(bucket_id, <ключ распределения>...)`.

| Схема таблицы | Физический первичный индекс | Отдельный индекс распределения |
|---|---|---|
| Ключ распределения — префикс первичного ключа (PK) | `(bucket_id, PK...)` | Нет |
| Ключ распределения не является префиксом PK | PK без изменений | `(bucket_id, <ключ распределения>...)` |
| Явный PK уже начинается с bucket_id | Явный PK | Нет |

Отдельный индекс распределения не уникален. Он используется SQL и vshard.

Если ключ распределения является префиксом PK, добавление `bucket_id` не меняет
смысл уникальности: одинаковый PK всегда имеет одинаковый `bucket_id`. В этом
случае отдельный индекс не нужен.

Если ключ распределения не является префиксом PK, первичный индекс остается
прежним. Например:

```sql
PRIMARY KEY (a) DISTRIBUTED BY (b)
```

создает первичный индекс `(a)` и индекс распределения `(bucket_id, b)`.

### Синтаксис

Направление частей индекса распределения задается в `DISTRIBUTED BY`:

```sql
DISTRIBUTED BY (
    [bucket_id [ASC | DESC],]
    column_1 [ASC | DESC],
    ...
)
```

`bucket_id` здесь — служебный маркер. Он не входит в аргументы функции
распределения.

Правила направлений:

- направление `bucket_id` по умолчанию — `ASC`;
- при объединении с PK пропущенное направление колонки наследуется из PK;
- если направления одной колонки в PK и `DISTRIBUTED BY` явно различаются,
  создание таблицы завершается ошибкой;
- в отдельном индексе пропущенное направление колонки означает `ASC`;
- при переиспользовании старого явного PK направление `bucket_id` сохраняется.

Если `DISTRIBUTED BY` не указан, ключ распределения по-прежнему выводится из PK.
Физический первичный индекс получает вид `(bucket_id ASC, PK...)`.

## Выполнение запросов

### Равенство и `IN`

Для равенства по полному ключу распределения Picodata вычисляет точный
`bucket_id`. Поиск использует обе части индекса:

```text
(bucket_id = hash(42) AND b = 42)
```

Для `IN` нужно сохранять связь между значением и его бакетом:

```text
(bucket_id = hash(42)  AND b = 42)
OR
(bucket_id = hash(666) AND b = 666)
```

Независимые условия `bucket_id IN (...)` и `b IN (...)` создают лишние
комбинации и не используются.

### Диапазон

Для диапазона по ключу распределения Picodata не может заранее ограничить
набор бакетов. Если запрос идет по всем бакетам, пользователь должен явно
выбрать индекс распределения и принудительно включить skip scan:

```sql
INDEXED BY "<индекс распределения>" USING SKIP SCAN
```

Автоматически этот индекс пока не выбирается: в Tarantool нет статистики,
необходимой для сравнения стоимости skip scan и полного сканирования. Без
указанной конструкции сохраняется обычное поведение планировщика.

Например, для индекса `(bucket_id, b)` skip scan перебирает локальные бакеты,
оставшиеся после фильтра по `bucket_id`, и в каждом ищет заданный диапазон
значений `b`. Сравнение идет по обычным правилам типа `b`. Поэтому этот способ
работает с `datetime`, `text` и другими типами и не требует упорядоченной
хэш-функции.

Если для запроса известен набор бакетов, вместе со skip scan добавляется фильтр
`bucket_id IN (...)`. Тогда поиск идет только по этим бакетам.

Если выбранный индекс нельзя применить, подготовка запроса завершается ошибкой.

Если PK и ключ распределения различаются, условия по PK продолжают использовать
первичный индекс. Условия по ключу распределения используют составной индекс
распределения.

В `EXPLAIN` должны быть видны выбранный индекс, набор бакетов и использование
skip scan. Способ доступа, идентификатор и версия индекса входят в ключ кэша
локального плана.

## Частично упорядоченная функция распределения

Для конкретного типа можно построить функцию, которая частично сохраняет
порядок. Тогда по границам диапазона значений можно было бы получить часть
бакетов без skip scan.

Общий механизм пока не определен:

- функция распределения может быть произвольной и задаваться плагином;
- порядок должен совпадать с правилами сравнения каждого типа и каждой части
  ключа;
- составные ключи и направления `ASC` и `DESC` усложняют такой контракт;
- сохранение порядка может ухудшить равномерность распределения данных;
- Picodata не умеет получать и проверять такие свойства функции.

Этот вариант не запрещается, но не входит в текущее решение. Для него нужен
отдельный интерфейс и отдельное исследование.

## Совместимость

Существующие таблицы не перестраиваются. В метаданных таблицы нужно различать
три устройства:

- старый отдельный индекс `(bucket_id)`;
- первичный индекс как индекс распределения;
- отдельный составной индекс распределения.

Старый явный `PRIMARY KEY (bucket_id, ...)` продолжает работать. Если его начало
совпадает с `(bucket_id, <ключ распределения>...)`, он используется как индекс
распределения. Иначе создается отдельный составной индекс.

Семантика `PRIMARY KEY (a) DISTRIBUTED BY (b)` не меняется: уникальность `a`
остается локальной для экземпляра. Возможные ограничения такой уникальности при
ребалансе должны рассматриваться отдельно.

## Последствия

- Точное условие по ключу распределения не сканирует весь бакет.
- Диапазон может использовать индекс вместо полного сканирования таблицы.
- Если ключ распределения является префиксом PK, отдельный индекс не хранится.
  Это особенно важно для vinyl.
- Если ключи различаются, доступ по PK и правила его уникальности не меняются.
- Отдельный индекс становится шире и занимает больше места.
- Skip scan делает поиск для каждого бакета, оставшегося после фильтра. На
  широком диапазоне он может быть дороже полного сканирования, но в рамках этого
  решения используется принудительно.

## Рассмотренные варианты

### Всегда добавлять `bucket_id` в PK

Не подходит для таблиц, у которых PK и ключ распределения различаются. Такое
устройство меняет уникальность и требует skip scan даже для обычного доступа по
PK.

### Оставить отдельный индекс только по `bucket_id`

Подходит для vshard, но почти не повышает селективность SQL-запросов. После
поиска бакета все равно нужно проверять строки по ключу распределения.

### Добавлять все бакеты в условие запроса

Условие `bucket_id IN (<все бакеты>)` увеличивает локальный план и описывает
перебор хуже, чем специальный skip scan. Подстановка `bucket_id` остается только
для заранее вычисленных бакетов.

## Проверка решения

Нужны проверки для следующих случаев:

- ключ распределения совпадает с PK, является его префиксом или не входит в
  его начало;
- простой и составной ключ распределения;
- направления `ASC`, `DESC`, их наследование и конфликт;
- равенство, `IN`, узкие и широкие диапазоны;
- skip scan по всем бакетам и по заданному набору бакетов;
- неполное условие по составному ключу распределения;
- `SELECT`, `UPDATE`, `DELETE`, соединения и явно выбранный индекс;
- отображение индекса, бакетов и skip scan в `EXPLAIN`;
- memtx, vinyl и перенос бакетов vshard;
- старые таблицы со всеми поддерживаемыми устройствами индекса.

Измерения должны сравнивать старый прямой диапазон, skip scan и полное
сканирование. Ожидаемая цена skip scan — дополнительный поиск для каждого
выбранного бакета.
