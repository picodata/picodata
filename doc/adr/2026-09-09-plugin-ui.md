# Подключаемые страницы WebUI для плагинов Picodata

## Контекст и постановка проблемы

Встроенный WebUI Picodata (`webui/`) — это React SPA, которое собирается один раз, во время сборки picodata, в единый JSON-бандл и встраивается в бинарник picodata через `include_str!`. При старте `start_webui()` (`src/lib.rs`) проходит по этому бандлу и регистрирует по одному маршруту `pico.httpd` на каждый файл, плюс три жёстко заданных SPA-фолбэк маршрута: `/`, `/nodes*path`, `/login*path`. Клиентский роутинг устроен так же жёстко: `Routes` (`webui/src/shared/router/config.ts`) — это закрытый enum (`LOGIN`, `NODES`, `USERS`), `Router.tsx` статически делает `import()` одного модуля на маршрут, а левая панель навигации (`SideMenu.tsx`) рендерит массив `navLinks` (сейчас там только «Instances»). Каждая страница, маршрут и пункт навигации известны уже на этапе компиляции самой picodata.

Плагины picodata устроены прямо противоположным образом: это shared-библиотеки (`.so`), которые обнаруживаются и (пере)загружаются динамически во время работы кластера (`src/plugin/manager.rs`), версионируются независимо и устанавливаются из директории `share_dir/<plugin>/<version>/`, содержащей `manifest.yaml` и миграции. SDK `picodata_plugin` даёт сервису плагина ровно одну точку интеграции по HTTP/TCP — `PicoListener` (`crates/picodata-plugin/src/transport/listener.rs`), сырой слушающий сокет, который сервис поднимает на своём собственном настроенном адресе. Доступа к `pico.httpd`, раздачи статических файлов и вообще какого-либо понятия «страницы» в API плагинов нет. Плагину, которому нужен хоть какой-то UI в браузере, сегодня приходится поднимать полностью отдельный HTTP-сервер на своём порту, со своим TLS, своей стилизацией и, что важнее всего, своей собственной аутентификацией — вне WebUI picodata.

**Формулировка проблемы**: как позволить плагину picodata поставлять одну или несколько страниц, которые появляются пунктами в левой панели навигации WebUI, маршрутизируются внутри уже существующего SPA (без отдельного origin/порта, о котором должен знать пользователь), и добавляются/убираются автоматически по мере установки/включения/выключения/обновления плагина — без пересборки ядра picodata и без требования жёстко фиксировать версии инструментария сборки WebUI (React/MUI/Vite) между независимо выпускаемыми плагинами.

## Прецедент в существующем плагине: kirovets-ng

Прежде чем перечислять варианты, стоит зафиксировать, что задача уже стихийно решена — без какой-либо поддержки со стороны picodata — в плагине `kirovets-ng`. Это уже работающий в проде обходной путь, и он наглядно показывает, зачем нужен официальный механизм, а заодно — каких конкретных ошибок он должен избежать.

- Фронтенд плагина (`front/`) — отдельное React 18 SPA на Vite со своим роутером (`react-router-dom`, `<Router basename="/config">`) и своим заголовком/навигацией, полностью независимое от `webui/` ядра picodata.
- Сборка фронтенда (`vite.config.ts`, локальный Vite-плагин `generateBuildFolder`) обходит выходную директорию и сериализует все файлы в `dist/ui/bundle.json` в формате `{ [filename]: { body, mime, is_entry } }` — что почти дословно совпадает с форматом, который `build.rs`/`start_webui()` уже используют для основного бандла WebUI (см. раздел «Доставка и раздача статических ассетов плагина» ниже). То есть схема «статический бандл → раздача через `pico.httpd`» уже возникла органически, как единственный способ, которым автор плагина смог доставить свой UI в браузер.
- Rust-код плагина (`src/ui/mod.rs`) встраивает `dist/ui/bundle.json` через `include_bytes!` и регистрирует маршруты напрямую вызовом `pico.httpd:route(...)`.
- Обновление конфигурации сервиса требует ручного снятия старых маршрутов перед регистрацией новых: плагин тащит с собой собственный Lua-модуль (`src/lua_module/functions/http.rs`) с функцией `remove_routes`, которая напрямую лезет в таблицы `httpd.routes`/`httpd.iroutes` и перезапускает httpd. Это хрупкий паттерн там, где нужен штатный механизм жизненного цикла маршрутов.
- Регистрация UI-маршрутов (`start_webui()`) вызывается из `init()`/`on_start` сервиса `router` — единственного сервиса, которому исторически поручили эту обязанность, вперемешку с инициализацией метрик, RPC-сервера аутентификации и уборщика сессий. Необходимо, чтобы новый UI появился на всем кластере, а не на особенных выделенных узлах - хотя бы потому что UI может быть закрыт reverse proxy с round robin балансировкой
- Самое показательное: чтобы получить рабочий UI без интеграции с сессией/JWT picodata, тот же `init()` выполняет `sql::query("ALTER SYSTEM SET jwt_secret = ''")` с комментарием `// Disable authorization for WebUI` — то есть **глобально отключает аутентификацию всего кластера**, лишь бы страница плагина открывалась без логина. Это ослабление защиты всего picodata ради обхода отсутствия способа переиспользовать сессию хоста.
- Стилистически фронтенд плагина собран на Tailwind CSS + Radix UI (паттерн shadcn/ui, каталог `src/components/ui/*`), тогда как ядро WebUI picodata использует MUI + Emotion (`webui/src/shared/theme`). При этом автор плагина уже вручную скопировал фирменные цвета picodata в виде hex-литералов прямо в JSX — `bg-[#F3EEE9]` в `App.tsx` и `bg-[#323232]` в `Header.tsx` — это ровно значения `background.default` и `common.colors.bg.colorBgGray` из `webui/src/shared/theme/theme.ts`, продублированные вручную, без единого источника истины.

`kirovets-ng` это готовый пилотный кейс для миграции: его текущая директория `front/` и `dist/ui/bundle.json` почти один в один ложатся на предлагаемую ниже директорию `webui/` и декларативную регистрацию страниц, а две ссылки его самодельного `Header.tsx` становятся двумя записями в манифестном `webui:` — с отказом от самостоятельной навигации в пользу единой левой панели WebUI.

## Цели

- Плагин декларирует свои страницы; после установки и включения плагина эти страницы появляются в левой панели навигации без пересборки ядра picodata.
- Выключение/удаление плагина убирает его пункты навигации и маршруты; обновление плагина подменяет ассеты новой версии без ловушки в виде устаревшего кеша.
- Страница плагина — полноценная часть SPA, а не iframe на чужой origin, хотя изоляция при желании остаётся доступной.
- Страницы плагинов переиспользуют уже существующую JWT-сессию WebUI — тот же токен, который `Protected.tsx` уже требует у каждого маршрута ядра, и та же ось `axios`-интерцептора (`webui/src/shared/api/client/axios.ts`).
- От авторов плагинов не требуется переходить на строго те же версии React/MUI/сборочных инструментов, что использует сама picodata.

## Не цели

- Серверный рендеринг страниц плагинов, SEO — WebUI это аутентифицированная админ-консоль.
- Полноценный UX «маркетплейса плагинов» (рейтинги страниц, скриншоты и т.п.) — вне рамок, эта ADR только про механизм доставки/монтирования.

## Архитектура решения

Решение раскладывается на три во многом независимых вопроса: как UI-ассеты плагина физически попадают в браузер, как они монтируются внутри host-SPA, и как host обнаруживает, какие страницы вообще существуют. Ниже описана выбранная схема для каждого из них. Рассмотренные, но отклонённые альтернативы вместе с причинами отказа собраны отдельно, в разделе [«Отклонённые альтернативы»](#отклонённые-альтернативы) в конце документа.

### Доставка и раздача статических ассетов плагина

Плагины уже распаковываются на диске на каждом инстансе как `share_dir/<plugin>/<version>/...` рядом с `manifest.yaml`, `.so` и миграциями. Статика плагинного UI (небольшой набор файлов JS/CSS/ассетов — по сути то же самое, что `kirovets-ng` уже сегодня кладёт в `dist/ui/`, см. «Прецедент» выше) поставляется вместе в составе плагина - бандл оказывается по пути `share_dir/<plugin>/<version>/assets/webui/`.

`pico.httpd` получает один статический маршрут на весь **плагин** в целом (а не на каждый сервис в отдельности — страницы декларируются на уровне плагина под префиксом `/plugin-ui/<plugin>/<version>/*`, который резолвится в файлы `share_dir/<plugin>/<version>/assets/webui/` на диске. Маршрут регистрируется, когда плагин включается, и снимается, когда плагин выключается или удаляется. Сегмент версии в пути означает, что обновление — это просто «новые маршруты для новой версии», а маршруты старой версии убираются вместе с ней, чтобы не придумывать собственный механизм инвалидации кеша.

Всё остаётся в одном origin — тот же TLS/сертификат, что и у остального WebUI, никакого CORS и никакого reverse-proxy; ассеты путешествуют вместе с пакетом плагина, который оператор и так устанавливает и распространяет.

### Регистрация страниц: `webui` как отдельная сущность манифеста

Страницы не являются полем внутри сервиса — они декларируются как самостоятельная сущность манифеста, на одном уровне со `services`:

```yaml
name: example
version: 1.2.0
services:
  - name: my-service
    description: business logic service
    default_configuration: {}
webui:
  - slug: dashboard          # -> /plugin/example/dashboard
    title: dashboard.title   # i18n-ключ — см. «Локализация» ниже
    entry: dist/page.js      # ES-модуль, определяющий custom element
    auth: cluster              # опционально, по умолчанию cluster; plugin — если страница сама управляет доступом, см «`auth: plugin`» ниже
migration: []
```

Причины держать `webui` на уровне плагина, а не внутри конкретного сервиса:
- **Страница — не свойство сервиса, а свойство плагина.** Она раздаётся `pico.httpd` того инстанса, на котором вообще есть WebUI-трафик, независимо от того, на каких тирах развёрнут тот или иной сервис плагина — у страницы нет причин существовать или не существовать в зависимости от того, докатился ли конкретный сервис до конкретного тира.
- **Разный жизненный цикл.** Сервисы включаются/добавляются на тиры по отдельности (`ALTER PLUGIN ... ADD SERVICE ... TO TIER`); у плагина в целом при этом есть свой, более грубый переключатель — включён он в кластере или нет. Именно к этому, плагинному, а не сервисному, переключателю естественно привязать регистрацию/снятие маршрутов `/plugin-ui/...` — ядру нужно продумать (при необходимости — завести) точку входа «плагин включён», симметричную уже существующему `PluginDisabled`. Это прямо устраняет паттерн, замеченный в `kirovets-ng` (см. «Прецедент» выше), где регистрация UI-маршрутов оказалась вморожена в `on_start` одного конкретного сервиса (`router`) вперемешку с несвязанной логикой и никогда не снималась в `on_stop`.
- Никакого нового императивного Rust API в `picodata_plugin` не требуется — регистрация страниц это чистые данные, которые ревьюятся так же, как и всё остальное в манифесте плагина, и легко валидируются при установке (уникальность `slug`, существование файла `entry`).

Ядро парсит секцию `webui` вместе с остальным `manifest.yaml` при загрузке плагина и хранит получившийся список страниц как часть состояния плагина в целом, **в том порядке, в котором записи перечислены в `webui:`** — этот порядок сохраняется и в ответе эндпоинта (см. «Место в навигации: вложенный список по плагину» ниже). Новый эндпоинт, `GET /api/v1/plugin-ui/pages`, возвращает объединённый список `{plugin, slug, title, entry, version, auth}` по страницам всех сейчас *включённых* плагинов, кластерно (источник — `_pico_plugin`); состав списка зависит от того, прошёл ли сам запрос аутентификацию — см. «`auth: plugin`» ниже. Поле `version` — это версия самого плагина — SPA использует именно его, чтобы построить URL ассетов `entry` (`/plugin-ui/<plugin>/<version>/<entry>`) и имя custom element'а (см. «Монтирование страницы в SPA» ниже); без этого поля SPA не может собрать ни то, ни другое. Поле `auth` — то же значение, что и в манифесте (`cluster`/`plugin`) — SPA использует его, чтобы решить, в какую ветку дерева `react-router` монтировать конкретную страницу, см. ниже. Не путать с версией контракта `webuiSdk` — см. «Версионирование» ниже.

Страницы доступны любому аутентифицированному пользователю WebUI на тех же условиях, что и страницы самого ядра: маршрут монтируется внутри того же обёрточного роутера `Protected` (`webui/src/App/Router/Protected.tsx`), который уже сегодня требует валидного JWT (`tokens.auth` из `useSessionStore`) для любого маршрута ядра. Это поведение по умолчанию (`auth: cluster`); единственное осознанное исключение из него — необязательное манифестное поле `auth: plugin` у отдельной записи `webui:`, разбираемое ниже. Более тонкая, ролевая видимость пунктов навигации плагина стала бы возможной только после того, как в самом WebUI появится хоть какая-то модель ролей/привилегий за пределами сегодняшнего бинарного «залогинен/не залогинен» — этой модели пока не существует, и эта ADR сознательно не решает её.

#### Место в навигации: вложенный список по плагину

Страницы плагина не рассыпаются по одному в общий плоский список `SideMenu` наравне с «Instances»/«Users» — они группируются под одним пунктом верхнего уровня, подписанным именем плагина (поле `plugin` из ответа `GET /api/v1/plugin-ui/pages`, то есть `name` из `manifest.yaml` этого плагина), который разворачивается во вложенный список страниц этого плагина. На примере `kirovets-ng`: верхний уровень `SideMenu` — «Instances» (ядро) и «Kirovets-ng» (плагин), а бывшие «Config»/«Tables» из его самодельного `Header.tsx` (см. «Прецедент» выше) — не рядом с «Instances», а вложены под «Kirovets-ng». Пункт-группа плагина рендерится, только если у плагина осталась хотя бы одна страница, видимая при текущем состоянии аутентификации (см. «Навигация для неаутентифицированного посетителя» ниже) — плагин без ни одной видимой страницы не появляется в меню вовсе, ни как группа с пустым списком, ни как-либо ещё.

SPA рендерит дочерний список плагина строго в том порядке, в котором его страницы пришли в ответе `GET /api/v1/plugin-ui/pages` (ядро обязано сохранять на сериализации порядок объявления в `webui:`). Порядок самих групп-плагинов друг относительно друга — алфавитный, по имени плагина. Группы плагинов идут в `SideMenu` после пунктов ядра («Instances»/«Users»), не вперемешку с ними.

Группировка — чисто визуальный слой `SideMenu`, на пространство маршрутов не влияет: URL страницы плагина остаётся плоским `/plugin/<plugin>/<slug>` (см. «Монтирование страницы в SPA» ниже), у группы нет собственного маршрута и собственного сегмента пути.

#### `auth: plugin` — страница с собственной, не завязанной на WebUI аутентификацией

Части плагинов host-JWT не просто не нужен, а мешает: их страница обслуживает не операторов кластера, которые и так логинятся в WebUI picodata, а собственных конечных пользователей плагина с отдельной, уже существующей моделью аутентификации. Пример уже сегодня — `kirovets-ng`: интеграция с корпоративным Keycloak, отдельный OIDC-флоу — это не обходной путь, а содержательная функциональность плагина, обслуживающая пользователей, у которых нет и не должно быть причин заводить учётку picodata только ради одной страницы плагина. 
Требовать от них логин в WebUI поверх уже существующего Keycloak — плохое решени.

Для такого случая запись в `webui:` может нести `auth: plugin`: маршрут `/plugin/<plugin>/<slug>` для этой конкретной страницы монтируется без обёртки `Protected`, то есть без требования сессии WebUI. Ответственность за то, кто вообще видит контент, целиком переходит на сам custom element плагина — он обязан сам, до показа любых данных, выполнить собственную проверку аутентификации (для `kirovets-ng` — уже существующий Keycloak-флоу, включая редирект на `begin_auth` для неаутентифицированного посетителя) и сам решить, показывать ли что-либо до её прохождения. Поле принадлежит странице, а не плагину целиком: в рамках одного и того же плагина одна запись `webui:` вполне может остаться на `auth: cluster` (например, техническая страница только для операторов кластера), а другая — перейти на `auth: plugin`.

Важно не путать `auth: plugin` с обходным путём вроде `ALTER SYSTEM SET jwt_secret = ''` у `kirovets-ng` — `auth: plugin` — способ окончательно убрать такие обходные пути, не жертвуя при этом собственной, полноценной моделью auth, которая у плагина уже есть, и не расширяя это ослабление на весь кластер.

Адрес страницы (`/plugin/<plugin>/<slug>`) и сам механизм монтирования — загрузка `entry`, `customElements.define()`, имя тега с версией, контекст `webuiSdk` (см. «Монтирование страницы в SPA» выше) — от значения `auth` никак не зависят и не меняются: оба поля манифеста (`cluster`/`plugin`) приводят к одному и тому же способу собрать и смонтировать custom element. Меняется только то, какая обвязка вокруг него рендерится на стороне host — обёртка `Protected` и состав `SideMenu`, разобранные ниже.

##### Навигация для неаутентифицированного посетителя

Чтобы пункт `auth: plugin`-страницы вообще был кликабелен без логина, недостаточно снять `Protected` с одного её маршрута — сама панель навигации, `SideMenu`, и общий каркас страницы, `MainLayout` (`webui/src/shared/ui/layout/Main/MainLayout.tsx`), сегодня целиком вложены в `Protected` (`webui/src/App/Router/Router.tsx:37-51`), точно так же, как и защищённые страницы ядра. Дерево `react-router` расширяется третьей веткой, структурно параллельной существующей ветке `/login` (`Router.tsx:54-71`): `MainLayout` без обёртки `Protected`, содержащей только маршруты `auth: plugin`-страниц. Иными словами, у `auth: plugin`-страницы по-прежнему есть `SideMenu`/`Header` — просто без входа через `Protected`.

`SideMenu` при этом — layout-обёртка вокруг `<Outlet />` (`MainLayout.tsx:8-19`): у неё нет собственного URL, она просто рендерится вокруг того дочернего маршрута, который сейчас активен в дереве. Из этого следует, что у новой, неаутентифицированной ветки нет ни `index`-маршрута (`/`), ни catch-all вроде `*` — в ней перечислены только конкретные пути `auth: plugin`-страниц, по одному на запись из ответа `GET /api/v1/plugin-ui/pages`. Если анонимный посетитель зайдёт на голый `/` или на любой путь вне этого списка, он не попадёт в эту ветку — сработает существующий catch-all `*` внутри `Protected` (`Router.tsx:31-34`) и уведёт его на `/login`. То есть анонимный вход возможен только по прямой ссылке на конкретную, заранее известную `auth: plugin`-страницу — с неё, уже увидев отфильтрованный `SideMenu`, можно перейти на другие доступные без логина страницы, но «открыть меню с нуля» с домашнего адреса нельзя.

Список пунктов в `SideMenu` при этом не один и тот же для всех: анонимный запрос к `GET /api/v1/plugin-ui/pages` (без заголовка `Authorization` или с невалидным токеном) не отклоняется 401-м, а получает урезанный ответ — только записи с `auth: plugin`; запрос с валидным JWT получает полный список, как и сегодня. Раскрытия сверх того, что и так открыто анонимно по прямой ссылке, это не создаёт — список лишь делает уже доступные страницы обнаружимыми через меню, а не только по прямой ссылке. Группа-пункт плагина (см. «Место в навигации: вложенный список по плагину» выше) наследует эту же фильтрацию: если после урезания у плагина не осталось ни одной страницы, его группа не рендерится вовсе; если осталась хотя бы одна `auth: plugin`-страница, группа показывается, но только с ней, без остальных `auth: cluster`-страниц того же плагина, которые анонимному посетителю по-прежнему не видны. Симметрично, `SideMenu` показывает пункты «Instances»/«Users» только при наличии токена (сегодня они в `SideMenu.tsx` захардкожены безусловно — это меняется вместе с остальным); для анонимного посетителя в меню остаются только ссылки из урезанного списка. `Header` (`webui/src/shared/ui/Header/Header.tsx`) для такого посетителя уже сегодня штатно деградирует до плейсхолдера `"Cluster ID"` вместо реального имени кластера, потому что `useClusterInfo()` не получает данных без токена, — новой доработки это не требует.

На сервере это требует нового варианта авторизации. Сегодня единственный существующий примитив — `auth_middleware` (`src/http_server/auth.rs:273-280`) — всё-или-ничего: при включённой в кластере аутентификации отсутствующий или невалидный заголовок сразу возвращает ошибку, до хендлера дело не доходит (см. использование в `cluster.rs:577-587`, `instance.rs:101`). Для `GET /api/v1/plugin-ui/pages` заводится параллельный вариант — условно `auth_middleware_optional` — который не ошибается на отсутствующем/невалидном токене, а прокидывает в хендлер `Option<AuthContext>` (`None` для анонима); хендлер уже сам фильтрует список страниц по полю `auth`, когда контекста нет. Остальные существующие ручки (`tiers`, `cluster`, `memory`, `instance`, ...) не меняются и не затрагиваются — они остаются защищены прежним, строгим `auth_middleware`; `auth_middleware_optional` не ослабляет их задним числом, а остаётся отдельным, явно запрашиваемым выбором для нового кода — сначала для этого эндпоинта, а затем и для FFI-функции `picodata_plugin`, см. «Валидация WebUI-сессии в бэкенде плагина» ниже.

WebUI SPA запрашивает список страниц не один раз при старте, а периодически — тем же способом, каким уже опрашиваются остальные кластерные данные ядра, через общий hook `useQueryConfig` (`webui/src/shared/api/hooks/useQueryConfig.ts`), оборачивающий `react-query`'s `refetchInterval` поверх той же авторизованной оси `axios`, что и остальные запросы. У большинства существующих запросов на этом hook'е (кластер, тиры, пользователи, роли) интервал по умолчанию — 10 секунд (`defaultRefetchInterval`, `useQueryConfig.ts`); поскольку включение, выключение и обновление плагина — осознанное, нечастое административное действие, а не то, что обязано отражаться в интерфейсе мгновенно, для этого конкретного запроса интервал сознательно увеличен по аналогии с уже существующим у ядра оверрайдом на 120 секунд для запроса метрик памяти (`memory/useQuery.tsx`, `memory/constants.ts`). Страница, чей плагин выключается или удаляется, перестаёт появляться в течение одного такого интервала после следующего опроса этого эндпоинта — без полной перезагрузки SPA и без отдельного push/websocket-канала, при этом переиспользуя уже существующий в WebUI механизм периодического опроса, а не изобретая новый.

Статичность этой схемы (плагин не может условно добавлять/убирать страницы в рантайме в зависимости от собственного внутреннего состояния) — сознательный компромисс первой версии; при появлении реальной потребности императивная регистрация может быть добавлена позже как опциональное расширение поверх этого же механизма (см. отклонённый вариант в приложении).

### Монтирование страницы в SPA: Web Components + `webuiSdk`

Сборка плагина определяет один или несколько [custom elements](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_custom_elements) (например, `<picodata-plugin-page plugin="example" page="dashboard">`). Entry-модуль плагина экспортирует по умолчанию класс, наследующий `HTMLElement`; роутер хоста один раз лениво делает `import()` этого модуля и сам регистрирует полученный класс через `customElements.define()` (подробнее — в разделе «Точка монтирования и версия в имени тега» ниже), после чего просто рендерит соответствующий тег; дальше всё делает браузерный реестр custom elements. Это не зависит от фреймворка на стороне плагина: подходит любой тулчейн, способный выдать класс `HTMLElement` (React, Svelte, Lit или ванильный JS), так что авторы плагинов не привязаны к версиям React/MUI хоста.

Ошибки при `import()` entry-модуля, при вызове `customElements.define()` и в рендере самой React-обёртки точки монтирования перехватываются React error boundary хоста, поэтому не роняют оболочку и панель навигации. Эта гарантия не распространяется на код самого приложения плагина: если оно рендерится через собственный `createRoot()` (а не как часть React-дерева хоста) или пишет в DOM напрямую, ошибки внутри него — в рендере, в асинхронных обработчиках, в обработчиках событий — до error boundary хоста не долетают и им не перехватываются; то же верно для блокировки основного потока (например, бесконечным циклом внутри плагина), от которой ни один React error boundary в принципе не защищает. Поэтому разделение ответственности такое: хост обрабатывает ошибки загрузки/регистрации custom element'а и ошибки собственной React-обёртки точки монтирования; всё, что происходит внутри уже смонтированного элемента плагина, — ответственность самого плагина, включая, если он написан на React, собственный error boundary внутри своего дерева. Полной изоляции сбоев (в духе `iframe`, см. «Отклонённые альтернативы» ниже) этот подход не даёт — это осознанный выбор.

Отдельный случай — ошибки самого конструктора и lifecycle-колбэков (`connectedCallback`/`disconnectedCallback`/`attributeChangedCallback`) Custom Element'а плагина: это не React-код, и попадание таких ошибок в ближайший React error boundary хоста не гарантировано — зависит от того, в какой момент коммита DOM браузер апгрейдит элемент до зарегистрированного класса, а это деталь реализации React/браузера. Реализация обязана явно проверить фактическое поведение на целевых версиях React и задокументировать его, а не полагаться на него неявно. Для сигнала о критическом сбое уже после успешного монтирования — то есть когда ни один из перехватов выше не сработает, потому что элемент технически смонтирован и работает, но сам обнаружил невосстановимую ошибку — `webuiSdk` получает императивный метод (условно `reportFatalError(error)`): хост в ответ размонтирует custom element этой страницы и показывает на его месте общий error-экран. Выбран именно вызов через `webuiSdk`, а не DOM-событие, чтобы не заводить отдельный канал коммуникации плагин → хост поверх уже существующей поверхности `webuiSdk`.

Контракт host ⇄ плагин:
- **Пространство маршрутов**: `/plugin/<plugin-name>/<page-slug>` (`slug` уникален в рамках манифеста плагина), конструктивно отличное от основных маршрутов (`/nodes`, `/users`, `/login`, ...), поэтому коллизии структурно невозможны. Маршрут не включает версию плагина — он обязан оставаться стабильным; версия участвует ниже, в имени custom element'а и в URL ассетов, а не в самом маршруте.
- **Точка монтирования и версия в имени тега**: роутер хоста рендерит `<picodata-plugin-page src="/plugin-ui/<plugin>/<version>/<entry>" tag="picodata-plugin-<plugin>-<slug>-<version>">` — небольшую общую обёртку, которая лениво делает `import()` модуля `entry` плагина, забирает его default export (класс, наследующий `HTMLElement`) и **сама** вызывает `customElements.define(tag, PageClass)`, предварительно проверив `customElements.get(tag)`, чтобы не звать `define` повторно для уже зарегистрированного тега (например, если страница размонтируется и монтируется заново в рамках одной сессии SPA) — а затем рендерит этот тег. Сам entry-модуль `customElements.define()` не вызывает: эта обязанность исключительно у host, который уже знает имя плагина, страницы и версии, поэтому может сам, централизованно, строить имя тега и проверять факт регистрации, не полагаясь на то, что каждый независимый автор плагина реализует эту логику (включая идемпотентность) одинаково корректно. И `version`, и `entry` берутся из ответа `GET /api/v1/plugin-ui/pages` (см. «Регистрация страниц» выше). Версия — обязательная часть имени тега, а не только пути ассетов: у браузерного реестра `customElements` нет API снятия регистрации, поэтому повторный `customElements.define()` с уже занятым именем тега бросает исключение. Если бы имя тега не менялось между версиями плагина, первое же посещение его страницы после обновления навсегда ломало бы эту страницу до перезагрузки вкладки. С версией в имени тега каждая версия плагина получает собственное, ранее не занятое имя, поэтому переход на новую версию всегда успешно определяет новый тег; тег предыдущей версии остаётся зарегистрированным в реестре браузера как безвредный мёртвый груз (вместе с уже загруженным JS-модулем) до перезагрузки вкладки — это не создаёт утечки сверх той, что и так даёт сам браузер при `import()` произвольного модуля.
- **Контекст host → плагин**: выставляется как версионированный объект `window.picodata.webuiSdk`: аксессор токена текущей сессии (тот же JWT `tokens.auth`, который `useSessionStore` уже хранит в `localStorage`), тема (светлая/тёмная), локаль и базовый URL API кластера. Элемент плагина читает это вместо повторной реализации логина или зашивания origin API в код; про обновление токена при истечении сессии — см. «Обновление сессии» ниже.
- **Изоляция**: тот же origin/DOM, что и у хоста — естественно расшаривает куки/сессию. Для корневого элемента плагина рекомендуется (но не обязателен) Shadow DOM, чтобы CSS хоста и плагина не протекали друг в друга без отдельного browsing-контекста.

#### Жизненный цикл монтирования

В дополнение к тому, кто вызывает `customElements.define()` (см. «Точка монтирования и версия в имени тега» выше), контракт фиксирует сам жизненный цикл экземпляра:

- Хост гарантирует не более одного одновременно смонтированного живого экземпляра страницы: маршрут `/plugin/<plugin>/<slug>` рендерится в одном `<Outlet />` дерева `react-router`, поэтому переход на другую страницу сначала анмаунтит текущий экземпляр, а уже потом монтирует следующий. Плагину не нужно самому защищаться от параллельных живых копий одной и той же страницы.
- При анмаунте (переход на другой маршрут, закрытие вкладки) хост вызывает `disconnectedCallback` элемента штатным для custom elements образом; плагин обязан в нём освободить собственные ресурсы (подписки, сокеты, таймеры) — хост этого за него не делает.
- Повторное подключение того же тега (идемпотентность `define()` уже гарантирована хостом, см. выше) — ожидаемый сценарий, а не край: элемент должен корректно пережить цикл `disconnectedCallback` → `connectedCallback` без утечек и без падения на повторной инициализации.
- Локальное превью (см. «Поставка SDK для разработки плагинов» ниже) воспроизводит эти же обязанности хоста — выбор тега, `customElements.define()`, гарантию единственного живого экземпляра, вызов `disconnectedCallback`/`connectedCallback` — мини-обёрткой монтирования из `@picodata/webui-sdk-dev`; устройство этой обёртки в данной ADR не описывается и выносится в отдельный тикет.

#### Обновление сессии

Аксессор токена в `webuiSdk` (см. «Контекст host → плагин» выше) отдаёт токен как есть, не сообщая о его истечении. У самой оболочки уже есть механизм обновления: `useAuthAxios` (`webui/src/shared/api/client/axios.ts`) перехватывает 401 на собственной авторизованной оси запросов, обновляет токен через `useRefresh` (`webui/src/shared/entity/session/useQuery/useRefresh.ts`) и ретраит исходный запрос — но этот механизм сегодня wired только в собственные запросы ядра и никак не доступен странице плагина, которая делает запросы через свой `fetch`/HTTP-клиент, а не через ось ядра.

Плагин не должен обновлять refresh-токен Picodata самостоятельно — единственный владелец сессии остаётся оболочка. Вместо этого `webuiSdk` получает метод инициации/ожидания обновления (условно `refreshSession(): Promise<string>`), который:
- если обновление уже выполняется (запущено оболочкой или другим вызовом того же метода) — возвращает тот же промис, не порождая параллельный запрос обновления;
- при успехе — резолвится новым токеном;
- при невозможности восстановить сессию — реджектится отличимым от «не хватает прав» образом, чтобы плагин мог развести истечение сессии (обычно — предложить повторный логин через `SideMenu`/`Header` оболочки) и 403 по правам (ошибка самого запроса, не сессии);
- ответственность за повтор исходного запроса плагина после обновления остаётся на самом плагине — `webuiSdk` не проксирует HTTP-запросы, только обновляет токен; на число повторов плагин обязан наложить собственный лимит, особенно для операций изменения данных, чтобы не зациклиться на постоянно проваливающемся обновлении.

Это требование не распространяется на собственную сессию плагина при `auth: plugin` (см. выше) — там управление сессией целиком на стороне плагина.

Сама сегодняшняя реализация в ядре (`useRefresh`, `react-query`-мутация с `mutationKey`) не дедуплицирует параллельные вызовы `mutateAsync()` — `react-query` v3 дедуплицирует по `queryKey` у запросов, но не у мутаций. Чтобы метод `webuiSdk.refreshSession()` мог честно давать гарантию дедупликации, недостаточно просто прокинуть вызов в существующий `useRefresh` — сам этот механизм в ядре тоже нужно доработать (например, закэшировать текущий in-flight промис обновления вне `react-query`, а `useRefresh` и `webuiSdk` оба обращаться к этому общему промису), а не только обернуть его новой поверхностью для плагинов.

### Валидация WebUI-сессии в бэкенде плагина

Страница плагина (`auth: cluster`) получает токен текущей WebUI-сессии через `webuiSdk` (см. «Контекст host → плагин» и «Обновление сессии» выше) и вправе форвардить его в запросах к собственному бэкенду плагина за `PicoListener` (`crates/picodata-plugin/src/transport/listener.rs`) — например, чтобы бизнес-логика сервиса плагина знала, от чьего имени пришёл запрос, и сама авторизовала операцию. Сегодня `picodata_plugin` не даёт для этого ничего, кроме сырого токена: проверка подписи и разбор JWT (`src/http_server/auth.rs`) — приватный код ядра, и автору плагина пришлось бы либо реализовывать валидацию заново (риск разойтись с форматом/секретом ядра или сделать её неправильно), либо не проверять токен вовсе — тот же класс проблемы, который эта ADR уже решает для монтирования страницы, только теперь на уровне API самого плагина.

`picodata_plugin` получает публичную функцию валидации токена сессии, построенную по тому же принципу, что и уже существующий `authenticate()` (`crates/picodata-plugin/src/authentication.rs`) — тонкий FFI-мост в уже существующую в ядре логику (`src/http_server/auth.rs`), а не отдельная реализация JWT внутри плагина. `PicoListener` — сырой сокет без встроенного Rust HTTP-фреймворка (см. «Контекст и постановка проблемы» выше), поэтому функция не завязана на конкретный фреймворк (`tower::Layer`/`axum::middleware` и подобное) — она принимает строку токена и напрямую возвращает результат, встраиваемую автором плагина в обработчик на любом стеке, каким поднят его сервис за `PicoListener`:

- вариант «всё или ничего», аналог `auth_middleware` ядра: `Result<AuthContext, AuthError>`;
- опциональный вариант, аналог `auth_middleware_optional` (см. «Навигация для неаутентифицированного посетителя» выше) — `Option<AuthContext>`, обработчик сам решает, что делать с анонимным запросом.

Тем самым `auth_middleware_optional` перестаёт быть кодом, написанным только под один эндпоинт, а становится переиспользуемым в `src/http_server/auth.rs` примитивом, на который опирается и ядро, и эта FFI-функция для плагинов.

`AuthContext` (имя пользователя, роли) отдаётся обработчику плагина как результат аутентификации — плагин использует его для собственной авторизации операций (например, проверки роли перед деструктивным действием), но не для управления самой WebUI-сессией: обновление токена по-прежнему идёт только через `webuiSdk.refreshSession()` (см. «Обновление сессии» выше), а не через этот путь.

### Безопасность

Custom elements выполняются в собственном origin WebUI, поэтому скомпрометированная или багованная страница плагина может дотянуться за пределы своего элемента (до DOM других элементов, до токена сессии из окружения через `webuiSdk`). Это расширение доверия по сравнению с изолированным iframe (см. приложение), и оно принимается осознанно: плагины уже выполняют произвольный нативный код на сервере с полным доступом к базе данных в рамках `picodata_plugin`, так что браузерный JS из того же, уже доверенного пакета плагина не является существенно большей границей доверия. Рекомендуемые меры смягчения, которые предстоит проработать в реализации:
- `Content-Security-Policy`, ограничивающая бандлы плагинов от загрузки произвольных сторонних origin'ов скриптов.
- Рекомендация (не обязательное требование) Shadow DOM, что заодно снижает радиус поражения от случайных (а не только злонамеренных) коллизий DOM/CSS.
- Явный запасной вариант: ничто в этом дизайне не мешает custom element'у плагина самому решить рендерить внутри себя изолированный `<iframe>` для конкретной страницы — выбранная схема включает в себя вариант с iframe как выбор по желанию на уровне отдельной страницы, просто это не поведение по умолчанию.

### Версионирование

Поверхность `webuiSdk` и контракт загрузки custom element получают собственный номер версии, доступный как `window.picodata.webuiSdk.version`.

#### Поставка SDK для разработки плагинов

Контракт `window.picodata.webuiSdk`, описанный выше, существует только в рантайме — ни типов, ни способа получить тот же объект вне оболочки Picodata эта ADR до сих пор не определяла: автору плагина пришлось бы вручную дублировать типы по документации и не иметь возможности запустить страницу в изоляции от кластера. Это решается двумя отдельно публикуемыми пакетами:

- **`@picodata/webui-sdk-types`** — только TypeScript-типы публичной поверхности `webuiSdk`: аксессор токена, тема, локаль, базовый URL API, `version`, `refreshSession()` (см. «Обновление сессии» выше) и `reportFatalError()` (см. «Монтирование страницы в SPA» выше). Пакет не содержит рантайм-кода — это чистый контракт, на который ссылается и реализация хоста, и dev-реализация, и код самих страниц плагина.
- **`@picodata/webui-sdk-dev`** — dev-реализация того же контракта для локального превью страницы плагина вне picodata. Экспортирует функцию установки, которая создаёт `window.picodata.webuiSdk` с параметрами, задаваемыми разработчиком (токен, тема, локаль, base URL); прежде чем создавать объект, она проверяет `window.picodata?.webuiSdk` и не перезаписывает уже существующий — это runtime guard, чтобы код, случайно попавший в production-сборку страницы, не смог подменить SDK настоящей оболочки. Пакет также содержит мини-обёртку монтирования для локального превью, воспроизводящую обязанности хоста из «Точка монтирования и версия в имени тега» и «Жизненный цикл монтирования» выше — её устройство в этой ADR не описывается и выносится в отдельный тикет.

Установка dev-SDK сама по себе не создаёт действительную сессию Picodata: токен, который она прописывает в аксессоре токена, разработчик добывает сам (например, логином в реальный dev-кластер) — дальше код страницы обращается к `webuiSdk` одинаково что в локальном превью, что внутри picodata, не зная, какая из двух реализаций сейчас установлена. Типы, реализация оболочки и dev-реализация обязаны соответствовать одному и тому же контракту `@picodata/webui-sdk-types`.

### Переиспользование компонентов и стилей фронтенда

Как показывает `kirovets-ng` (раздел «Прецедент» выше), без единого источника истины авторы плагинов уже сегодня вручную копируют фирменные цвета picodata в виде hex-литералов в свой JSX. Полноценное переиспользование самих React-компонентов исключено уже выбором Web Components как способа монтирования (см. выше и отклонённый вариант с общим React-рантаймом в приложении): по замыслу плагин может быть написан на любом стеке, а не обязательно на MUI, и мы сознательно платим за эту независимость невозможностью просто `import` компонент ядра. Поэтому единообразие обеспечивается не общим кодом компонентов, а общим слоем **дизайн-токенов**, одинаково доступным независимо от стека плагина — MUI (ядро) или Tailwind/shadcn (`kirovets-ng`) подключают его напрямую, ремаппингом в своём собственном конфиге, без отдельно публикуемых пакетов интеграции под конкретный стек (см. ниже).

#### Единый источник токенов

Заводим пакет `@picodata/design-tokens`, генерируемый из существующего `webui/src/shared/theme/theme.ts` (он остаётся единственным источником истины; пакет — его экспортируемая проекция). Пакет публикует один и тот же набор значений в двух видах:
- `tokens.css` — плоский набор custom properties, дословно повторяющий ключи `theme.ts`: `--pico-color-bg-light: #f3eee9; --pico-color-bg-gray: #323232; --pico-color-primary: #f7ad4e; --pico-color-text-primary: #050505; --pico-radius-*; --pico-shadow-elevation-1; --pico-font-family: 'Montserrat', sans-serif;` и т.д. — а также `@font-face` для Montserrat, которую ядро уже подключает через `MuiCssBaseline.styleOverrides`.
- `tokens.ts`/`tokens.json` — те же значения как обычные JS-константы, для стеков, которым удобнее типизированный импорт (например, чтобы собрать программно свой `tailwind.config.js` или MUI-тему).

`tokens.css`/`tokens.ts`/`tokens.json` не хранятся в git — они генерируются из `theme.ts` на шаге сборки `@picodata/design-tokens`, а публикация новой версии пакета обязательна как часть выпуска именно той версии picodata core, в которой изменился `theme.ts` (а не отдельный ad hoc процесс, за которым нужно было бы следить вручную). Это снимает вопрос рассинхронизации — сравнивать закоммиченную копию не с чем. Разработчик плагина получает уже готовые файлы из зависимости и не обязан запускать генератор темы picodata сам.

#### Как токены доходят до Shadow DOM плагина

Custom properties, в отличие от обычных CSS-правил, **наследуются сквозь границу Shadow DOM**: значение, заданное на `:root` документа хоста, видно внутри `shadowRoot` элемента плагина, даже когда сам Shadow DOM изолирует остальные стили. Поэтому:
- Ядро WebUI подключает `tokens.css` на уровне документа, выставляя custom properties на `:root` — тем же способом, что сегодня подключает шрифты Montserrat.
- Плагин внутри своего Shadow DOM пишет CSS/Tailwind-классы, резолвящиеся через `var(--pico-color-*)`, — то есть подхватывает актуальную палитру хоста (включая будущую тёмную тему, если она появится), не импортируя ни одного класса или компонента ядра и не рискуя, что его собственные глобальные стили (например, Tailwind preflight) просочатся наружу и сломают MUI, — и наоборот.
- `window.picodata.webuiSdk` дополнительно отдаёт текущую тему программно (`theme: "light" | "dark"` и объект тех же токенов) — для случаев, когда плагину нужно ветвление в JS, а не только в CSS.

#### Интеграция для конкретных стеков

- **Tailwind / shadcn/ui**, как в `kirovets-ng`: подключить `@picodata/design-tokens/tokens.css` и переопределить в собственном `tailwind.config.js`/`index.css` плагина то, что сегодня `tailwind.config.js` в `kirovets-ng` мапит на дефолтные HSL-переменные шаблона shadcn (`--background`, `--primary`, `--border` и т.п.), направив их на `--pico-color-*` вместо значений по умолчанию из шаблона. Для `kirovets-ng` это буквально замена содержимого `:root { --background: ...; }` в `src/index.css` на `@import "@picodata/design-tokens/tokens.css";` плюс ремаппинг имён переменных в `tailwind.config.js` — без единой правки в самих компонентах (`components/ui/*`), которые уже написаны в терминах семантических имён (`bg-primary`, `bg-background`), а не хардкода, и без изменения хардкоженных `bg-[#F3EEE9]`/`bg-[#323232]` в `App.tsx`/`Header.tsx` — те заменяются на `bg-background`/`bg-muted` и начинают резолвиться из общего источника вместо продублированного literal-а. Ремаппинг делает каждый плагин у себя сам — отдельного публикуемого пресета под это на первом этапе нет.
- **MUI**, стек самого ядра: плагин, который тоже хочет писать на MUI, собирает свою MUI-тему поверх тех же токенов — `createTheme({...})` со значениями из `tokens.ts`/`tokens.json`, по сути свою версию `theme.ts` ядра, без общего пакета. Поскольку выбранная схема монтирования не шарит рантайм React/Emotion с хостом (см. отклонённый вариант с Module Federation в приложении), такой плагин в любом случае бандлит собственные `react`/`@mui/material`/`@emotion/*` и инициализирует Emotion с `CacheProvider container={shadowRoot}` — штатной опцией Emotion для рендеринга внутри Shadow DOM, — так что итоговая страница выглядит пиксель-в-пиксель как часть ядра ценой собственного веса бандла (ещё один экземпляр React+MUI), что для страницы админ-панели — приемлемый компромисс.
- **Прочие стеки/vanilla JS**: минимальный контракт — только `tokens.css`. Этого достаточно, чтобы цвета фона, текста, акцента и радиусы скругления совпадали с хостом, даже если ни один компонент не переиспользуется буквально.

#### Общий кит компонентов: решение отложено

Общий npm-пакет готовых React-компонентов (кнопка, поле ввода, таблица, диалог, тосты и т.п.) в эту ADR сознательно не входит. `kirovets-ng` — пока единственный плагин с собственным UI в организации, и по одному образцу нельзя надёжно отличить компоненты, которые действительно повторятся у будущих плагинов, от специфичных лично для `kirovets-ng`; спроектированный заранее состав такого пакета был бы предположением, а не выводом из реального использования. Показательно, что уже в самом `kirovets-ng` часть его сегодняшних UI-примитивов (`skeleton.tsx`, `separator.tsx`, `tooltip.tsx`, `sidebar.tsx` — 386 строк) вообще не используется — то есть даже состав одного-единственного набора компонентов, скопированного из чужого шаблона, не был толком проверен практикой.

Решение о том, заводить ли `@picodata/plugin-ui-kit` (и какой у него будет состав), стоит принять позже — когда появится несколько независимых плагинов с собственным UI и по факту их использования станет видно, какие компоненты у них пересекаются. До тех пор единственный публикуемый пакет дизайн-системы — `@picodata/design-tokens` (см. «Единый источник токенов» выше); каждый плагин, включая `kirovets-ng`, продолжает держать свои UI-примитивы в собственном репозитории, только стилизуя их через `--pico-color-*` вместо хардкода (см. «Интеграция для конкретных стеков» выше).

#### Проверка: переносится ли `kirovets-ng` на новый механизм без переписывания логики

**Полностью заменяется декларацией в манифесте, без переноса кода**:
- `front/src/App.tsx` (24 строки) и `front/src/components/Header.tsx` (36 строк) — весь маршрутизатор плагина и его самодельная навигация («Конфигурация», «Таблицы») исчезают: это ровно две записи в манифестной секции `webui:` (см. «Регистрация страниц» выше), точки монтирования которых регистрирует host. `basename="/config"` из `App.tsx` пропадает — маршрут теперь `/plugin/kirovets-ng/config` и `/plugin/kirovets-ng/tables`, назначаемый хостом, а не самим плагином.

**Остаётся в репозитории плагина как есть, меняется только источник цвета**:
- `front/src/components/ui/*` (15 файлов, 1266 строк) — никуда не переносятся и не удаляются: это по-прежнему собственная копия UI-примитивов плагина. Меняется только их стилизация — `bg-primary`/`bg-background` и подобные семантические классы (уже используемые в этих компонентах, а не хардкод) начинают резолвиться из `--pico-color-*` вместо HSL-переменных дефолтного шаблона shadcn. Из этих 1266 строк 386 (`skeleton.tsx`, `separator.tsx`, `tooltip.tsx`, `sidebar.tsx`) сегодня не используются вовсе — их можно удалить как отдельную уборку мёртвого кода, обнаруженную именно в ходе этой проверки, но это не требование самой ADR.
- `front/src/pages/TablesPage.tsx` (284 строки), `front/src/components/FileManager/*` (`FileDialogs.tsx` и ещё 672 строки в `FileEditor`/`FileToolbar`/`FileTreeItem`/`FileTree`/`index.tsx`), `front/src/main.tsx` — импорты `Button`/`Input`/`Spinner`/`ConfirmDialog`/`Table`-семейства/`Dialog`/`Breadcrumb`/`Sheet`/`useToast` остаются из `../ui/*` без единой правки путей; бизнес-логика (`HttpApi.tables.*`, `handleTruncate`, `handleReimport`, дерево файлов, редактор на Monaco, zip/drag-and-drop) не трогается вовсе.
- `front/tailwind.config.js` и `front/src/index.css` — дефолтные HSL-переменные шаблона shadcn заменяются на `@import "@picodata/design-tokens/tokens.css";` и ремаппинг переменных на `--pico-color-*` в самом `tailwind.config.js`; заодно исчезают захардкоженные `bg-[#F3EEE9]`/`bg-[#323232]`, которые раньше были только в `App.tsx`/`Header.tsx` и уже удалены на первом шаге.

**Остаётся как есть**:
- `front/src/pages/ConfigPage.tsx` (10 строк) — тонкая обёртка над `FileManager`, не меняется вовсе (заголовок при желании можно оставить как есть).
- `front/src/lib/api/*`, `front/src/lib/utils/{files,icons,paths,randoms,zips,styles}.ts`, `front/src/hooks/{use-file-drag-drop,use-file-operations,use-zip-drag-drop}.ts`, `front/src/types/tables.ts` — вся прикладная логика плагина (HTTP-клиент, работа с файлами/zip, drag-and-drop, утилита `cn()`) не меняется.

**Итог проверки**: декларацией в манифесте заменяется только «обвязка» маршрутизации и навигации — `App.tsx`/`Header.tsx` (60 строк). Всё остальное, включая собственную копию UI-примитивов (1266 строк) и всю прикладную логику (`FileManager/*`, `TablesPage.tsx`, `lib/`, `hooks/` — порядка 1250 строк), остаётся в репозитории плагина без переписывания — у примитивов меняется только источник цвета. Иными словами: перенос механически возможен уже сейчас, без ожидания решения по общему киту компонентов.

#### Иконки и типографика

- Иконки пунктов `SideMenu` для страниц ядра сегодня — инлайновые React-SVG-компоненты (`webui/src/shared/icons`). Иконка страницы плагина, наоборот, — обычный статический файл, который плагин вправе поставить со своей сборкой (кастомизируема), но манифестного поля под неё не заводим: путь получается по той же конвенции, что и у переводов (см. «Локализация» ниже), — по фиксированному имени, производному от уже известного `slug` страницы: `webui/icons/<slug>.svg`, раздаваемому тем же самым существующим статическим маршрутом, `/plugin-ui/<plugin>/<version>/icons/<slug>.svg` (см. «Доставка и раздача статических ассетов плагина» выше) — никакого нового поля манифеста ради этого не требуется, SPA строит URL сама из уже известных ей `plugin`/`version`/`slug`. Хост подставляет этот URL в `<img>`/CSS `background-image` (не как встраиваемый и потому исполняемый React-компонент — это структурно исключает инъекцию скриптов через «иконку»); если по этому пути файла нет, пункт `SideMenu` рендерится без иконки — `onError` просто прячет `<img>`, без замены на что-либо ещё.
- Шрифт Montserrat, уже подключаемый ядром через `@font-face` в `theme.ts`, публикуется той же инструкцией `@font-face` внутри `tokens.css` — плагину не нужно бандлить свои файлы шрифта, достаточно положиться на `font-family: var(--pico-font-family)`, унаследованное в Shadow DOM так же, как и цвета.

#### Локализация: `title` — i18n-ключ, а не отображаемый текст

Манифестное поле `title` (заголовок пункта `SideMenu`) — это **ключ локализации**, а не строка, которую хост рендерит как есть. Переводы для него — не часть манифеста, а такой же статический ассет плагина, как `entry`: файлы `webui/i18n/<locale>.json` (`{ "dashboard.title": "My Dashboard" }`), лежащие рядом с остальными файлами плагина и раздаваемые тем же самым уже существующим маршрутом `/plugin-ui/<plugin>/<version>/i18n/<locale>.json` (см. «Доставка и раздача статических ассетов плагина» выше).

WebUI SPA запрашивает бандл перевода для текущей локали, а если его нет (плагин не обязан покрывать каждую локаль, которую поддерживает ядро) — для локали ядра по умолчанию; если ключ не находится ни там, ни там, на экране остаётся сам ключ `title` как есть, а не пустая строка — это тот же принцип «сломанный кусок не должен выглядеть как ничего», что уже применён к `PluginPageErrorBoundary` (см. «Монтирование страницы в SPA» выше), и заодно позволяет автору плагина сразу увидеть в UI, какого перевода не хватает. Бандл привязан к версии плагина тем же путём, что и остальные ассеты, поэтому кешируется агрессивно и бесконечно (`staleTime: Infinity` на стороне SPA) — в отличие от списка страниц, содержимое конкретной версии перевода в принципе не может измениться без выпуска новой версии плагина.

Собственный текст внутри страницы плагина (не то, что рендерит хост в `SideMenu`, а то, что рендерит сам custom element) в эту схему не входит и остаётся полностью на усмотрение плагина — `webuiSdk.getLocale()` (см. «Монтирование страницы в SPA» выше) уже отдаёт текущую локаль хоста именно для этого случая.

## Последствия

- Хорошо, потому что страницы плагинов становятся доступны из левой панели навигации без пересборки ядра picodata, что согласуется с тем, как плагины и так устанавливаются/включаются динамически.
- Хорошо, потому что всё остаётся в одном origin, поэтому страницы плагинов прозрачно наследуют уже реально работающую сегодня JWT-сессию/аутентификацию WebUI (см. «Регистрация страниц» и «Монтирование страницы в SPA» выше) вместо повторной реализации логина.
- Хорошо, потому что от авторов плагинов не требуется переходить на строго те же версии React/MUI, что и у хоста, что снижает порог входа для сторонней разработки UI плагинов.
- Хорошо, потому что жизненный цикл страниц (добавление/удаление/обновление) бесплатно вытекает из уже существующего управления жизненным циклом плагина.
- Хорошо, потому что единый пакет дизайн-токенов даёт объективный источник истины для брендовых цветов/шрифтов вместо ручного копирования hex-литералов между кодовыми базами (см. `kirovets-ng`).
- Плохо, потому что custom elements в общем origin — это реальное расширение браузерного доверия к авторам плагинов по сравнению с полностью изолированным iframe (хотя и небольшое на фоне уже существующей серверной модели доверия).
- Плохо, потому что `pico.httpd` теперь должен раздавать статические файлы из рантайм-директории на каждый включённый плагин (раньше он раздавал только встроенный на этапе компиляции основной бандл) — умеренно новое состояние, которое нужно поддерживать согласованным с включением/выключением/обновлением плагинов.
- Плохо, потому что это вводит новый контракт (поверхность `webuiSdk`, соглашение о загрузке custom element), который нужно поддерживать и версионировать, и с которым обязаны считаться и ядро picodata, и каждый плагин, желающий иметь UI.
- Плохо, потому что `GET /api/v1/plugin-ui/pages` вводит первый в кодовой базе пример эндпоинта с опциональной, а не всё-или-ничего аутентификацией (`auth_middleware_optional`, см. «Навигация для неаутентифицированного посетителя» выше) — новый класс серверного кода, который нужно отдельно тестировать на то, что анонимный вызов действительно не может получить ничего сверх `auth: plugin`-страниц, а не только полагаться на то, что клиент сам не покажет лишнее в `SideMenu`.
- Плохо, потому что `auth_middleware_optional` этим не ограничивается: та же логика становится основой FFI-функции валидации сессии в `picodata_plugin` (см. «Валидация WebUI-сессии в бэкенде плагина» выше) — то, что для анонимного запроса означает `None` вместо ошибки, теперь интерпретирует не только код ядра, но и бэкенд каждого плагина; корректность этой интерпретации (не выдать лишнего анониму) — ответственность уже не только ядра, но и каждого автора плагина.

## Upgrade-план: перевод плагина с уже существующим UI

Практическая инструкция для автора плагина, у которого уже есть свой браузерный UI мимо этого механизма — сегодня единственный такой случай в организации это `kirovets-ng` (см. «Прецедент» выше), но раздел написан как общий чеклист на будущее, а не только под него. Цель — снять с плагина отдельный origin/порт, самодельную аутентификацию и продублированную стилизацию, не переписывая прикладную логику страниц (как уже показано разбором файл-за-файлом в «Проверка: переносится ли `kirovets-ng` на новый механизм без переписывания логики» выше).

Платформенных предпосылок со стороны ядра для самого upgrade'а нет: маршрут `/plugin/<plugin>/<slug>` стабилен между версиями плагина, а `ALTER PLUGIN ... TO VERSION` меняет только версию в пути ассетов и в имени custom element'а (см. «Версионирование» выше) — с точки зрения ядра переход на новую версию уже готовой к этому механизму страницы ничем не отличается от обычного апгрейда плагина. Всё, что ниже, — работа на стороне самого плагина, один раз.

### Шаги

1. **Аудит существующего UI.** Перечислить: какие клиентские маршруты сегодня есть у собственного роутера плагина (это будущие записи `webui:`), как реализована аутентификация (обычно — то, что нужно снести первым, см. шаг 5), какой стек стилизации используется (Tailwind/MUI/vanilla — определяет, как именно резолвить `--pico-color-*` в свой конфиг на шаге 6), есть ли собственный `Header`/`Sidebar` (снимается целиком, см. шаг 7).
2. **Реструктуризация сборки.** Собрать статику фронтенда плагина в поддиректорию `webui/` внутри исходников плагина и объявить её в `custom_assets` упаковщика (`pike`). Не нужно вручную учитывать, что `pike` заворачивает её в `assets/webui/` на диске (см. «Доставка и раздача статических ассетов плагина» выше) — это резолвит ядро, автору плагина достаточно положить `webui/` на верхнем уровне исходников, как уже сделано в `kirovets-ng`.
3. **Манифест.** Завести секцию `webui:` верхнего уровня в `manifest.yaml` — по одной записи на каждый существующий сегодня клиентский маршрут/пункт собственной навигации (`slug`, `title`, `entry`). См. «Регистрация страниц» выше за форматом.
4. **Точка входа страницы.** На каждый `entry` — модуль, default export которого — класс, наследующий `HTMLElement`, который **не** вызывает `customElements.define()` сам (это делает host, см. «Монтирование страницы в SPA» выше). Если элемент использует Shadow DOM (рекомендуется, не обязательно), на корневом элементе нужен явный `:host { display: block; height: 100% }` — без него страница коллапсирует до нулевой высоты (см. `fix(webui): give the plugin page mount point an explicit height` и комментарий в `PluginPage.tsx`).
5. **Аутентификация.** Здесь на аудите из шага 1 обычно обнаруживаются два разных случая, которые легко спутать, потому что у `kirovets-ng` они сегодня стоят рядом в одном и том же `init()`, — их нужно разбирать порознь:
   - **Обходной путь без собственной модели auth** — вроде `ALTER SYSTEM SET jwt_secret = ''` у `kirovets-ng` (см. «Прецедент» выше) — должен исчезнуть безусловно и в первую очередь, вне зависимости от того, что решено по следующему пункту. Для запросов, которым нужен только доступ к API самого кластера, замена — `window.picodata.webuiSdk.getSessionToken()`/`apiBaseUrl`.
   - **Полноценная собственная аутентификация** — вроде интеграции с Keycloak у `kirovets-ng` (см. «`auth: plugin`» выше) — снимать не нужно и не следует. Для страницы с такой аутентификацией отметить соответствующую запись `webui:` в манифесте полем `auth: plugin` — это снимает требование host-JWT именно для неё, оставляя всю ответственность за проверку доступа на уже существующей аутентификации плагина. Страницы того же плагина без своей модели auth (например, техническая страница только для операторов кластера) при этом спокойно остаются на `auth: cluster` — поле per-страничное.
6. **Стилизация.** Подключить `@picodata/design-tokens/tokens.css` и заменить любые захардкоженные hex-литералы фирменных цветов (`bg-[#F3EEE9]` и подобное) на `var(--pico-color-*)`; по стеку — ремаппинг `--pico-color-*` на переменные Tailwind/shadcn или MUI-тему в собственном конфиге плагина (см. «Интеграция для конкретных стеков» выше) — собственные UI-примитивы плагина при этом остаются на месте, меняется только их источник цвета, см. готовую построчную раскладку для `kirovets-ng` в разделе «Проверка» выше.
7. **Навигация.** Удалить собственные `Header`/`Sidebar` целиком — пункты навигации теперь приходят бесплатно из host `SideMenu`, вложенные под общий пункт-группу плагина, в порядке записей `webui:` (см. «Место в навигации: вложенный список по плагину» выше), с заголовком из `title` манифеста и файлом `webui/icons/<slug>.svg` (при его отсутствии пункт остаётся без иконки).
8. **Роутинг.** Удалить собственный экземпляр `react-router`/`basename`; каждый прежний маршрут верхнего уровня становится одной записью `webui:`. Если внутри одной старой страницы была вложенная клиентская маршрутизация (как `FileManager`/`FileEditor` у `kirovets-ng`) — она остаётся внутренним делом того же custom element'а, host маршрутизирует только на уровне `slug`, не глубже.
9. **Снятие самодельного жизненного цикла маршрутов.** Удалить любой код, который сам регистрирует/снимает `pico.httpd`-маршруты (`src/ui/mod.rs`, `remove_routes` и подобное у `kirovets-ng`) — регистрация теперь полностью декларативна и привязана к включению/выключению плагина в целом на стороне ядра, без какого-либо кода на стороне плагина.
10. **Тестирование на реальном кластере (`cargo pike run`).** Не полагаться на то, что «раз собралось — значит работает»: проверить install → enable → страница появилась в `SideMenu` и открывается; полная перезагрузка/F5 прямо на `/plugin/<plugin>/<slug>` (SPA-фолбэк ядра); `ALTER PLUGIN ... TO VERSION` на новую версию плагина — страница должна подхватить новую сборку, а не молча продолжить рендерить старый custom element; disable плагина — пункт навигации и старые ассет-маршруты должны исчезнуть в течение одного интервала опроса `GET /api/v1/plugin-ui/pages`.
11. **Снос старого UI.** Только после того, как шаги 1–10 пройдены и проверены на реальном кластере — удалить прежний standalone HTTP-сервер плагина целиком (свой бандл, свой Lua HTTP-модуль, свой порт/TLS), а не оставлять его рядом «на всякий случай»: держать оба входа параллельно означает поддерживать две модели аутентификации одновременно, ровно то, от чего эта ADR уходит.

### Чеклист

- [ ] `webui/` фронтенда объявлена в `custom_assets` пакета плагина
- [ ] секция `webui:` в `manifest.yaml` — по записи на прежний маршрут
- [ ] каждый `entry`-модуль экспортирует класс `HTMLElement`, не регистрирует себя сам
- [ ] `:host { display: block; height: 100% }` на корневом элементе страницы
- [ ] обходные пути вроде `ALTER SYSTEM SET jwt_secret = ''` убраны безусловно
- [ ] для страниц без собственной модели auth — доступ к API кластера через `webuiSdk.getSessionToken()`/`apiBaseUrl` (`auth: cluster`, по умолчанию)
- [ ] для страниц с уже существующей собственной аутентификацией (Keycloak и т.п.) — она сохранена как есть, манифест помечен `auth: plugin`, и сама страница проверяет доступ до показа данных, а не полагается на то, что WebUI её как-то защитит
- [ ] цвета/радиусы/шрифт — через `var(--pico-*)`, без захардкоженных hex-литералов
- [ ] собственные `Header`/`Sidebar`/`react-router` верхнего уровня удалены
- [ ] собственная регистрация/снятие `pico.httpd`-маршрутов удалена
- [ ] пройден цикл install/enable/F5-reload/version-upgrade/disable на реальном кластере
- [ ] старый standalone UI-сервер полностью удалён, не оставлен как fallback

### `kirovets-ng` как эталонный кейс

Полная построчная раскладка «что удаляется, что остаётся как есть, что меняется только по стилизации» для конкретно `kirovets-ng` уже сделана в «Проверка: переносится ли `kirovets-ng` на новый механизм без переписывания логики» выше — этот upgrade-план и есть процедура выполнения того разбора на практике, обобщённая на любой будущий подобный случай.

## Отклонённые альтернативы

Для каждого из трёх вопросов раздела «Архитектура решения» рассматривались и были отклонены следующие варианты.

### Доставка ассетов: плагин раздаёт UI сам через `PicoListener`, host делает reverse-proxy или iframe

Альтернатива выбранной раздаче статических файлов с диска через `pico.httpd`: оставить UI плагина полностью на порту, который он и так получает от `PicoListener`, а `pico.httpd` либо проксирует `/plugin-ui/<plugin>/...` на этот бэкенд, либо host-SPA просто делает `<iframe src="http://host:plugin-port/...">`.

**Плюсы**:
- Ноль изменений в формате упаковки плагина — плагин буквально может быть «любым веб-приложением» за своим листенером.
- Сильная изоляция процесса/рантайма от самого ядра picodata (зависший или упавший UI-сервер плагина не затрагивает `pico.httpd`).

**Почему отклонён**:
- Reverse-proxy означает, что `pico.httpd`/tarantool теперь должен стримить/пулить соединения к произвольному числу бэкендов плагинов — заметно больше движущихся частей, чем уже имеющаяся раздача статических файлов с диска.
- Iframe на другой порт означает другой origin, а значит, снова возникают ровно те проблемы с CORS/куками/сессией, которых эта ADR пытается избежать, плюс порт плагина напрямую становится видимым операторам/файрволам.
- Плагину теперь нужно реализовать (или встроить) HTTP-сервер статики и заново изобрести версионирование ассетов, дублируя то, что `pico.httpd` уже делает для основного бандла.

### Монтирование страницы: простой `<iframe>`

Альтернатива выбранным Web Components: роутер хоста рендерит `<iframe>`, указывающий на entry-HTML-страницу плагина.

**Плюсы**:
- Максимальная изоляция — плагин может использовать буквально любой фронтенд-стек, любую версию React/Vue/Angular, без какой-либо связанности с тулчейном хоста.
- Тривиально реализовать на стороне хоста: один компонент `<iframe>`, никакого контракта со стороны плагина определять не нужно.

**Почему отклонён**:
- UX второго сорта: отдельный контекст скролла/фокуса/горячих клавиш, нет простого способа расшарить тему MUI хоста (тёмная/светлая, цвета) или его layout-«обвязку», взаимодействие только через `postMessage`.
- Аутентификацию приходится явно прокидывать через границу фрейма (токен через query-строку/`postMessage`), что легко сделать тонко неправильно (утечка токена в историю браузера/referrer и т.п.).
- Ощущается как приклеенное сбоку, а не нативная часть продукта, что противоречит целям ADR.

Не выброшен полностью: ничто не мешает конкретному custom element'у плагина рендерить `<iframe>` внутри себя для страницы, которой действительно нужна такая изоляция — см. раздел «Безопасность» выше.

### Монтирование страницы: Module Federation с общим рантаймом React/MUI

Альтернатива выбранным Web Components: использовать Webpack 5 Module Federation (или `@originjs/vite-plugin-federation` для Vite), чтобы бандлы плагина шарили ровно те же инстансы React, ReactDOM и MUI, что загружает хост, и рендерились как обычные React-компоненты/маршруты.

**Плюсы**:
- Максимально тесная визуальная/поведенческая интеграция — страницы плагина неотличимы от нативных страниц WebUI, полный доступ к библиотеке компонентов и хукам хоста.
- Не нужно изобретать контракт custom element; плагины буквально являются React-компонентами.

**Почему отклонён**:
- Вынуждает каждого автора плагина сидеть на строго тех же мажорных (часто и минорных) версиях React/ReactDOM/MUI, что и хост — это напрямую противоречит цели о независимом версионировании/релизах плагинов. Обновление WebUI picodata с бампом React единовременно сломает все страницы плагинов, если только они не пересобраны синхронно.
- Нет значимой изоляции сбоев — компонент плагина выполняется «по-настоящему» внутри React-дерева хоста; неисправный компонент плагина способен повредить общий React-контекст/состояние так, как изолированный custom element не может.
- Жёстко привязывает разработку UI плагина к собственным решениям picodata по фронтенд-стеку (конфиг Vite, версия MUI), которые большинство авторов плагинов (в первую очередь Rust-разработчики, работающие с `picodata_plugin`, судя по существующим примерам плагинов) вряд ли захотят отслеживать.

### Регистрация страниц: императивный Rust API вместо декларации в манифесте

Альтернатива декларативной секции `webui` в манифесте: Rust API, который сервис вызывает из `on_start`/`on_config_change` для регистрации страниц, например `ctx.register_webui_page(PageDescriptor { .. })` внутри `Service::on_start`.

**Плюсы**:
- Полностью динамично — сервис может регистрировать/снимать регистрацию страниц в зависимости от своего рантайм-состояния.

**Почему отклонён**:
- Заметно больше поверхности для проектирования и стабилизации в `picodata_plugin` (порядок регистрации/снятия регистрации, что происходит при рестарте/падении сервиса посреди регистрации и т.п.) ради потребности, которую манифестный подход пока явно не демонстрирует.
- Сложнее статически валидировать при установке; ошибающийся код может «дёргать» пункты навигации в рантайме.
- Возвращает ровно ту проблему, которую решает выбор «`webui` — сущность плагина, а не сервиса» (см. «Регистрация страниц» выше): императивный вызов из `Service::on_start` снова привязывает жизненный цикл страницы к жизненному циклу одного конкретного сервиса, тому самому анти-паттерну, что уже допущен в `kirovets-ng`.

Не исключается полностью на будущее: при появлении реального сценария, которому декларативного манифеста недостаточно, императивный API может быть добавлен как опциональное расширение поверх уже существующего декларативного механизма, а не взамен него.
