# Пул Lua-потоков для вызовов Lua из SQL

## Контекст

SQL обращается к Lua, чтобы узнать репликасет бакета (`router:route`)
и взять ссылку vshard на сторадж (`lref.add`, `lref.use`, `lref.del`).
Пока ссылка жива, vshard не переносит бакеты этого стораджа.

Раньше каждый такой вызов создавал новый Lua-поток (`lua_State`: свой
Lua-стек, а не поток ОС) и после вызова бросал его. Функцию он каждый
раз искал по цепочке таблиц `pico` → `dispatch` → `lref` → имя.

Сами потоки создаются быстро, дорог мусор от них. Точечный запрос
создавал 4 потока, и на них приходилось 2.7 КБ из 2.9 КБ, которые запрос
выделял в Lua. На tpcb сборка этого мусора занимала 4.5% времени
TX-потока (потока ОС, где выполняются SQL и Lua), а поиск функций —
ещё 1.7%.

## Варианты

1. **Общий главный Lua-стек.** Мусора нет совсем, но так нельзя:
   `lref.add` и `router:route` могут переключить файбер, и тогда другой
   файбер положит свои значения на тот же стек.
2. **Пул Lua-потоков.** Файбер берёт поток из пула и держит его до конца
   вызова, даже если по пути переключается. Два файбера никогда не
   делят один стек.
3. **Пул с отдельной настройкой ёмкости через `ALTER SYSTEM`.** Лишняя
   настройка: число одновременных SQL-запросов уже ограничивает
   `sql_runtime_concurrency_max`.

## Решение

Выбран вариант 2.

- Если в пуле нет свободного потока, вызов не ждёт, а создаёт новый.
  Поэтому пул не ограничивает число одновременных запросов.
- Поток возвращается в пул, только если его стек пуст. Иначе поток
  выбрасывается.
- Пул хранит не больше `min(sql_runtime_concurrency_max, 1024)`
  свободных потоков, лишние уничтожаются при возврате. Запрос обычно
  держит один поток за раз, поэтому после прогрева пул не создаёт
  новых потоков, пока занятых не больше его ёмкости. Потолок 1024
  защищает от случая, когда лимит подняли до огромного числа, чтобы
  фактически его снять.
- Поток, взятый для поиска маршрута, отпускается до локального
  выполнения запроса. Иначе каждый DML, ждущий записи в WAL, держал бы
  свой поток.
- Функции `pico.dispatch` и `pico.dispatch.lref` закрепляются в реестре
  Lua при первом вызове, дальше их достают одной операцией. Неудачный
  поиск не запоминается, тексты ошибок прежние.

## Последствия

- Точечный запрос выделяет в Lua 0.2 КБ вместо 2.9 КБ. Сборка мусора
  на этом пути занимает 0.4% времени TX-потока вместо 4.5%. tpcb даёт
  на 10% больше транзакций в секунду.
- Свободный поток после сборки мусора занимает около 0.6 КБ, так что
  даже 1024 потока — меньше 1 МБ.
- Остаются код vshard на Lua (6.2% TX-потока на tpcb) и обвязка tlua.
  Группировка бакетов для запросов по всем бакетам (`Buckets::All`)
  будет отдельным изменением.
