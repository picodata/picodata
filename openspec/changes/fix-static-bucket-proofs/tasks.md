# Задачи

## 1. Доказательство по ключам

- [x] 1.1 Ввести отдельный результат планирования и описать его смысл
  в коде. Проверить границы и ограничения перебором выражений `AND`/`OR`
  и отображений ключей в бакеты, включая совпадения.
- [x] 1.2 Сравнивать полное представление ключа. Добавить тесты на типы,
  порядок компонентов и совпавший хеш при разных ключах.
- [x] 1.3 Подключить новые операции через `BucketsResolver`, сохранив
  общий разбор фильтров. Проверить существующие тесты расчёта бакетов
  исполнителя и новые тесты статических доказательств.

## 2. Выбор плана

- [x] 2.1 Перевести `single_node_buckets`, `union_shares_one_bucket`
  и кеш на новое доказательство. Тестами планов подтвердить отсутствие
  лишнего агрегирования для одинаковых ключей и общего ключа после `OR`.
- [x] 2.2 Согласовать правила соединений, `UNION ALL`, `Any` и пустоты
  с исполнителем. Тестами проверить глобальные таблицы, границы `Motion`
  и сохранение строк скалярного агрегата. Различать фильтр или условие
  `INNER JOIN`, целиком равное `false`/`NULL`, и отдельный `AND false`,
  в том числе добавленный `enrich_restrictions`.
- [x] 2.3 Добавить случаи спецификации в интеграционные проверки SQL.
  При 3000 бакетах проверить их настоящее размещение на двух шардах
  и точные результаты, включая запрос с ключами `1` и `10208`.
  Для соединения с глобальной таблицей проверить отдельно `WHERE false`
  и противоречивые равенства: оба запроса должны вернуть строки `0` и `2`.
- [x] 2.4 Добавить проверки составного ключа и повторного исполнения
  подготовленного запроса; подтвердить ожидаемые планы и результаты.
- [x] 2.5 Исправить обработку `ScanCte`: доказательство одного узла
  не должно отменять обязательную материализацию `VALUES` и существующие
  правила повторного использования CTE. Подтвердить сохранение результата
  один раз, правильные имена столбцов и оптимизации общего бакета.

## 3. Общая проверка

- [x] 3.1 Запустить затронутые тесты `sql-ir`, `sql-planner`,
  `sql-executor`, `sql-frontend`, интеграционные случаи
  `scalar_agg_union.sql`, `cte.sql` и повторную привязку параметров
  с включённым и выключенным `enrich_restrictions`.
  Все случаи спецификации должны проходить.
- [x] 3.2 Проверить изменения ожидаемых планов: каждый межшардовый этап
  должен быть обоснован утратой доказательства или обязательной
  материализацией. Случаи одинаковых ключей сохраняют оптимизацию.
