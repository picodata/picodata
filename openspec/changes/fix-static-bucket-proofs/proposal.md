# Исправление проверки одношардового исполнения

## Зачем

Данные таблицы распределены по шардам — группам узлов. Бакет — часть данных,
назначенная одному шарду. Планировщик выбирает способ выполнения запроса,
а исполнитель отправляет его на нужные шарды.

Планировщик может ошибочно решить, что хватит одного шарда, и пропустить
объединение частичных результатов. Например, таблица `t` распределена
по `a` и содержит только строку `a = 2`:

```sql
SELECT count(*)
FROM (
    SELECT a FROM t WHERE a = 1 AND a = 10208
    UNION ALL
    SELECT a FROM t WHERE a = 2
) u;
```

Ответ должен быть одной строкой `1`. Первая ветка не даёт строк,
вторая даёт одну. Но при 3000 бакетах ключи `1` и `10208` попадают
в бакет 1934, а ключ `2` — в 1410. Исполнитель выбирает оба бакета.
Если они на разных шардах, без итогового объединения вернутся `0` и `1`.

Причина: планировщик пересекает отпечатки ключей — числа для их сравнения.
Разные отпечатки дают пустое пересечение, хотя реальные бакеты совпадают.
Отсутствие строк также не отменяет результат `count(*)`: он равен нулю.

Доказательство одного узла используется и для именованных подзапросов
(`WITH`, или CTE). Для `VALUES` требуется сохранить их результат отдельно
(материализовать), чтобы не потерять имена столбцов. Новый результат `Any`
ошибочно разрешает пропустить этот шаг и ломает соединение CTE с собой.

## Что изменится

- Реальные номера бакетов отделятся от доказательств планировщика.
- При `AND` и `OR` сохранятся безопасные ограничения по ключам.
- Ветки с одинаковыми ключами сохранят одношардовую оптимизацию.
- Пустой вход и запуск на любом узле получат отдельные правила.
- Сохранится обязательная материализация CTE, включая случаи с `VALUES`.
- Проверки охватят два шарда и настоящий расчёт бакетов.

## Возможности

### Новые

- `single-shard-proof`: надёжное доказательство одношардового исполнения
  с сохранением оптимизаций для одинаковых ключей.

### Изменяемые

Нет: существующих спецификаций в проекте пока нет.

## Затронутые части

Расчёт ограничений в `sql-ir/src/ir/bucket.rs`, проверки
в `sql-ir/src/ir/transformation/redistribution.rs` и их кеш. Пути указаны
от каталога `crates/`. Разбор выражений остаётся общим с исполнителем.

Проверки планов в `sql-planner` и `sql-frontend`, случаи
в `test/int/sql/scalar_agg_union.sql` и `test/int/sql/cte.sql`.
Правильность не должна зависеть от включения `enrich_restrictions`.
