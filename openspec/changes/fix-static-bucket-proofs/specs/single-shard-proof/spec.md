# Надёжное одношардовое исполнение

## Purpose

Запрос должен возвращать правильный результат при любом размещении бакетов
по шардам. Доказанное исполнение в одном бакете сохраняет оптимизацию.

## ADDED Requirements

### Requirement: Правильный результат при совпадении бакетов

Запрос обязан (MUST) возвращать тот же результат, что и вычисление
над всей таблицей, даже если разные значения ключа попали в один бакет.
Пустое пересечение отпечатков не доказывает отсутствие бакетов.

#### Scenario: Противоречивая ветка UNION ALL

- **WHEN** таблица `t`, распределённая по `a`, содержит только `a = 2`,
  число бакетов равно 3000, а бакеты 1934 и 1410 лежат на разных шардах
- **WHEN** выполняется следующий запрос:

```sql
SELECT count(*)
FROM (
    SELECT a FROM t WHERE a = 1 AND a = 10208
    UNION ALL
    SELECT a FROM t WHERE a = 2
) u;
```

- **THEN** результат состоит ровно из одной строки `1`

#### Scenario: Противоречивая часть OR

- **WHEN** при тех же данных выполняется запрос:

```sql
SELECT count(*) FROM t
WHERE (a = 1 AND a = 10208) OR a = 2;
```

- **THEN** результат состоит ровно из одной строки `1`

#### Scenario: Противоречивая сторона INNER JOIN

- **WHEN** при тех же данных выполняется запрос:

```sql
SELECT count(*)
FROM (SELECT a FROM t WHERE a = 1 AND a = 10208) l
JOIN (SELECT a FROM t WHERE a = 2) r ON l.a = r.a;
```

- **THEN** результат состоит ровно из одной строки `0`

### Requirement: Сохранение доказанных оптимизаций

Планировщик обязан (MUST) сохранять одношардовое исполнение,
когда общий бакет доказан через одинаковые ключи. Это относится
и к ключам из нескольких столбцов.

#### Scenario: Одинаковые ключи в двух ветках

- **WHEN** обе ветки `UNION ALL` или стороны `INNER JOIN` ограничены
  одним и тем же постоянным ключом и сверху вычисляется `count(*)`
- **THEN** `EXPLAIN` не показывает лишний межшардовый этап агрегирования

#### Scenario: Общий ключ после AND и OR

- **WHEN** вычисляется `count(*)` с фильтром
  `(a = 1 AND a = 10208) OR a = 1`
- **THEN** сохраняется одношардовое исполнение

### Requirement: Сохранение результата на пустом входе

Система обязана (MUST) сохранять строки, создаваемые агрегатами
без `GROUP BY`: `count(*)` даёт ноль, а `sum(a)` — `NULL`
на пустом входе. Запуск на любом одном узле не означает пустой результат.

#### Scenario: Пустой агрегат внутри UNION ALL

- **WHEN** над `t` с единственной строкой `a = 2` выполняется
  `SELECT count(*) FROM t WHERE false UNION ALL SELECT a FROM t`
- **THEN** результат содержит ровно две строки: `0` и `2`
- **THEN** при замене `count(*)` на `sum(a)` получаются `NULL` и `2`

#### Scenario: WHERE false и глобальная таблица

- **WHEN** таблица `t`, распределённая по `a`, содержит только `a = 2`,
  глобальная таблица `g`, доступная на каждом шарде, содержит `a = 2`,
  число бакетов равно 3000, а бакеты 1934 и 1410 лежат на разных шардах
- **WHEN** выполняется запрос:

```sql
SELECT count(*)
FROM (SELECT a FROM t WHERE false) l
JOIN g ON l.a = g.a
UNION ALL
SELECT a FROM t WHERE a = 2;
```

- **THEN** результат содержит ровно две строки: `0` и `2`

#### Scenario: Противоречивые равенства и глобальная таблица

- **WHEN** при тех же таблицах, данных и размещении бакетов
  выполняется запрос:

```sql
SELECT count(*)
FROM (SELECT a FROM t WHERE a = 1 AND a = 10208) l
JOIN g ON l.a = g.a
UNION ALL
SELECT a FROM t WHERE a = 2;
```

- **THEN** результат содержит ровно две строки: `0` и `2`

### Requirement: Сохранение обязательной материализации CTE

Планировщик обязан (MUST) сохранять обязательную материализацию CTE
с `VALUES`, даже если доказано исполнение на одном узле. Существующие
правила повторного использования CTE сохраняются.

#### Scenario: Соединение CTE с VALUES без переименования столбцов

- **WHEN** выполняется запрос:

```sql
WITH cte AS (VALUES (1))
SELECT *
FROM cte JOIN cte t2
ON cte."COLUMN_1" = t2."COLUMN_1";
```

- **THEN** результат состоит ровно из одной строки `(1, 1)`
- **THEN** результат CTE материализуется один раз для обеих ссылок

### Requirement: Независимость от дополнительных упрощений

Правильность результата обязана (MUST) сохраняться с включённым
и выключенным `enrich_restrictions`, а также при повторном исполнении
подготовленного запроса с другими значениями параметров.

#### Scenario: Обе настройки оптимизатора

- **WHEN** случаи совпадения бакетов, пустого входа и CTE проверяются
  при обеих настройках
- **THEN** результат в каждой настройке соответствует требованиям выше

#### Scenario: Повторное исполнение с другими параметрами

- **WHEN** для `t` с единственной строкой `a = 2` запрос
  `SELECT count(*) FROM t WHERE a = $1 OR a = $2` подготавливается один раз
  и выполняется со значениями `(1, 1)`, затем `(1, 2)`
- **THEN** первое исполнение возвращает одну строку `0`, второе — одну `1`
