# Решение

## Контекст

Проблема и пример приведены в [описании изменения](proposal.md).

`StaticResolver` хранит отпечатки ключей в `BucketSet::Exact`.
Исполнитель использует этот же тип для настоящих номеров бакетов.
Обычное пересечение корректно только для настоящих номеров.

`get_expression_tree_buckets` уже разбирает фильтры для обеих сторон.
План строится до подстановки параметров; при подстановке этапы пересылки
данных заново не выбираются.

## Цели и границы

Сохранить сведения об одинаковых ключах и исправить доказательство
без зависимости от числа бакетов. Точность означает отсутствие ложных
доказательств и сохранение случаев, перечисленных в спецификации.

Вне задачи: распознавание всех случайных совпадений бакетов разных ключей,
новые зависимости и полный перенос обхода дерева исполнителя.

## Решения

### Отдельное доказательство

Оставить реальные номера в `Buckets`. Для планирования ввести отдельный
результат: верхняя граница количества бакетов, ограничения по ключам
и признак доказанной пустоты или непустоты. Режим `Any` учитывать отдельно.

Ограничение по ключу `k` означает: любой выбранный бакет обязан совпасть
с бакетом `k`. Несколько ограничений действуют одновременно.

- `AND` сохраняет ограничения обеих сторон; граница равна минимуму.
- `OR` сохраняет общие ограничения; без них границы складываются.
- Общее ограничение даёт границу один. Доказанная пустая ветка
  не увеличивает множество при `OR`.
- Различие ключей не доказывает пустоту или разные бакеты.

Так `a = 1 AND a = 10208` сохраняет ограничения по обоим ключам.
Объединение с `a = 2` теряет общий ключ, а с `a = 1` сохраняет его.
Полный переход на оценки количества теряет эту точность; запрет только
пустых отпечатков не исправляет случай с `OR`.

### Общий разбор, разные операции

Расширить существующий `BucketsResolver`, чтобы разбор выражений
использовал операции соответствующего результата. Исполнитель продолжает
считать реальные множества, планировщик — доказательства.

Перевести `single_node_buckets`, `union_shares_one_bucket`
и `MotionsCache` на новое представление, сохранив проверку кеша
повторным вычислением в отладочной сборке.

Для `UNION ALL` учитывать объединение бакетов веток. Для `INNER JOIN`
учитывать объединение сторон, ограниченное условием соединения.
Для `LEFT JOIN` сохранять правила левой стороны, как у исполнителя.
Граница пересылки данных (`Motion`) останавливает перенос доказательства.

### Идентичность ключа

Сравнивать полное представление ключа: типы, порядок компонентов
и байты существующего кодирования для маршрутизации. Хеш допустим
для поиска, но его совпадение требует полного сравнения.

Разные параметры до подстановки не считаются одинаковыми. Для них
сохраняется существующая оценка количества; расширять оптимизацию
подготовленных запросов в этой правке не требуется.

### Пустота и запуск на любом узле

Вывод об отсутствии строк из `EqualityFacts` не доказывает отсутствие
бакетов исполнения. Пустоту бакетов определять по тем же правилам,
что и исполнитель. В частности, он распознаёт `false` и `NULL`, если
это весь фильтр или всё условие `INNER JOIN`. Отдельный `AND false`
этого не гарантирует, в том числе после `enrich_restrictions`.

`Any` означает запуск на любом одном узле. Сочетания с ним считать
отдельно по правилам исполнителя; при недостатке доказательств сохранять
обычный распределённый план. Не переносить привязку к ключу через
возможный переход в `Any`.

Сохранить изоляцию скалярных агрегатов под `UNION ALL`: они создают
строку даже при отсутствии входных строк.

### Материализация CTE

Исполнение на одном узле и сохранение результата CTE — разные решения.
Доказательство `Any` само по себе не разрешает пропускать материализацию.
В `ScanCte` сохранить существующие проверки `resolve_cte_conflicts`:
они нужны для имён столбцов `VALUES` и повторного использования CTE
над глобальными таблицами или `SELECT` без `FROM`.

Результат CTE с `VALUES` сохраняется один раз и используется всеми
ссылками. Случаи с доказанным общим бакетом сохраняют свои оптимизации.

## Риски и проверки

- Ошибка правил `AND` и `OR`: проверить их перебором небольших выражений
  и отображений ключей в бакеты, в том числе с совпадениями.
- Особые режимы: отдельно проверить `Any`, пустые множества, глобальные
  таблицы и границы `Motion`.
- Потеря оптимизации: проверить планы для одинаковых и составных ключей.
- Пропуск материализации CTE: проверить планы в `sql-frontend` и исполнение
  `cte.sql`, включая соединение CTE с `VALUES` без переименования столбцов.
- Тестовый маршрутизатор считает хеш иначе, чем рабочий. Пример с `10208`
  проверять интеграционно при 3000 бакетах на двух шардах.
- Проверить обе настройки `enrich_restrictions` и повторное исполнение
  подготовленного запроса.

## Внедрение

Изменение входит в обычную сборку; переноса данных не требуется.
Если проверка не доказывает один узел, сохраняется распределённый план.
При откате следует сохранить эту безопасную ветку, не возвращая
пересечение отпечатков в качестве доказательства.
